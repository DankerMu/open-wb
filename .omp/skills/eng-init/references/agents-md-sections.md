# AGENTS.md Section Templates

The rendered AGENTS.md sections, in order. Each template uses `{{PLACEHOLDER}}` syntax for content captured during grilling. Optional sections include skip conditions.

## Rendering strategy — concise hard kernel

For repair, incremental hardening, degraded projects, and large refactors, prefer a compact root `AGENTS.md` over a comprehensive manual. The root file should be the hard kernel agents must obey immediately — this is the *content* checklist, not the section order:

- one project/refactor rule;
- exact command entry points;
- source-of-truth links;
- verification matrix;
- forbidden moves;
- work ownership / concurrency;
- human gates / critical paths;
- enforcement index.

**Section order is fixed and Code Canonicality is always first.** Whatever the mode, however compact the render, the numbered sections below appear in their numbered order, and `## Code Canonicality` is the first section after the file header — before Project Identity, before Commands. Dropping it to a later position, or omitting it because the kernel list above does not name it, is a rendering defect: an agent that reads the top of the file and stops must already know that parallel `_v1`/`_v2` implementations are forbidden here. Trimming for compactness removes *optional* sections and shortens prose inside kept ones; it never reorders them.

Move cold explanations to linked references (`CONTEXT.md`, `constraints.yaml`, `agent_tasks/README.md`, ADRs, existing docs) or preserve them as user-owned sections. Do not copy long README/CONTRIBUTING content into AGENTS.md. A shorter file with hard constraints is better than a long file agents skim past.

## Section 1 — Code Canonicality (always, P0)

This section captures the universal code-canonicality rule plus project-specific enforcement pointers. **Always include, even in `audit-only` reports.** Reason: agents should not need external memory to know that parallel `_v1/_v2/_new` implementations are forbidden in this repo.

```markdown
## Code Canonicality

Same logic must have exactly one implementation in the repo. Version evolution belongs in git history, not in filenames or identifiers.

- Before adding any function, class, module, or file: grep the codebase for existing similar implementations. If found, extend or refactor the existing one. Only create new if truly absent.
- Forbidden suffixes for filenames, class names, function names, and module names: `_v1`, `_v2`, `_v3`, `_new`, `_old`, `_backup`, `_temp`, `_copy`, `_final`, `_real`, `_improved`, `_refactored`, `_fixed`, `_legacy`, `_deprecated`. If one exists in the codebase already, treat it as debt to unify, not a pattern to extend.
- Refactor in place: commit the working state first, modify the original file, run tests. If it breaks, `git revert`. Never keep an old version alongside the new "just in case" — git is the safety net.
- No parallel implementations as a transition unless `## Source of Truth & Refactor Contract` explicitly names a staged dual-run or compatibility-bridge cutover policy. Without that written exception, do not ship v2 while v1 still exists; replace atomically.
- Commented-out code is a lint error, not a safety net. Delete it; git remembers.
- Unreferenced exports and dead code paths are debt. Wire them up in the same change or delete them.
- Do not use the repo as a scratchpad. Directories like `tmp/`, `scratch/`, `backup/`, `_old/`, `deprecated/`, `archive/`, `wip/` must not appear in commits.

### Enforcement

| Rule | Enforced by |
|------|-------------|
| Forbidden suffixes | {{NAMING_GUARD_PATH}} (pre-commit hook) |
| Duplicate code | `{{DUPLICATE_CODE_TOOL}}` (`{{DUPLICATE_CODE_CONFIG_PATH}}`) — CI fails if duplication exceeds the configured threshold |
| Dead code | `{{DEAD_CODE_TOOL}}` in pre-commit + CI |
| Commented-out code | `{{COMMENT_LINT_TOOL}}` (lint rule {{RULE_ID}}) |
| Scratchpad dirs | {{NAMING_GUARD_PATH}} (pre-commit hook) |
| Conventional commits | `{{COMMIT_CHECK_TOOL}}` ({{COMMIT_CHECK_CONFIG_PATH}}) |

Every row above must point at a tool that actually runs. If a tool is not wired, that row is a gap: wire it in the same change, or move the rule to the Enforcement Index as `review-only` so nobody mistakes it for a machine check.
```

## Section 5a — Verification Matrix (always at L2+; optional L1 unless rehabilitation is active)

Rendered immediately after `## Development Workflow`. Maps every runtime surface to the command that verifies it and the evidence a PR must show. Required at L2+ and whenever `{{IF_REHABILITATION_OVERLAY}}` is true; optional at L1 only for healthy projects. Drop rows for surfaces the repo lacks — a row for a surface that does not exist is noise.

```markdown
## Verification Matrix

| Surface | Verify with | Command | Evidence required |
|---------|-------------|---------|-------------------|
| Liveness / health | Health endpoint probe | `{{DEV_STATUS_CMD}}` | HTTP 200 + jsonpath $.status == "ok" |
| API endpoint | Smoke test via hurl/curl | `{{SMOKE_CMD}}` | HTTP status + response body |

| CLI command | Run against known input | `{{CLI_VERIFY_CMD}}` | Exit code + output |
| DB migration | Up + down on a fresh DB | `{{DB_VERIFY_CMD}}` | Migration log |
| Background job | Trigger job, observe completion | `{{JOB_VERIFY_CMD}}` | Job log + resulting state |
```

## Section 6 — Important Development Notes (always)

High-density, repo-specific footguns. Each line should be a concrete rule with a short reason (preferred form: "Do X, not Y (because Z)."). These notes are where you document exceptions to otherwise-general rules (e.g., "Normally run the full check suite, but docs-only changes may skip build."). Hard cap: max 10 entries, every entry dated, pruned at milestones — an undated note is unverifiable, date everything. The Incident-to-constraint ratchet (§ Agent Operating Rules) feeds and prunes this list.

Constraint lists **earn entries through real incidents**: seed this section and per-stack pitfall lists from failures that actually happened (Q6.7 answers, postmortems, review comments that repeated) — never from generic best-practice inventories. A short list of load-bearing rules beats a long list nobody reads; when an incident reveals a missing guard, add the narrowest durable rule, preferring executable enforcement over another prose line.

```markdown
## Important Development Notes

Max 10 entries, dated, pruned at milestones. An undated note is unverifiable — date everything.
```

## Section 7 — Conventions (always)

```markdown
## Conventions

### Naming

- Files: {{FILE_NAMING}} (e.g., kebab-case for TS, snake_case for Python).
- Identifiers: {{IDENT_NAMING}} (camelCase / snake_case / PascalCase per stack norm).
- Tests: {{TEST_NAMING}} (e.g., `*.test.ts`, `test_*.py`, `*_test.go`).
- Forbidden suffixes: see Code Canonicality section above.

### Debt markers

- `FIXME` — should block the next release; a release ships with an open `FIXME` only when reviewers explicitly accept it.
- `TODO` — fix as soon as resources allow.
- `XXX` — maybe someday; lowest priority, no commitment.
- Pick the tag matching the urgency so anyone scanning code can tell a release blocker from a someday-maybe; the tech-debt scanner reports them by grade.

### Deviations carry reasons

- Every non-default configuration value — a rule switched off, a pool or concurrency choice, a timeout, an exclusion — carries an inline comment naming its motivating failure mode. An unexplained deviation does not survive the next cleanup, and should not.
- An empty catch names what it swallows and why nothing else can reach it; keep the guarded block to the one statement that can throw it.

### Commit format

- Conventional commits required: `<type>(<scope>): <message>`.
- Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `ci`, `build`, `perf`.
- Scopes: {{SCOPES_LIST}} (typically module / package names).
- Body: optional, but required for breaking changes (prefix line with `BREAKING CHANGE:`).
- Enforced by `{{COMMIT_CHECK_TOOL}}` ({{COMMIT_CHECK_PATH}}).

### Pull requests

- Use the PR template at `.github/PULL_REQUEST_TEMPLATE.md`.
- Required sections: Summary, Test plan, Risk.
- Required labels: one of `feat`, `fix`, `refactor`, `chore`.
- Reviewers: at least {{REVIEWER_COUNT}}. {{CODEOWNERS_LINE}}

### Branch model

- {{BRANCH_MODEL_DESC}} (e.g., trunk-based on `main`; feature branches named `<author>/<short-slug>`).
- Branch protection on `main`: {{BRANCH_PROTECTION_RULES}}.
- Stacked PRs: a branch may be deleted only when no open PR bases on it — deleting a base branch auto-closes every PR that bases on it, silently destroying the chain. Use the platform's native stacked-PR mechanism whenever available (e.g. GitHub `gh stack`): the platform owns stack identity, ordering, retargeting, and merge state. If unavailable, do not use a stacked-PR chain at all — no per-PR merges with manual retargeting. Land dependent PRs sequentially (open the next only after the previous one merges), or fold the chain into a single change. Rewriting pushed history is allowed only with `--force-with-lease`, aborts if the remote moved, and never uses raw `--force`.

### Coverage threshold

- Minimum {{COVERAGE_PERCENT}}% line coverage. CI fails below this.
- At L3/L4 the threshold is **per-file**, not repo-wide — a global threshold lets a well-covered big file subsidize a bare one.
- Read an uncovered line as a dead-code candidate first and a missing test second: the coverage gate doubles as a dead-code detector. Delete the line or test the behavior; never bolt an assertion-free test onto it.
- Every coverage-ignore comment carries a reason. Every exclude entry carries a reason **and an exit condition** (`constraints.yaml` `exemptions`), so exemptions shrink instead of accumulating.
- Enforced by `{{COVERAGE_CONFIG_PATH}}`.
```

## Section 8 — Code Review Self-Check (always)

Agents run this checklist before opening a PR (or requesting human review). Keep this short and strict; it exists to prevent avoidable review churn and CI ping-pong.

```markdown
## Code Review Self-Check

- Can explain "why this approach" vs the nearest obvious alternative; matched existing patterns unless there is a stated reason to diverge.
- Verified the bug/feature is addressed at the correct layer (not just silencing a symptom).
- Ran the checks selected per `### Scoped verification` — the narrowest evidence covering every changed surface — and they pass on this branch (full `{{CHECK_CMD}}` only when the change is genuinely repo-wide or CI needs diagnosing).
- Added/updated tests for the change, and verified the new/changed tests fail before the fix and pass after.
- Updated docs/comments only if they materially help future readers; did not add tutorial text.
- Checked for canonicality violations: no `_v2` files, no duplicated logic, no dead exports, no scratch dirs.
- Avoided hidden dependencies: no new implicit global state, no environment-only behavior without documenting it in `## Development Workflow`.
- Kept the diff focused: no drive-by refactors, no unrelated formatting churn.
- Wrote a PR description that states: intent, approach, test plan, and risk; did not overstate what works (explicit about what was not tested).
```

```
### Out-of-bounds operations

{{OOB_LIST_FROM_USER}}

### Debugging CI failures (protocol)

When CI fails, do not guess. Identify which layer failed, reproduce locally with the same command, then fix the root cause and re-run the failing layer.

1. **Classify the failure layer** (names match the risk-layered CI template): `layer1-fast-checks` (fmt/lint/typecheck), `layer2-unit-tests`, `layer3-integration-tests`, `layer4-anti-drift` (duplicate/dead code), `layer5-secret-scan`.
2. **Read the logs first.** Extract the *first* actionable error and the exact command CI ran.
3. **Reproduce locally** using the same command from `## Development Workflow` (never "something close").
4. **Fix the root cause**, not the symptom (e.g., correct a flaky test instead of increasing timeouts).
5. **Re-run the same layer locally**, then run `{{CHECK_CMD}}` before pushing.
6. If CI failure is due to environment parity (OS/version/service), record the mismatch in `## Important Development Notes` so the next agent doesn’t repeat it.

### Evidence requirements

- Success claims require fresh command output from the current session: command + exit code + relevant output.
- **Verify the world, not the self-report.** Evidence for "the agent/tool did X" must observe the world: re-execute the command, re-read the file externally, hit the real endpoint, query the row. Keyword-probing the agent's own transcript or output is not evidence — a cheating or confused agent passes that probe.
- When a claim implies "and nothing else changed", assert it: untouched files byte-identical, no unexpected rows, no stray processes.
- UI claims require a screenshot + zero new console errors.
- A success claim without fresh output is treated as unverified.
- PRs include a `## Runtime evidence` section; "None — review-only change" is allowed only with a stated reason.

### Scoped verification — evidence matches the surface

- Select the **narrowest** check that covers the changed behavior, and report only commands actually run:

| Change surface | Narrowest evidence |
|---|---|
| Behavior in one module | the focused tests owning that module |
| Model-/user-visible output | the owning snapshot/compare suite |
| Docs | doc gates (links, generated `--check`) |
| Build/publish path | build + packaging checks + built-artifact smoke |
| External provider behavior | the real-API e2e slice |

- Never default to the full suite, and never rerun a passing check just because a commit or push comes next — CI owns exhaustive coverage and the platform matrix. Full local rehearsal is for explicit request, CI diagnosis, or a genuinely repo-wide change.
- Test selection and coverage selection are separate decisions: name the affected files in the coverage scope explicitly; never use pass-with-no-tests or a narrowed include to hide an uncovered affected file.
- Derive the change list from an explicit base via `{{CHANGE_SCOPE_CMD}}` — never from a guessed upstream.

### Iteration loop gates

- Max 3 fix-and-recheck cycles per failing check; then stop and report what was tried and what specific help is needed.
- Never weaken, skip, or delete a test to get green. A skip requires a linked issue + a deadline.
- Checkpoint commit at every green state.
- One task = one branch.

### Environment tiers

| Tier | Agents may |
|------|------------|
| Local | Everything within these rules |
| Staging | Deploy only via CI; read logs and dashboards |
| Prod | Nothing destructive; read-only observability at most ({{PROD_ACCESS_OR_NONE}}) |

### Concurrency model

- Parallel agents use separate git worktrees; never share a working tree.
- Feature branches named `{{BRANCH_PATTERN}}`; one task = one branch.
- Rebase onto the target branch before opening or updating a PR — no merge commits from the target into the feature branch.
- Lockfile conflicts are resolved by re-running `{{INSTALL_CMD}}` from the merged manifest and committing the result — never hand-edit a lockfile.


{{IF_REFACTOR_WORK_UNITS}}
### Refactor work ownership

- Claim exactly one refactor work unit before editing (`agent_tasks/`, issue tracker, GitHub label, or the tracker named in `## Source of Truth & Refactor Contract`).
- Do not duplicate another agent's claimed failure. If ownership is unclear, stop and ask before editing.
- Each work unit must name: Goal, Reference, Reproduce command, Allowed files, Forbidden moves, Done when, Owner, Started, and Notes.
- Close a work unit only after its verifier passes and the evidence is recorded.
{{END_IF}}
{{IF_REFACTOR_SINGLE_OWNER}}
### Refactor ownership

- No parallel refactor agents. One agent/person owns the refactor at a time.
- Before handing off, record current failing verifier, files in progress, and next intended step in `## Important Development Notes` or the agreed tracker.
{{END_IF}}

{{IF_REFACTOR_OVERLAY}}
### Large-refactor agent roles

- **Discover**: reproduce the failure, compare with the `Reference`, identify root cause, and write the evidence into the claimed work unit or single-owner handoff note. No implementation edits.
- **Fixer**: edit only the allowed files named by the work unit, tracker item, or current refactor handoff after a Discover note or failing regression identifies the scope. Add or update the smallest regression/compare case that proves the fix.
- **Reviewer**: compare the result against `## Source of Truth & Refactor Contract`; reject untested divergence, weakened or skipped compare tests, silent fallback, and files outside the allowed scope.
- **Delegation is trust-but-verify.** A delegated agent's report describes intent, not necessarily what landed: the accepting role re-runs the gates itself on the real tree. For a regression guard, prove it fails on the unfixed code (introduce the regression, watch it go red, revert) — a guard that passes on both sides guards nothing. An agent that reframes the problem as "already handled" is a signal to dig in personally, not to close the unit.
- **Environment attribution needs evidence.** Claiming a failure is environment-specific requires the exact command, exit code, and the platform difference; without that, treat it as a real failure.
- A single person may play multiple roles only on small repos, but the evidence must still be separated: discovery evidence, fix evidence, review evidence.
{{END_IF}}

- Snapshot updates are reviewed hunk-by-hunk; blanket regeneration is forbidden.
- Generated code is changed only via its generator, never edited by hand.
```

## Rendering rules

- **Substitute every eng-init placeholder.** Upper-snake `{{PLACEHOLDER}}` tokens are eng-init placeholders; substitute them fully before writing. Lowercase tokens such as `{{route}}` in just recipes or `{{base_url}}` in `.hurl` files are target-tool runtime variables and may remain literal. - **Delete empty list items.** If a placeholder like `{{NOTE_4_OR_BLANK}}` is blank, remove that numbered line entirely.
- **Preserve order.** Do not reorder sections; ordering encodes priority for the reader (Code Canonicality first because it is the most violated).
- **Quote user wording verbatim** in Project Identity and any rule the user phrased directly. Paraphrasing strips meaning.
- **Keep auxiliary file paths absolute-from-repo-root.** Never relative paths in this file. E.g., `.husky/pre-commit`, not `husky/pre-commit`.
- **Size budget.** Rendered root `AGENTS.md` must stay under 320 lines, with a target of ≲290 lines. (Raised from 275 when v3.1/v3.2 added roughly 40 lines of always-rendered rules — Scoped verification, Known blind spots, debt markers, deviations, stacked-PR deletion; a ceiling that ignores content the skill itself mandates is a budget bug.) When over budget, **relocate before condensing and condense before raising**: push stack detail to module-level `AGENTS.md`, `agent_tasks/README.md`, or linked reference files first. The two largest sections in a full L3/L4 render are Agent Operating Rules and Enforcement Index — relocate from there, and never drop a rule to fit. Ordering encodes priority — never reorder to save space.
