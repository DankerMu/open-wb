# chat-sessions Specification

## Purpose
定义会话、消息与执行步骤的 schema 和追加迁移，以及账号隔离的存储视图、原子受理与补偿、正文刷盘、步骤和终态、故障恢复、关闭及显式启动对账契约。REST/runtime/SSE装配由后续变更增补。

## Requirements

### Requirement: 会话数据 schema
Migration032_chat_sessions.sql SHALL atomically create chat_sessions, chat_messages and chat_steps using the existing runner-owned transaction. Existing0010/002/010/030/031 receipts and business data SHALL remain unchanged;032 SHALL append as the sixth receipt without changing ledger validation.

### Requirement: 会话文本无损读取与标题复用
SessionStore SHALL preserve complete text values, including embedded U+0000, leading U+FEFF, non-ASCII and astral characters, across list/getMessages titles, user and assistant content, step name/detail/output, and trusted runtimeState ompSessionFile. Public outputs SHALL remain strings or the existing nullable values. Empty string and SQL NULL SHALL remain distinct, except that a NULL step output (pre-033 rows and unfinished steps) is read as an empty string in step views. Appended content and finish/close flushes SHALL retain the complete concatenated value.
Admission SHALL reuse an existing title without truncating its suffix, retain the complete previousTitle for rollbackPrompt, and keep the persisted title storage class TEXT. The first-title Unicode-prefix rule SHALL remain unchanged. The fix SHALL NOT claim recovery of suffixes already overwritten by older admissions.
Lossless reading SHALL respect the actual database text encoding. Existing UTF-8, UTF-16le and UTF-16be databases SHALL remain readable without changing encoding, schema, unrelated data or migration receipts. Per-connection encoding selection SHALL NOT leak between databases. Leading U+FEFF SHALL be preserved; no new fatal invalid-byte policy, character stripping or input rejection SHALL be introduced. Failed encoding/SQL reads SHALL propagate rather than silently selecting a guessed encoding.
Owner isolation, order, status transitions, epoch/resume independence, transaction boundaries and compensation/flush errors SHALL remain as already specified. The shared text-read implementation SHALL have one canonical owner in core/db and no per-consumer alternate decoding implementation.

### Requirement: REST prompt 受理与补偿
The prompt route SHALL accept only application/json and an object whose key set is `{message}` or `{message,attachments}`, with message:string and the optional `attachments` an array of path strings (shape, preconditions, sandbox resolution and the rejections 400/403/404 are message-attachments「prompt 携带附件」; an absent `attachments` and `[]` are the same request). It SHALL trim the string once and require text of at most32768 UTF-8 bytes; the trimmed text SHALL be nonempty unless the request carries a nonempty `attachments` (owner ruling 2026-10-06: a prompt may consist of attachments only). The `message` key SHALL be present and a string in every case. Empty trimmed text with `attachments` absent or `[]` SHALL return400 bad_request as before; empty trimmed text with a nonempty `attachments` is never rejected for being empty — it is admitted when the list passes every check of message-attachments「prompt 携带附件」 and otherwise rejected with that check's own result (400/403/404). Invalid shape, media, malformed JSON or oversized parser envelope SHALL return400 bad_request; decoded valid escape-heavy text SHALL NOT be rejected merely because its wire JSON exceeds32768 bytes. The existing bounded parser envelope remains distinct from the semantic message limit. A trimmed text that starts with `/` SHALL NOT be rejected for that reason: Requirement「Slash 命令白名单与命令目录」 decides whether it reaches omp as a command or as plain text.
The route SHALL use store.acceptPrompt(sessionId,principal.id,text,attachments) — `attachments` being the validated `[{path,size}]` list or none, stored on the user row in the same admission (message-attachments「附件落库与快照」) — with the trimmed original text for the atomic admission (the persisted user content is that trimmed text — the empty string for an attachment-only prompt, with no other normalisation; the first title follows Requirement「会话持久化与回合刷盘」: the 18-code-point prefix of the text, or of the first attachment's file name when the text is empty), then await supervisor.prompt(sessionId, toWireText(text, skills) + attachmentSuffix(paths), snapshotStep) — with no await between the admission and that call; the suffix is the empty string without attachments, so such requests dispatch the same bytes as before (message-attachments「交给 omp 的附件后缀」); an empty text takes no branch of its own: `classifyPrompt("")` is `text`, `toWireText` returns it unchanged and the dispatched text is the suffix alone — where `snapshotStep` is the never-rejecting pre-dispatch step that records the per-turn workspace snapshot of the admitted user message as specified by workspace-snapshots「受理时做快照」 (run by the supervisor before any acquisition or dispatch, see Requirement「Supervisor dispatch and generation binding」; its outcome never fails the prompt: `too_large` and `failed` outcomes still dispatch), and where `skills` is `sessionSkills(agentDir, cwd, sandboxRoot)` for that session's cwd, computed only for text starting with `/` (`[]` otherwise), and `toWireText`/`sessionSkills` are those of Requirement「Slash 命令白名单与命令目录」 (identity for every text that does not start with `/` and for whitelisted commands; a leading U+0020 otherwise) and `agentDir` is the registerSessionRoutes dependency of Requirement「会话 REST」. The owned SessionSupervisorPort SHALL expose prompt(sessionId:string,text:string,beforeDispatch?:()=>Promise<void>):Promise<void>; resolution means dispatch accepted, not turn finished. Successful admission SHALL return202 {userMessageId,assistantMessageId,undo}: the two ids from that exact store admission and `undo` the undo state of the admitted user message (message-undo「可撤回状态」; one of `available|too_large|failed|command|unbound|none`). An archived session (`archived_at` non-NULL) SHALL return409 session_archived without added rows, snapshot or dispatch, checked in the same synchronous segment as admission (session-metadata「会话归档」). Running sessions SHALL return409 session_busy without added rows or dispatch; so SHALL a session whose supervisor control claim is held by an in-progress regenerate, fork or stop — the claim check and admission SHALL run without an intervening await; idle/done/failed/stopped SHALL be eligible.
Supervisor rejection SHALL compensate the unprogressed accepted pair through store.rollbackPrompt before returning the canonical error; the snapshot row of the removed user message goes with it (foreign-key cascade) and its snapshot directory is removed after the compensation. HttpError agent_unavailable SHALL produce502, HttpError session_busy SHALL produce409, HttpError agent_capacity SHALL produce503; unknown failures SHALL remain generic5xx. Compensation failure SHALL propagate as generic5xx, not be masked as502/409/503. The supervisor SHALL NOT reject after publishing/persisting progress; post-dispatch failures belong to supervisor lifecycle. No retries or real runtime/SSE implementation are part of this boundary.

### Requirement: Supervisor dispatch and generation binding
SessionSupervisor SHALL implement the prompt(sessionId,text,beforeDispatch?):Promise<void> port (the optional third argument is a `() => Promise<void>` pre-dispatch step, added by s1f-session-list-temp-space for the per-turn workspace snapshot) using the already-admitted store.runtimeState active pair, owner, resume metadata and workspace binding. runtimeState SHALL report the session's `workspaceId` (the `workspace_id` column) and the supervisor SHALL resolve the cwd from it: when `workspace_id` is non-NULL, the root returned by the workspace store's owner-scoped `rootOf` called with the session's `owner_id` as principal id; otherwise the owner root `<SANDBOX_ROOT>/<ownerId>` used before this change. Every spawn of a session generation and every fork temporary runtime SHALL pass that cwd as omp `--cwd`; a non-NULL `workspace_id` for which `rootOf` returns null SHALL fail the acquisition as a generic failure (compensated like other acquisition failures) and SHALL NOT fall back to the owner root; when `rootOf` returns a root that does not exist as a directory at acquisition time, the supervisor SHALL NOT create it (no mkdir of a workspace root) and SHALL NOT spawn or fall back, and the acquisition SHALL fail as agent_unavailable (REST 502 with the ordinary prompt compensation); a failure thrown while resolving the bound root (including `rootOf` rejecting a root that exists but is not a plain directory, or any fault inside that resolution) SHALL likewise fail as agent_unavailable, a narrow exception to generic storage-fault provenance. The binding is immutable, so a resumed generation's cwd equals the one recorded when the session file was created. On the prompt path it SHALL neither admit nor compensate a pair itself. When `beforeDispatch` is given, the supervisor SHALL run it exactly once, after the turn has entered the pre-dispatch phase in which a stop registers a stop intent (turn-control「停止生成 REST」; entered in the same synchronous segment as the call, with no await between REST admission and that point) and before waiting for a retiring instance, pool admission or any spawn; it SHALL await its settlement and then apply the same closed/claim rechecks that follow its other pre-acquisition waits. A `beforeDispatch` rejection SHALL reject the port as a generic failure through the ordinary failed-dispatch path (the turn's stop state released, REST compensates); callers that must not fail the prompt (the snapshot step) SHALL pass a step that never rejects. While the step is pending the turn has no dispatched prompt: a stop SHALL register the intent and return, and the one `abort` SHALL be requested after the dispatch receipt exactly as for a stop that arrives during pool admission. Regenerate and fork (Requirement「会话 REST」) are supervisor-owned admission and compensation paths: the supervisor SHALL perform their single final SQLite transaction (including the control-claim recheck) and their failure compensation (retiring the process, shutting down a fork's temporary process, or settling a dispatched regenerate assistant row `failed`). The supervisor SHALL hold a per-session control claim for regenerate, fork and stop from a passed precheck until dispatch completes or the response is returned; while it is held, prompt, regenerate and fork on that session SHALL be rejected with session_busy (a stop after regenerate has dispatched proceeds normally because the session is then `running`), and the claimed session's process counts as in-turn for the process cap. It SHALL reject duplicate supervisor admission and close new admission during shutdown. Runtime SessionBusyError SHALL become canonical session_busy; AgentUnavailableError and OmpProtocolError SHALL become agent_unavailable. Storage, registry and unknown adapter faults SHALL remain generic failures: acquisition-specific adapter provenance SHALL take precedence over the runtime's sanitized error. On the regenerate and fork paths the failure mapping of turn-control「重新生成 REST」and「从此处分叉 REST」takes precedence over this rule: a storage fault of their final transaction, and any regenerate dispatch failure after that transaction commits, SHALL reject with agent_unavailable; a failed control-claim recheck SHALL reject with session_busy.
The supervisor SHALL await the exact runtime dispatch receipt and persist the validated sessionFile before resolving the REST port, without consuming business frames first. Pre-progress failure SHALL retire/discard that runtime before rejecting so REST can compensate. No post-progress error SHALL reject the already-accepted REST operation.
Every runtime generation acquisition, including idle re-spawn, crash recovery and a regenerate on a session whose process has been reclaimed or evicted, SHALL increment stream_epoch exactly once via the existing store method before shared-token issuance; reuse of a live generation SHALL not increment it. Regenerate SHALL acquire that normal generation (epoch+1, a fresh ring) through the same lazy acquisition path as prompt. A fork's temporary runtime is not a generation: it SHALL NOT bump either session's stream_epoch, own a ring, publish events or bind a session slot, and counts only against the process cap. Failed acquisition may advance epoch independently of REST compensation. Runtime SHALL retain token-revocation ownership; native exit SHALL make that generation token invalid, without stale callbacks revoking a newer token. No requestId SHALL be guessed from an ACK.

### Requirement: Supervisor ordered persistence and publication
The supervisor SHALL initialize the canonical pure mapper with the exact admitted assistant id and dispatch requestId. It SHALL consume the full runtime iterator, preserving arrival order including frames before ACK. toolCallId SHALL map to numeric startStep results using zero-based per-turn ordinals; public events SHALL carry numeric stepId only. Stop is the one exception: when a stopped turn's `agent_end` does not arrive within the bounded grace and the supervisor retires the runtime (turn-control), the supervisor SHALL settle the turn `stopped` and synthesize exactly one `turn.end{status:"stopped"}` through applyStop without any error event; late frames or the native exit of that retired runtime SHALL NOT produce error or a failed turn.end. Whenever a turn ends without the child answering its pending approvals (failure, stop retire), the terminal transaction SHALL settle them `deny` (Requirement「会话持久化与回合刷盘」) and the supervisor SHALL publish each `approval.resolved` after that commit and before turn.end, writing no frame to the dead or retiring child. A stop posted while the runtime is holding such a turn open follows the stop exception above: the `abort` frame makes omp cancel the compaction silently, so no `agent_end` arrives and the supervisor settles the turn `stopped` through applyStop after the bounded grace.

### Requirement: Slash 命令白名单与命令目录
`server/src/sessions/slash-commands.ts` SHALL export the builtin whitelist `BUILTIN_COMMANDS` in this fixed order: `compact` (label `整理上下文`, description `压缩较长对话的上下文，保留要点`, hint `可选：想保留的重点`) and `todo` (label `任务清单`, description `查看或修改助手的任务清单`, hint `可选：append <任务>`); no other omp builtin SHALL be whitelisted by this change (`retry` is deliberately excluded: turn-control's regenerate already covers it and its `agentInvoked:true` receipt would add a second local-command completion mode). It SHALL export `listSkills(agentDir)`: synchronously enumerate the entries of `<agentDir>/skills` whose name does not start with `.`, keep at most the first 256 of them in code-point order of their SKILL.md path (further entries are ignored without any filesystem access), and read `<entry>/SKILL.md` for each kept entry without branching on the entry type (a plain file simply fails the read). A symlink is followed only inside the skills directory — a deliberate host restriction; omp itself follows any symlinked directory (`discovery/helpers.ts:428-431`): the host resolves the real path of `<entry>/SKILL.md` and skips the entry unless that real path lies inside the real path of `<agentDir>/skills` — both real paths SHALL come from the kernel (`realpathSync.native`), not from Node's JS `realpathSync`, which stops resolving at a FIFO or socket and folds `..` lexically, so its result can name a different file than the one the kernel opens; and both SHALL be kept as the raw bytes the kernel returned (`{ encoding: "buffer" }`): the containment check compares bytes and the open is given the same bytes, because decoding a path to a string replaces every ill-formed UTF-8 sequence with U+FFFD and re-encoding it names a different path — then opens the resolved path with `O_NOFOLLOW`, so file content outside `skills/` never reaches the catalogue through a link; the read SHALL be bounded and non-blocking as defence in depth — under omp-runtime「OMP_STATE_DIR 托管布局」 the directory is no longer writable by the omp uid, but whatever an operator installs there is still read by the server process: SKILL.md is opened with `O_NONBLOCK | O_NOCTTY` (a terminal device placed there cannot become the server's controlling terminal), and only a regular file of at most 262144 bytes is read — a FIFO, device, directory or larger file is skipped like an unreadable one; normalise `\r\n?` to `\n` and read only the leading frontmatter block — the content starts with `---` and the block ends before the first later line starting with `---`; an unclosed block is no frontmatter — taking, without a YAML library, the top-level (unindented) `key: value` lines for `name`, `description` and `enabled`: a value is trimmed and loses one pair of surrounding quotes; a value that is exactly a block-scalar indicator (`>` or `|`, optionally followed by `+` or `-`) takes the following more-indented lines, each trimmed, joined with one U+0020 (`>`) or `\n` (`|`); `name` defaults to the entry name when missing or empty. An entry is skipped when SKILL.md is missing or unreadable, when `description` is missing or empty, or when the unquoted `enabled` value is `false` (omp's own drop rules for a user-level skill: `discovery/builtin.ts:295-300`, `discovery/helpers.ts:397-403`), and — a host rule; omp does not validate names — when `name` does not match `^[^\s/]+$` (such a name cannot be selected through `/skill:<name>`, whose name ends at the first U+0020). Entries sharing a `name` collapse to the one whose SKILL.md path is smallest in code-point order (omp is first-wins over the same order, `extensibility/skills.ts:220-221`). Any failure to enumerate `skills` (absent, not a directory, unreadable) yields `[]`, as omp's scan does (`discovery/helpers.ts:384-392`); the result is sorted by `name` in code-point order and is recomputed on every call (no cache). It SHALL export `listProjectSkills(cwd, sandboxRoot)` (#773): the project skills of a session cwd, read from `<D>/.omp/skills` for the directories `D` = `cwd`, its parent, and so on, stopping after the first `D` where `lstat(<D>/.git)` succeeds (that `D` is still scanned — omp's `repoRoot`, `capability/fs.ts:84-95`, `discovery/builtin.ts:284`; the host does not enumerate `D`) or after `sandboxRoot`, whichever comes first. The walk runs on kernel real paths: `cwd` and `sandboxRoot` are first resolved (`realpathSync.native`, raw bytes), and a resolved `cwd` that is neither the resolved `sandboxRoot` nor below it (byte prefix followed by `/`) yields `[]` — the sandbox root is `2770` and the owner root is not checked for links by the session cwd resolver, so the omp uid can put a symlink where a cwd is expected; every `D` is a parent of the resolved `cwd`, hence a real directory inside the sandbox. Each `<D>/.omp/skills` is read by exactly the rules of `listSkills` above (hidden entries, the 256-entry cap, kernel real paths as raw bytes with the containment boundary being that `skills` directory, `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, regular file of at most 262144 bytes, the frontmatter reader, the skip rules and the name rule), with three additions because the directory is writable by the omp uid: a `SKILL.md` whose `fstat` link count is not 1 is skipped (a hard link to a file the server can read would otherwise echo that file's frontmatter); the kernel real path of `<D>/.omp/skills` SHALL equal, byte for byte, the kernel real path of `D` followed by `/.omp/skills` — so neither `.omp` nor `skills` is a link and the containment boundary cannot be moved outside `D` — otherwise that `D` yields nothing; and the directory is enumerated through a directory handle reading at most 4096 entries — one holding more yields nothing for that `D` (the 256-entry cap applies after the sort, as for the platform directory); a `description` longer than 200 code points is cut to its first 200. A name found in a nearer `D` hides the same name in a farther one (omp v18.0.10, verified by run: nearest project skill wins); the result is sorted by `name` in code-point order, never throws (any failure for one `D` yields nothing for that `D`) and is recomputed on every call. Only `.omp/skills` is read: omp v18.0.10 also loads project skills from `.claude`, `.codex`, `.agents`, `.agent`, `.opencode` and `.github` under the cwd (the first, third and fourth also under its ancestors), from the same four directories under the managed `HOME`, and from ancestors above `sandboxRoot` when no `.git` stops it; none of these is listed, and in the two precedence pairs run against the real binary (`.omp` project vs `.claude`/`.codex`/`.agents` project of the same name; platform vs `.claude` project of the same name) the `.omp` or platform skill won, so a listed name runs the listed skill — unless a nearer `.omp/skills` holds a skill of that name which the host's read rules skipped and omp loaded (omp follows links and has no caps): then the farther or platform entry is listed with its own `source` and `overrides` while omp runs the nearer one (accepted residual). It SHALL export `sessionSkills(agentDir, cwd, sandboxRoot)`: the platform skills of `listSkills(agentDir)` and the project skills of `listProjectSkills(cwd, sandboxRoot)` as `{name, description, source: "skill" | "project", overrides}` — a project skill replaces the platform skill of the same name (omp runs the project one) and carries `overrides: true`; every other entry carries `overrides: false`; platform entries first, then project entries, each group in name order. A file is listed only when `lstat` says regular file (a symlink is not followed and not listed); the host reads no content, and any filesystem error for a location lists nothing for it. ### Requirement: 派发前按会话设置对齐进程
`store.runtimeState` SHALL 在既有内容之外报告会话行的 `approval_mode`、`model_id`、`reasoning_effort` 三个原始列；supervisor SHALL 在每一次派发——prompt 与 regenerate——时由它们经 session-composer-settings「有效值解析」的同一个纯函数算出有效值，并在写出该回合的 `prompt` 帧之前按下列次序使进程与之一致。有效值在一次派发内只算一次；派发之间不缓存。

1. **审批档位**。每个 slot SHALL 记下其进程启动时所用的档位。存活且可复用的 slot 的启动档位与有效档位不同时，supervisor SHALL 先退役该 slot（与空闲回收、驱逐相同的退役路径，等待其完成），再走一次普通的新准入：新进程以有效档位与最后已知的会话文件 `--resume` 启动，是一个正常的新 generation（`stream_epoch` 恰加一、新的 ring、经进程上限准入，`agent_capacity` 照常为 503）。启动档位与有效档位相同时 SHALL 复用存活进程，不因本条多一次重启。
2. **模型与推理强度**。每个 generation SHALL 记下在它上面最近一次成功应用的模型与强度（新 generation 为「尚未应用」）。取得进程之后：尚未应用、或有效模型与已应用的不同 → 经 `runtime.command` 发 `set_model{provider:"workbuddy", modelId:<有效模型>}`；随后若有效模型支持推理，且（本次刚发过 `set_model`，或有效强度与已应用的不同）→ 发 `set_thinking_level{level:<有效强度>}`。两者都未变时不发命令帧；有效模型不支持推理时不发 `set_thinking_level`。命令成功后才更新所记的已应用值。prompt 路径上这一步紧接在取得进程之后；regenerate 路径上它同样紧接在取得进程之后、`get_branch_messages` 之前（turn-control「重新生成 REST」的执行序），即先于 `branch` 与该路径的 SQLite 事务。
3. 写出 `prompt` 帧（既有的派发回执规则不变）。

第 1、2 步的任何失败（退役或准入失败、`command` 以 `AgentUnavailableError` 拒绝、进程在其间退出）SHALL 作为派发前失败处理：不写 `prompt` 帧，该 slot 被退役，prompt 路径以 `agent_unavailable` 拒绝使 REST 补偿受理对（`agent_capacity` 保持 503）；regenerate 路径上这两步都发生在 `branch` 与事务之前，所以属于「事务前失败」：502 `agent_unavailable`（准入满为 503 `agent_capacity`），不发 `branch`，不改任何行——被重新生成的旧助手消息及其步骤、审批保持原样，`omp_session_file` 不变，占用释放。regenerate 的事务提交之后只剩写 `prompt` 帧一步，其失败映射不变（新助手行记 `failed`）。第 2 步发生在该会话的回合认领已登记之后，其间到达的 prompt / regenerate / fork 照常得到 `session_busy`。
走到派发时该会话没有在途回合也没有被持有的控制占用（既有的 prompt 与 regenerate 前置），所以第 1 步的退役 SHALL NOT 打断任何回合或待决审批。会话设置的修改（`PATCH`）SHALL NOT 触发本条的任何动作：supervisor 不被通知，存活进程在下一次派发之前保持原状。
fork 的临时进程 SHALL 以源会话的有效档位与有效模型作为 spawn 参数，SHALL NOT 执行第 2 步（它不派发 prompt）；fork 对源会话存活进程的先行退役规则不变。空闲回收、崩溃恢复、驱逐后的再次获取都经同一条派发路径，因而同样按当时的有效值启动并重新应用模型与强度。
