# Design: s1f-chat-followups

## Context

`s1f-chat-surface` 归档后，#874 的备注逐条对照了当前代码。本 change 只收「今天确有其事」的条目与 owner 2026-10-06 的六项决定；
没有新功能，没有新依赖。多数任务是一处小改加一条断言，下面只写不显然的取法。

与 `fix-new-session-handoff`（#872）的关系：它改 `ownership.ts`、`types.ts`、`use-chat-session.ts` 的「新建会话」处理与 `turn-actions.ts` 的受理处置位，
并改 session-sidebar 规格。本 change 不碰 session-sidebar 规格；组 1、组 4 与它共享 `turn-actions.ts` / `use-chat-session.ts`，在它合入后开工。

## Goals / Non-Goals

**Goals**

- 首次发送被拒后，新会话显示它的正常状态，不再是一片空白。
- owner 决定的四项可访问性改进，各有可判红的断言。
- 代码块复制不带末尾换行。
- 清掉经核对仍存在的小问题与过期注释；补上便宜且具体的缺失断言。
- 验收清单的每一行都能照着做、看得出结果；旧的 demo 比对清单从仓库删除。

**Non-Goals**

- 正文比状态晚一帧（`defer`）、输入框增高依赖 `field-sizing`：owner 决定不处理，只记入 ADR。
- 包体上限与代码分割：owner 决定暂不设上限，S1f 全部 change 完成后再定。
- 拷入层文件的任何修改；会话列表八个文件的行为（只改一行注释）。
- #874 中归为「仅记录」的条目（不支持的浏览器、非整数 DPR、将来才可能出现的时序、与旧实现等价的行为等）。
- 交接未落定时切换会话或后退（#872 已定不纳入）。

## Decisions

### D1 首次发送被拒：在失败收尾处补读一次历史

现状（`use-chat-session.ts` 的历史 effect）：创建返回、URL 带上新会话 id 时，页面为了不打断交接而跳过这次历史读取；prompt 被受理后由受理对账安装快照。
prompt 未被受理时没有任何路径再读历史：`turn-actions.ts` 的失败收尾恢复草稿、写输入框错误、清掉交接登记，但历史 effect 的依赖没有变化，不会重跑，
历史状态停在「未读取」，线程区的滚动容器里什么都没有。

取法：失败收尾（未受理分支）在清掉登记之后，若这次交接是欢迎态首次发送（登记的 `originSessionId` 为空、会话 id 已有），且页面仍归同一 client、仍选中该会话，
就调用一次既有的 `loadHistory`。`loadHistory` 经依赖注入进 `useTurnActions`（以 ref 注入，见下）。

- 不新设状态机分支：读取中、读取失败、404 都走 `loadHistory` 既有的呈现（读取中输入框短暂锁定、无 `生成中`；失败显示历史错误；404 回欢迎态）。
- 条件不放宽到「任何被拒的 prompt」：既有会话的历史已在手，再读一次是多余请求，还会关掉并重开事件连接。
- 适用于一切未受理的结果（400/409/502/503 信封、网络失败），不只 owner 举例的 4xx/409/503：它们走同一个收尾分支，不补读的后果相同。401 照旧交给登录。
- `loadHistory` 的引用随 location 变化，直接注入会让 `dispatchPrompt` 的引用也跟着变；受理后历史读取失败的分支不清登记却释放了控制器，此时派发 prompt 的 effect 重跑会重发一次 prompt。
  所以两处一起做：`loadHistory` 经 ref 注入（`dispatchPrompt` 的引用保持稳定），并给派发 effect 的闸加「登记尚未受理」（`!pending.accepted`，#897 加的标记）。任务 1.2 断言全程恰一次 prompt；`!pending.accepted` 是第二道保险，没有独立的变异证据。
- 「页面仍归同一 client、仍选中该会话」是防御条件：用户在 prompt 被拒前切走或回欢迎态时，历史 effect 已清掉登记并中止请求，失败收尾在更早处返回，走不到补读。它没有独立的变异证据。
- 输入框上的错误文案归属于该会话，补读不清它（`loadHistory` 只清流错误）。

否决：在历史 effect 里加一个「交接已结束」的状态量触发重跑——多一个状态，且要再区分受理与拒绝；在收尾处直接调用更短。

### D2 卡消失后的焦点

规则（tool-approval delta）：提问卡因结算消失时，若消失前焦点在该卡内，焦点移到 `id` 大于它的最小一张待决卡的 `允许`，没有更大的取剩余第一张；没有待决卡时移到输入框。焦点在别处不动；卡出现时不夺取。

两处不显然：

- **「焦点在该卡内」怎么判**。按下 `允许` / `拒绝` 后本卡两个按钮立即禁用；浏览器会把焦点从被禁用的按钮上收走（落到 `body`），所以等到卡卸载时再看 `document.activeElement` 已经晚了。
  判定分两路：作答那一刻焦点在本卡内，且此后焦点没有落到别的元素（仍在卡内或在 `body`）；或者卡没有被本页作答（超时、别的标签页作答）而在卸载前一刻焦点在卡内。
  两路都由停靠区（`composer-dock.tsx`，它已经在渲染期比对卡的集合）记录与处置，卡组件只上报「作答时焦点在我这里」。
  jsdom 不做禁用失焦，测试里显式 `blur()` 模拟一例，另由 ui-walk 在真实浏览器里走一遍。
- **输入框此刻是锁定的**。最后一张卡消失时回合仍在进行，输入框处于禁用，`focus()` 无效。照搬「新建会话」的延后聚焦做法（`use-chat-session.ts` 里解锁那次提交才聚焦）：
  记下「待聚焦」，输入框解锁时若焦点仍未落到别的元素才聚焦，否则作废。停靠区为此多收两个入参：输入框的 ref 与锁定状态（`conversation-view.tsx` 都已持有）。

移过去的焦点不豁免 400 毫秒防误点：卡集合变化本来就武装了它，键盘连按两下 Enter 不会连答两张。

否决：卡出现时自动聚焦第一张（夺焦，违反「不夺取」）；最后一张消失时聚焦 `停止`（owner 指定输入框）。

### D3 被裁剪的列表可键盘聚焦

与提问卡 `title` 正文同一做法：内容高度超过可见高度时滚动容器带 `tabindex="0"`，否则不带。把 `approval-card.tsx` 里那段测量（layout effect 里量一次，`ResizeObserver` 可用时随尺寸重量）
抽成一个 hook 放进新文件，三处共用：提问卡正文、任务清单的列表（`todo-panel.tsx` 的 `ul`）、项目配置对话框的滚动容器（`project-config.tsx` 里包着各分组的那个 `div`，不是组内的 `ul`）。

- 新文件在 `web/src/features/chat/` 下，必须登记进 `MIGRATED_AREAS` 并同步守卫里的清单断言（终态守卫要求逐文件登记）。
- 重量的触发量：提问卡是 `title`；任务清单是清单内容、限高档位与展开状态（列表只在展开时渲染：收起态挂载后再展开必须重量并把观察器挂到新元素上）；项目配置是文件列表。
- 可聚焦的滚动容器不是控件：不加角色、不加按键处理；「面板只读」「对话框唯一控件是关闭」两条条文各补一句说明。
- 提问卡的「内容较长，请滚动查看全部」提示是同意安全的要求，只属于提问卡，另两处不加。

### D4 代码块复制去掉末尾一个换行：改在应用层

ADR-0013 的六类修改里没有一类允许改拷入组件的运行时行为。不需要：`markdown-body.tsx` 已经用 `components` 覆盖了 `CodeHeader`，拷入文件里的那个 `CodeHeader` 从不运行，
剪贴板写入发生在应用层的 `useCopyFeedback`。把传给它的文本去掉末尾恰一个 `\n` 即可，拷入文件零改动，不需要为此增补修改类别；ADR 只记录 owner 的行为决定。

末尾那个换行是 Markdown 转换追加的，恒为 `\n`；代码块自己以空行结尾时原文是两个换行，去掉一个后仍以一个换行结尾。消息级 `复制` 不受影响。

### D5 删除 demo 比对清单

`docs/acceptance/demo-parity-checklist.md` 自 ADR-0013 起只是历史记录，其中的行号与组件名大多已失效。owner 决定删除，#874 里所有针对它的备注随之关闭。
现行指向只有两处要改：功能验收清单的文件头一句、functional-acceptance 规格里的一句（delta）。其余出现处（ADR-0013 正文、ADR-0011、`IMPLEMENTATION_PLAN.md`、
`docs/reviews/2026-09-24-demo-parity-audit.md`、守卫测试里的一个样本字符串、`openspec/changes/archive/**`）是当时的叙述或自检样本，不改。没有测试、脚本或 CI 读取这个文件。

### D6 两处「整理」其实改了可观察行为

- `max-[760px]:` → `narrow:`：前者编译为「小于 760」，后者是外壳的「不超过 760」。视口恰为 760 宽时这七处的样式会变，变成与外壳一致。没有测试断言这些类名。
- 任务清单读侧降级：存量值解析不出或不合规时快照的 `todo` 为 `null`，此前是请求失败。只有带外改库可达。读侧不改写该列，不记日志（每次快照读取都会经过，日志会刷屏）。

- 测量 hook 的单元测试：可控的 `ResizeObserver` 替身触发重量。
- `useCopyFeedback` 的剪贴板写入值（`web/test/chat-markdown.test.tsx`）。
- 服务端 store 单元层：`readTodo` 对坏值返回 `null`；REST 层一条快照用例。
- ui-walk（真实浏览器）：真实点击 `回到最新`；键盘作答后焦点最终落在输入框；探针自身的修正。
- 静态：已迁移文件里带 `list-none` 的元素都带 `role="list"`；`chat.css` 的 `@media (hover` 块内选择器归属；`MIGRATED_AREAS` 含新文件。

## Risks / Trade-offs

- **焦点规则在不同浏览器里的差异**：禁用失焦的时机各家不同。缓解：判定不依赖卸载时刻的 `activeElement` 单一来源（D2 两路）；jsdom 与 ui-walk 各有一例。
- **补读历史与事件连接**：补读会开事件连接，新会话没有回合，连接空闲，与直接打开一个零消息会话相同。
- **描述文本可能很长**：`aria-describedby` 指向 `title` 全文，50 行的 `title` 会被读屏整段读出。owner 已决定关联正文；真实读屏下的体验没有验证（见 Not yet specified）。
- **760 宽的样式变化**：属修正，但没有浏览器级断言覆盖这一个像素；走查视口是 390 与 1440，不经过它。

## Not yet specified

- 要移去的下一张卡若正在作答在途（按钮禁用），`focus()` 无效，焦点留在 `body`：本 change 不处理。
- 作答失败（卡内出现错误、按钮恢复可用）后焦点不回到刚才按的按钮：禁用失焦把它留在 `body`，本 change 不处理。
- `aria-describedby` 是否也加在 `允许` / `拒绝` 按钮上：本 change 只加在卡（`role="group"`）上，按钮名不变；真实读屏下是否足以区分未验证。
- 被裁剪的滚动容器获得焦点后读屏读出什么（没有角色与名称）：与提问卡正文现状相同，未验证。
- 任务清单与项目配置列表的 `ResizeObserver` 重量路径没有真实浏览器证据（走查栈产生不了被裁剪的清单）。
- 验收清单里「让助手删除文件」的步骤依赖模型照做；模型不配合时只能到服务器上删。
