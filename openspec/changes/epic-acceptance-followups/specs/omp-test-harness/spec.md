# Spec Delta

## MODIFIED Requirements

### Requirement: 受控上游请求记录
The loopback fake-upstream (`server/test/support/fake-upstream.mjs`) SHALL keep, per server instance, an ordered in-memory record of every chat-completions request it has accepted (after its own bearer check, on either declared mount point): for each request, the top-level `model` of the request body (the string, or `null` when the member is absent or not a string), the number of elements of its `messages` array (`0` when absent), and `maxTokens`: the top-level `max_tokens` when it is a number, else the top-level `max_completion_tokens` when that is a number, else `null`. It SHALL expose that record through its test-only control surface as `GET /__control/requests`, authenticated with the same expected bearer as gate control (401 otherwise), answering 200 `{"requests":[{"model":…,"messages":…,"maxTokens":…}]}` in arrival order with `Cache-Control: no-store`; an instance started through `start()` SHALL also return the same list from the handle's `requests()` accessor. A request is recorded once its bearer check has passed and its body has parsed as a JSON object — before the fixture's own validation of `messages` — so a request the fixture then answers with an error is recorded too (with `messages` `0` when that member is absent or not an array); a body that is not a JSON object is not recorded. The record SHALL hold no message text, header or key, SHALL keep only the latest 1000 entries and is never reset during the instance's life. Adding it SHALL NOT change any existing response, marker, gate, ordering or error behaviour of the fixture, and the product SHALL NOT call it. Its purpose is to let official-binary comparison cases assert which `model` and which output limit real omp actually sends (model-selection「模型与强度从下一条消息起生效」, model-proxy「透传端点与 bearer 鉴权」「托管 models.yml」).

#### Scenario: 记录模型名与消息条数
- **WHEN** a fixture instance accepts three chat-completions requests whose bodies name `m1` with one message and `max_tokens: 32768`, `m3` with three messages and `max_completion_tokens: 8192`, and no `model` with two messages and `max_tokens: "32768"` (a string), then receives `GET /__control/requests` with the expected bearer, and again without a bearer
- **THEN** the first control response is 200 `{"requests":[{"model":"m1","messages":1,"maxTokens":32768},{"model":"m3","messages":3,"maxTokens":8192},{"model":null,"messages":2,"maxTokens":null}]}` with no-store and the handle's `requests()` deep-equals that array; the second is 401; the three completions responses are byte-identical to what the fixture produced before this requirement existed
