## MODIFIED Requirements

### Requirement: 假 omp 进程契约
The standalone zero-dependency Node fixture SHALL expose JSONL stdin/stdout frames matching omp v18.0.10 commit 33cc6b9a043a74e00a157e72ca909272796d8461 for its supported commands, with explicit argv-selected scenarios. It SHALL not replace production code or contact a real model service in its contract tests.
For S1c turn control the fixture SHALL additionally parse `--session-dir <dir>` and `--approval-mode <mode>` from argv and support thirteen scripted scenarios (`abort-ok`, `abort-ignored`, `branch`, `approval`, `approval-parallel`, `approval-then-abort`, `approval-chain-abort-ignored`, `slow-ready`, for S1c session metadata/presentation `thinking`, `edit-write`, `slash`, for the S1f task list `todo`, and for the S1g permission tiers `approval-write`). `abort-ok`: after prompt ack, `agent_start` and two text deltas the turn waits; on an inbound `abort` frame it emits `message_end` with `stopReason` `aborted`, terminal `agent_end` and `response{command:"abort"}` echoing the abort id, then accepts a further prompt as a normal turn; `--start-delay-ms <n>` (honored only by `abort-ok` and `slow-ready`; default 0; position-independent, last occurrence wins; under those two scenarios an invalid or missing value exits 1 with zero frames, like `--ready-delay-ms`; every other scenario ignores the flag and its value) makes the fixture queue the held turn's `agent_start` and two deltas n ms after the prompt ack while stdin keeps being read; an `abort` read after that ack but before the turn's `agent_start` models omp v18.0.10's generation bail (the prompt still pre-processing is silently dropped): the fixture answers `response{command:"abort",success:true}` echoing the abort id, cancels the pending turn and never emits its `agent_start`, deltas, `message_end` or `agent_end`, and a following prompt runs as a normal complete turn. With n=0 the held turn opens in the same serial step as the ack, so an `abort` is always read after `agent_start` and the two deltas. `abort-ignored`: same held turn, but inbound `abort` produces no frame at all and the process stays alive until stdin closes or a signal arrives (bounded-fallback probe). `branch`: `get_branch_messages` responds with a fixed deterministic list of at least two user entries `[{entryId,text}]` documented in the fixture; `branch{entryId}` for a known entry writes a real new nonempty `.jsonl` file under the `--session-dir` directory (distinct from the resumed/default path), switches the process to it so every subsequent `get_state.sessionFile` returns that new path, and responds `{text}` with that entry's text; an unknown `entryId` yields an error response and leaves `sessionFile` unchanged. `approval`: when argv contains `--approval-mode write`, a prompt turn emits `agent_start`, text deltas and `message_end stopReason toolUse`, then `extension_ui_request{id, method:"select", title:"Allow tool: bash\n…", options:["Approve","Deny"]}` (exactly the recognizer shape of omp-runtime) and, without waiting for its answer, `tool_execution_start` for bash (mirroring omp v18.0.10 as measured on the real binary: the approval select precedes `tool_execution_start`, which does not wait for the answer), and emits no further frame until a matching `extension_ui_response{id}` arrives; every `tool_execution_end` of an approval-gated turn of the four approval scenarios (not of the later normal turns) is immediately followed by that call's `message_end{message:{role:"toolResult", toolCallId, toolName, content, isError}}` whose `content` equals the end's `result.content` and whose `isError` is always a boolean (`true` for a denial, `false` otherwise, as omp v18.0.10 emits it); `{value:"Approve"}` continues with the normal `tool_execution_end` and completion, any other value or `cancelled` emits `tool_execution_end` with `isError: true` before completing; without `--approval-mode write` the same scenario behaves as `normal` and emits no select. `approval-then-abort`: like `approval`, but after the select's answer and that answer's `tool_execution_end` (with `isError: true` for any value other than `Approve` or for `cancelled`) the turn is held exactly like `abort-ok` — no completion frame — until an inbound `abort`, which is then honored with the aborted close of an approval turn (measured on the real binary after a `Deny`; after an `Approve` the fixture reuses the same close as a model, not a measurement) — `turn_end`, `turn_start`, assistant `message_end{content:[], stopReason:"aborted", errorMessage:"Interrupted by user"}`, `turn_end`, terminal `agent_end` and `response{command:"abort"}` echoing the abort id — after which a further prompt is accepted as a normal turn; an `abort` arriving while the select is still pending produces no frame until the select is answered and is honored right after that answer's `tool_execution_end` and its toolResult `message_end`, with the same aborted close. A host that writes `Deny` and then `abort` (the stop order) therefore gets a deterministic aborted end. `approval-parallel`: when argv contains `--approval-mode write`, a prompt turn emits `agent_start`, text deltas and one `message_end stopReason toolUse` carrying two bash tool calls, then two `extension_ui_request` selects of the same recognizer shape with distinct `id`s (one per tool call, in tool-call order) back to back, and then two `tool_execution_start` frames for bash with distinct `toolCallId`s (in tool-call order), all before either select is answered; each select is answered independently and in any order: a matching `extension_ui_response{id}` emits the `tool_execution_end` of that select's own tool call only (successful for `Approve`, `isError: true` for any other value or `cancelled`), the other call stays pending. Once both are answered: if at least one answer was `Approve` and no `abort` has arrived, the turn continues to its normal text, assistant `message_end` and terminal `agent_end`; if every answer was a denial (`Deny`, any other value or `cancelled`) and no `abort` has arrived, the turn is held exactly like `abort-ok` — no completion frame — until an inbound `abort`, which is then honored with the same aborted close (modelling the model's follow-up call during which a host's stop, which denies every pending select before writing `abort`, lands). An `abort` arriving while either select is still pending produces no frame of its own until both are answered: each answer still emits its own tool call's `tool_execution_end` immediately as above, and after the last one, instead of the normal completion and whatever the answers were, the abort is honored with the aborted close of an approval turn described for `approval-then-abort`. Without `--approval-mode write` it behaves as `normal`. Each of `approval`, `approval-parallel` and `approval-then-abort` gates only the first prompt turn of the process; once that turn has ended (completed or aborted), a further prompt is accepted as a normal turn. `approval-chain-abort-ignored`: when argv contains `--approval-mode write`, a prompt turn starts exactly like `approval` (`agent_start`, text deltas, `message_end stopReason toolUse`, a first select of the recognizer shape, then bash `tool_execution_start`); once that select is answered with any value or `cancelled` it emits that call's `tool_execution_end` (`isError: true` unless `Approve`) and its toolResult `message_end`, then a second select of the same recognizer shape with a distinct `id` and a second bash `tool_execution_start` with a distinct `toolCallId`, and emits nothing further until that select is answered; an answer to the second select emits its `tool_execution_end` and toolResult `message_end` likewise, after which the turn stays held without completing. Any inbound `abort`, at any point, produces no frame at all and the process stays alive until stdin closes or a signal arrives (like `abort-ignored`), so a host can observe a bounded retire while an approval is still pending; without `--approval-mode write` it behaves as `normal`. `slow-ready`: the `ready` frame is withheld until a delay has elapsed, then emitted with the normal fields, after which the process behaves exactly as `abort-ok` (a prompt is held after `agent_start` and two text deltas until an inbound `abort`, which it honors; the prompt after that aborted turn completes as a normal turn); the delay in milliseconds is taken from argv `--ready-delay-ms <n>` (non-negative integer; default 500 when absent) so a host test can make the owner acquire/handshake window observable and act (e.g. stop) while the prompt is still awaiting dispatch; inbound frames are not expected before `ready`, and stdin closing during the delay exits the process cleanly (unlike `no-ready`/`no-ready-hang`, `ready` does eventually arrive). The knob is independent of `--scenario` ordering (the server test `spawnImpl` in `server/test/session-supervisor-helpers.ts` appends `--scenario <name>` after the production argv, and `server/test/linux/uid-isolation.test.ts` `HANG_PATTERN` matches only `scenario hang-term$`, so neither is affected). `thinking`: after prompt ack the turn emits `agent_start`, then `message_update` frames whose `assistantMessageEvent` is, in order, `thinking_start{contentIndex:0, partial}`, exactly three `thinking_delta{contentIndex:0, delta, partial}` with `delta` values `先读需求，`, `再列要点，`, `最后作答。` (none a prefix of another; their concatenation `先读需求，再列要点，最后作答。` is the deterministic thinking text, documented as a named constant in the fixture), and `thinking_end{contentIndex:0, content:"先读需求，再列要点，最后作答。", partial}`; then at least three `text_delta` frames (contentIndex 1) carrying the fixture's normal reply deltas, an assistant `message_end` with `stopReason` `stop` whose `message.content` holds `{type:"thinking", thinking:"先读需求，再列要点，最后作答。"}` followed by the text block, and terminal `agent_end`; it emits no tool frames and no `extension_ui_request` under any `--approval-mode`. `thinking` additionally honours two optional argv knobs, both ignored by every other scenario and independent of `--scenario` ordering like `--ready-delay-ms`: `--thinking-repeat <n>` (positive integer; default 1 when absent) emits the three `thinking_delta` values, in the same order, `n` times in sequence (`3n` deltas between `thinking_start` and `thinking_end`), and `thinking_end.content` and the `message_end` thinking block then equal the concatenation of all `3n` deltas, i.e. the fixed text repeated `n` times (15 code points per repetition, so `n` ≥ 2185 exceeds 32768 code points); `--hold-after-thinking` makes the turn emit nothing after `thinking_end` (no text deltas, no completion) and hold exactly like `abort-ok` until an inbound `abort`, which is then honored with `message_end` `stopReason` `aborted`, terminal `agent_end` and `response{command:"abort"}` echoing the abort id, in that order; an `abort` read before `thinking_end` has been emitted is honored right after it, and a further prompt after the aborted turn runs the same `thinking` turn again. Without these knobs `thinking` is exactly as described above. `edit-write`: after prompt ack the turn emits `agent_start`, then the same `thinking_start`, three `thinking_delta` (`先读需求，`/`再列要点，`/`最后作答。`) and `thinking_end` frames as the `thinking` scenario (so a single bound turn carries thinking, an edit, a write and text — the chat-stream `Ordered publication after persistence` scenario is constructible), then one assistant `message_end` with `stopReason` `toolUse` carrying two tool calls (no text before the tools), then for the first call `tool_execution_start{toolCallId, toolName:"edit", args:{input:<fixed hashline input documented in the fixture>}}` (hashline-mode args carry no `path` key, exactly like omp's default edit mode, so the path is observable only in `details`) and `tool_execution_end{toolCallId, toolName:"edit", result:{content:[{type:"text",text:…}], details:{path:"<cwd>/notes.md", diff:"+1|a\n+2|b\n-3|c\n 4|d"}}}` — the `details.diff` uses omp's `+N|`/`-N|`/` N|` line format (not unified diff) and therefore counts 2 added and 1 removed lines; then for the second call `tool_execution_start{toolCallId, toolName:"write", args:{path:"out/report.html", content:<fixed html documented in the fixture>}}` and `tool_execution_end{toolCallId, toolName:"write", result:{content:[…], details:{resolvedPath:"<cwd>/out/report.html"}}}` with no `diff` key (omp's write tool reports no diff); then assistant `message_end` with `stopReason` `stop` and terminal `agent_end`. `<cwd>` is the fixture's own `process.cwd()` at the time of the turn, so a host test places the reported paths inside or outside a bound workspace root by choosing the child's working directory (the production spawn sets it to `--cwd`; a test `spawnImpl` may choose another). Before emitting each `tool_execution_end` the fixture actually writes the file it reports — `<cwd>/notes.md` with the documented post-edit content and `<cwd>/out/report.html` (creating `out/`) with the documented html — so realpath-based host checks see real files; if a write fails that call's `tool_execution_end` carries `isError: true` and no `details`, and the turn still completes. With `--approval-mode write` neither `edit` nor `write` is an exec-tier tool, so `edit-write` emits no `extension_ui_request` under any `--approval-mode`. `todo` (mirrors the `tool_execution_end` result of omp v18.0.10's `todo` tool, whose `result.details` is `{op, phases:[{name, tasks:[{content, status, blocker?}]}], storage, completedTasks?}` with the complete list in `phases`): every prompt turn emits, after the prompt ack, `agent_start`, one assistant `message_end` with `stopReason` `toolUse` carrying one `todo` tool call (no text before the tool), `tool_execution_start{toolCallId, toolName:"todo", args}`, `tool_execution_end{toolCallId, toolName:"todo", result:{content:[{type:"text",text:…}], details}}` without `isError`, then at least two text deltas (the fixed answer text), assistant `message_end` with `stopReason` `stop` and terminal `agent_end`; each turn uses a fresh `toolCallId`. `args` and `details` depend only on the ordinal of the prompt turn within the process and are documented as named constants in the fixture: the first turn has `args` `{op:"init",list:[{phase:"准备",items:["读取需求","列出要点"]},{phase:"交付",items:["输出结论"]}]}` and `details` `{op:"init",phases:[{name:"准备",tasks:[{content:"读取需求",status:"in_progress"},{content:"列出要点",status:"pending"}]},{name:"交付",tasks:[{content:"输出结论",status:"pending"}]}],storage:"session"}` (omp promotes the first pending task to `in_progress` when none is in progress); the second turn has `args` `{op:"view"}` and `details` `{op:"view",phases:<the same phases value as the first turn>,storage:"session"}`; the third and every later turn has `args` `{op:"done",task:"读取需求"}` and `details` `{op:"done",phases:[{name:"准备",tasks:[{content:"读取需求",status:"completed"},{content:"列出要点",status:"in_progress"}]},{name:"交付",tasks:[{content:"输出结论",status:"pending"}]}],storage:"session",completedTasks:[{phase:"准备",content:"读取需求"}]}`. `todo` is not an exec-tier tool, so the scenario emits no `extension_ui_request` under any `--approval-mode`; it writes no file and honours no knob. `slash` (mirrors omp v18.0.10's RPC handling of whitelisted builtins, `modes/rpc/rpc-mode.ts:1020-1056`): a prompt whose `message` is exactly `/todo` emits `command_output{text:"No todos. Use /todo append <task> to start one."}` and then the prompt response `{agentInvoked:false}` (no `agent_start`, no `agent_end`); a prompt whose `message` is exactly `/compact` emits the prompt response `{agentInvoked:false}` first and, after a 50 ms timer, `command_output{text:"Compaction complete."}` unless argv contains `--compact-silent`, in which case the output is suppressed and nothing else follows the response; an inbound `abort` is always answered `response{command:"abort"}` (echoing its id) and, when it arrives during that timer, cancels the pending output — `--compact-silent` suppresses only the output, never the abort answer; any other prompt (including one whose first character is U+0020 followed by `/`, the host's escaped plain text) runs the `normal` turn. `branch` SHALL additionally accept argv `--branch-entry <text>` (repeatable): each value appends one more user entry `{entryId,text}` with exactly that text after the fixed list, in argv order, so host tests can place an escaped (` /help …`) or plain (`继续`) entry as the last one; `branch{entryId}` for such an entry behaves like any known entry. Existing scenarios and defaults SHALL remain unchanged. Whenever the fixture creates a session `.jsonl` file under `--session-dir`, it SHALL also create the sibling directory named after that file without the `.jsonl` suffix, containing one regular file and one nested directory holding one regular file, modelled on the artifact directory real omp keeps next to a session file.
For S1g the fixture SHALL additionally: (1) support the scenario `approval-write`: when argv contains `--approval-mode always-ask`, a prompt turn emits `agent_start`, text deltas and `message_end stopReason toolUse` carrying one `write` tool call, then `extension_ui_request{id, method:"select", title:"Allow tool: write\nPath: workbuddy-report.html", options:["Approve","Deny"]}` and, without waiting for its answer, `tool_execution_start` for write, and emits no further frame until a matching `extension_ui_response{id}` arrives; `{value:"Approve"}` continues with the normal `tool_execution_end`, its toolResult `message_end` and completion, any other value or `cancelled` emits `tool_execution_end` with `isError: true` before completing; with any other `--approval-mode` value (or none) the scenario behaves as `normal` and emits no select. The four existing approval scenarios stay keyed to `--approval-mode write` exactly as stated above — under `always-ask` and `yolo` they behave as `normal`; this is a fixture simplification, not a statement about omp (real omp also asks for bash under `always-ask`, which the official-binary cases of session-permission-tier pin). (2) In every scenario, answer `set_model{provider, modelId}` with `response{command:"set_model", success:true, data:{provider, id:modelId}}` echoing the request id, except that the documented failing model id `workbuddy-missing-model` yields `response{command:"set_model", success:false, error:"Model not found: <provider>/workbuddy-missing-model"}` and changes nothing; and answer `set_thinking_level{level}` with `response{command:"set_thinking_level", success:true}` (no data), except that the documented failing level `workbuddy-bad-level` yields a `success:false` response. (3) After a successful `set_model`, every later `get_state` data additionally carries `model:{provider, id}` of the last one; after a successful `set_thinking_level`, `thinkingLevel` of the last one; before the first such command `get_state` data is unchanged from today (neither key present). Both commands are answered between turns only; one arriving while a turn is in flight is recorded and answered after that turn's terminal `agent_end` (the host never sends one mid-turn). Both frame types appear in the inbound frame record of Requirement `假 omp 入站帧记录` like any other frame. No existing scenario's emitted frames change.

#### Scenario: 默认握手与完整回合
- WHEN a spawned fixture receives negotiate_protocol version 2, get_state and prompt with request ids
- THEN ready advertises supported transport; successful responses echo ids, negotiation data has protocolVersion 2, get_state data has nonempty sessionFile; prompt ack precedes a turn containing at least three message_update.assistantMessageEvent text_delta frames, matching tool_execution_start/end, assistant message_end and terminal agent_end

#### Scenario: 握手故障与进程退出
- WHEN no-ready or missing-session is selected
- THEN respectively no ready frame is emitted or get_state omits sessionFile, while the difference is observable through a real subprocess
- WHEN idle normal stdin closes
- THEN the process exits cleanly without leaking resources

#### Scenario: 字节级分块与交错
- WHEN chunked get_state follows successful v2 negotiation
- THEN rpc_chunk frames are individually within 1MiB and concatenate decoded bytes into the exact greater-than-3MiB Unicode JSON object; chunkId/index/count/byteLength are consistent
- WHEN interleaved is selected
- THEN an unrelated frame deliberately interrupts that sequence so downstream decoders can reject it

#### Scenario: 回合失败与交互取消
- WHEN crash or error is selected and a prompt is accepted
- THEN crash exits nonzero without terminal completion, while error emits assistant stopReason error with errorMessage before terminal agent_end
- WHEN extension-ui is selected
- THEN a confirm request is emitted, and terminal completion waits for a matching cancelled extension_ui_response

#### Scenario: 真实代理承载
- WHEN call-proxy reads the managed providers.workbuddy configuration and receives a prompt
- THEN it POSTs the prompt messages with stream true to baseUrl/chat/completions using the environment WORKBUDDY_MODEL_TOKEN bearer; if the streamed response carries tool calls it reassembles them, reports each as matching tool_execution_start/end frames carrying the upstream tool call id and name, and POSTs one second request whose messages are the original user message, the assistant tool-call message and a role tool result for that call id; streamed content of the answering round maps to text_delta without byte-boundary corruption, and the turn ends successfully after DONE
- WHEN a 200 response ends without content or tool calls, or the second round again yields only tool calls
- THEN the assistant message ends with stopReason error rather than a successful empty turn
- WHEN configuration is invalid or the local HTTP request fails
- THEN the failure is observable without a fabricated successful reply or a token leak into stdout/stderr

#### Scenario: abort 收尾与忽略
- **WHEN** `abort-ok` accepts a prompt and then receives `abort` with request id X
- **THEN** after the two deltas no completion is emitted until the abort; then `message_end` with `stopReason` `aborted`, `agent_end` and `response{id:X, command:"abort"}` follow in that order, and a subsequent prompt completes as a normal turn
- **WHEN** `abort-ignored` receives `abort` in the same position
- **THEN** no frame is emitted afterwards, the process does not exit on its own, and it still exits when stdin closes or SIGTERM arrives

#### Scenario: branch 产生真实新会话文件
- **WHEN** `branch` is spawned with `--session-dir <dir>` and `--resume <old>`, receives `get_branch_messages`, then `branch{entryId}` for the last listed entry, then `get_state`
- **THEN** the list is the fixed documented user entries; a new nonempty `.jsonl` file exists under `<dir>` that is not `<old>`; the branch response `text` equals that entry's text; `get_state.sessionFile` equals the new path
- **WHEN** `branch` is sent an unknown `entryId`
- **THEN** an error response is returned, no file is created and `get_state.sessionFile` is unchanged

#### Scenario: 审批 select 门控 bash
- **WHEN** `approval` is spawned with `--approval-mode write` and accepts a prompt
- **THEN** after `message_end` with `stopReason` `toolUse` comes a `select` request with options exactly `["Approve","Deny"]` and title starting `Allow tool: bash`, then `tool_execution_start` for bash before any answer, and no further frame arrives until the select is answered
- **WHEN** the response value is `Approve`
- **THEN** a successful `tool_execution_end`, its toolResult `message_end` and normal completion follow
- **WHEN** the response value is `Deny` or the response is `cancelled`
- **THEN** `tool_execution_end` carries `isError: true`, its toolResult `message_end` carries `isError: true`, and the turn still completes with `agent_end`
- **WHEN** `approval` is spawned with `--approval-mode yolo`
- **THEN** the turn matches the `normal` scenario and no `extension_ui_request` is emitted

#### Scenario: 并行审批各自应答
- **WHEN** `approval-parallel` is spawned with `--approval-mode write` and accepts a prompt
- **THEN** after the `toolUse` `message_end` come two `select` requests with distinct ids and then two bash `tool_execution_start` frames with distinct `toolCallId`s, all emitted before any answer, and no further frame arrives until an answer
- **WHEN** the second select is answered `Deny` first and then the first select is answered `Approve`
- **THEN** after the `Deny` exactly the second tool call's `tool_execution_end` with `isError: true` and its toolResult `message_end` arrive, and nothing else until the other answer; after the `Approve` the first tool call's `tool_execution_end` without `isError` and its toolResult `message_end` arrive, followed by normal completion and terminal `agent_end` — only the denied step is `isError`
- **WHEN** both selects are pending and an `abort` with request id X arrives, then the first select and then the second are answered `Deny`
- **THEN** no frame follows the `abort` until the first answer; each `Deny` is followed by exactly its own tool call's `tool_execution_end` with `isError: true` and its toolResult `message_end`; after the second one `turn_end`, `turn_start`, an assistant `message_end` with empty content, `stopReason` `aborted` and `errorMessage` `Interrupted by user`, `turn_end`, terminal `agent_end` and `response{id:X, command:"abort"}` follow in that order, with no normal completion
- **WHEN** both selects are answered `Deny` with no `abort` yet, and an `abort` with request id X arrives afterwards
- **THEN** after the two `tool_execution_end` frames with `isError: true` and their toolResult `message_end` frames nothing is emitted until the `abort`; then `turn_end`, `turn_start`, the empty assistant `message_end` with `stopReason` `aborted` and `errorMessage` `Interrupted by user`, `turn_end`, terminal `agent_end` and `response{id:X, command:"abort"}` follow in that order
- **WHEN** `approval-parallel` is spawned with `--approval-mode yolo`
- **THEN** the turn matches the `normal` scenario and no `extension_ui_request` is emitted

#### Scenario: 延迟握手
- **WHEN** `slow-ready` is spawned with `--ready-delay-ms 300`
- **THEN** no frame is emitted during the first 300 ms, then `ready` with the normal fields is emitted, `negotiate_protocol` and `get_state` behave exactly as in `normal`, and a prompt behaves exactly as in `abort-ok`: after its ack, `agent_start` and two text deltas no completion is emitted until an `abort` arrives, then `message_end` with `stopReason` `aborted`, `agent_end` and `response{command:"abort"}` follow in that order, and the next prompt completes as a normal turn
- **WHEN** `slow-ready` is spawned without `--ready-delay-ms`, or its stdin closes before the delay elapses
- **THEN** respectively `ready` arrives after the 500 ms default, or the process exits cleanly (exit code 0) without hanging

#### Scenario: select 挂起时 abort 被延后
- **WHEN** `approval-then-abort` has a pending select and receives `abort`
- **THEN** nothing is emitted until `extension_ui_response` for the select arrives; then `tool_execution_end` (isError for Deny), its toolResult `message_end`, `turn_end`, `turn_start`, the empty assistant `message_end` with `stopReason` `aborted`, `turn_end`, `agent_end` and `response{command:"abort"}` follow in that order, so a host that answers Deny before abort can be proven by frame order
- **WHEN** `approval-then-abort` has its select answered `Deny` and only afterwards receives `abort`
- **THEN** `tool_execution_end` with `isError: true` and its toolResult `message_end` follow the answer, nothing further is emitted until the `abort`, and then `turn_end`, `turn_start`, the empty assistant `message_end` with `stopReason` `aborted`, `turn_end`, `agent_end` and `response{command:"abort"}` follow in that order

#### Scenario: 审批链上 abort 被忽略
- **WHEN** `approval-chain-abort-ignored` is spawned with `--approval-mode write`, accepts a prompt, its first select is answered `Deny` and an `abort` arrives
- **THEN** the first tool call's `tool_execution_end` carries `isError: true` and is followed by its toolResult `message_end`, then a second `select` with a distinct id and the recognizer shape and a second bash `tool_execution_start` with a distinct `toolCallId` follow in that order, whether the `abort` arrived before or after them; no frame is ever emitted in response to the `abort`, no completion is emitted, the process does not exit on its own, and it still exits when stdin closes or SIGTERM arrives
- **WHEN** `approval-chain-abort-ignored` is spawned with `--approval-mode yolo`
- **THEN** the turn matches the `normal` scenario and no `extension_ui_request` is emitted

## ADDED Requirements

### Requirement: 受控上游请求记录
The loopback fake-upstream (`server/test/support/fake-upstream.mjs`) SHALL keep, per server instance, an ordered in-memory record of every chat-completions request it has accepted (after its own bearer check, on either declared mount point): for each request, the top-level `model` of the request body (the string, or `null` when the member is absent or not a string) and the number of elements of its `messages` array (`0` when absent). It SHALL expose that record through its test-only control surface as `GET /__control/requests`, authenticated with the same expected bearer as gate control (401 otherwise), answering 200 `{"requests":[{"model":…,"messages":…}]}` in arrival order with `Cache-Control: no-store`; an instance started through `start()` SHALL also return the same list from the handle's `requests()` accessor. A request is recorded once its bearer check has passed and its body has parsed as a JSON object — before the fixture's own validation of `messages` — so a request the fixture then answers with an error is recorded too (with `messages` `0` when that member is absent or not an array); a body that is not a JSON object is not recorded. The record SHALL hold no message text, header or key, SHALL keep only the latest 1000 entries and is never reset during the instance's life. Adding it SHALL NOT change any existing response, marker, gate, ordering or error behaviour of the fixture, and the product SHALL NOT call it. Its purpose is to let official-binary comparison cases assert which `model` real omp actually sends (model-selection「模型与强度从下一条消息起生效」, model-proxy「透传端点与 bearer 鉴权」).

#### Scenario: 记录模型名与消息条数
- **WHEN** a fixture instance accepts three chat-completions requests whose bodies name `m1` with one message, `m3` with three messages and no `model` with two messages, then receives `GET /__control/requests` with the expected bearer, and again without a bearer
- **THEN** the first control response is 200 `{"requests":[{"model":"m1","messages":1},{"model":"m3","messages":3},{"model":null,"messages":2}]}` with no-store and the handle's `requests()` deep-equals that array; the second is 401; the three completions responses are byte-identical to what the fixture produced before this requirement existed
