## ADDED Requirements

### Requirement: 输入框能力的冒烟与走查
`make smoke` 与 `make ui-walk`（及其 CI job）SHALL 在既有文件与既有栈上覆盖本 change 的三项能力，不新增 Hurl 文件、不新增 Make 目标、不改变两个 job 的 action 身份、端口与超时；栈仍是官方 omp v18.0.10 加受控上游，配置取缺省值（未设置 `APPROVAL_MAX_MODE`、`MODEL_CATALOG`、`UPLOAD_MAX_BYTES`、`UPLOAD_MAX_FILES`）。

**HTTP 冒烟**（真实 HTTP 断言，写在既有文件里）：

- `smoke/session-meta.hurl`：`GET /api/composer/options` 为 200 且 `approvalModes` 恰三项、`models` 恰一项、`upload.maxBytes` 为 524288000；新建会话的视图带 `approvalMode:"write"`；`PATCH {approvalMode:"yolo"}` 返回的视图为 `yolo`，随后 `GET /api/audit` 的最新一条为 `session.permission` 且 `detail.from="write"`、`detail.to="yolo"`；此后无 body 新建的会话视图为 `yolo`（沿用最近选择；这个会话用的是临时空间，文件在结束前把它 `DELETE` → 204，不留会话与临时空间）；`PATCH {approvalMode:"auto"}` 为 400；用例结束前把该账号的最近选择改回 `write`（对一个会话 `PATCH {approvalMode:"write"}`），使其后的用例与走查从缺省档开始。
- `smoke/files.hurl`：向自有空间 `POST /api/workspaces/:id/uploads?name=smoke-upload.txt`（`application/octet-stream`，固定的几个字节）为 201，`path` 以 `uploads/smoke-upload` 开头、`size` 为所发字节数；再传一次同名为 201 且 `name` 与第一次不同（同名自动编号；在一个干净的空间上两次的 `name` 恰为 `smoke-upload.txt` 与 `smoke-upload (1).txt`，`make smoke` 连跑两遍时后一遍得到更大的编号）；`tree?path=uploads` 列出两者；`name=../escape.txt` 为 403 `sandbox_denied`；以 `application/json` 上传为 400；第二个账号向该空间上传为 404。
- `smoke/chat.hurl`：在一个 `approvalMode` 为 `yolo` 的会话上（该文件自己创建，绑定正式工作空间或用临时空间均可，结束前与该文件的其它会话一样被删除）发一条不带标记的 prompt（受控上游发出 bash 工具调用），不作答任何审批而轮询到 `done`，快照里该助手消息 `approvals` 为 `[]`；在同一空间上传一个文件后带 `attachments` 发一条 prompt，快照里该用户消息的 `attachments` 恰为该路径与其大小。

**UI 走查**（真实浏览器，步骤写在一个新的 helper 文件里——`web/e2e/ui-walk-sessions.spec.ts` 与 `web/e2e/ui-walk-layout.ts` 已贴近 800 行上限，不往里加行；由既有 spec 文件调用），在 `desktop-light` 与 `mobile-dark` 两种视口下：

1. 欢迎态与一个已选会话的能力行满足 chat-web「输入框与能力栏」的 `真实浏览器下能力行不挤出发送键`。
2. 在一个绑定工作空间的会话里打开权限菜单、选 `全部自动`：出现标题为 `切换到全部自动？` 的确认框；点 `取消` 后按钮仍为 `权限：只问命令`；再选一次并点 `确认切换` 后按钮为 `权限：全部自动` 且计算样式的文字颜色等于警示色 token 的取值；随后选回 `只问命令`（不出现确认框）。
3. 模型按钮的可访问名为 `模型：deepseek-v4.1-flash`，菜单恰一项；推理强度按钮为 `推理强度：高`，菜单恰八项。
4. 经「+」菜单的 `上传文件` 选入一个由走查生成的小文件：出现一个附件标签，上传完成后没有状态字样；输入文字并发送，回合结束后该用户气泡里有名为 `附件` 的列表且含该文件名；刷新页面后仍在。
5. 走查的 error oracle（零新增控制台报错、无未处理的失败请求）对以上步骤同样生效。

本条新增的步骤创建的每一个会话 SHALL 由创建它的文件或 helper 删除（Hurl 里在所在登录态退出之前 `DELETE` → 204；走查 helper 在包住步骤的 `finally` 里删除，204 或 404 均接受），与「冒烟与走查不留会话与临时空间」的保证一致：连跑两遍之后不留会话行与 `tmp-` 目录。正式工作空间 `uploads/` 里由冒烟上传的文件留着，所以 `files.hurl` 的上传断言不写死编号（见上），对重复运行稳定。

冒烟与走查 SHALL NOT 引用密钥或真实模型上游；`always-ask` 与 `yolo` 在真实 omp 上的审批行为的完整证据是 session-permission-tier 的官方二进制对照用例（uid-isolation job），冒烟只取 `yolo` 下 bash 回合无需作答这一条作为真栈上的旁证。

#### Scenario: 走查覆盖能力行、档位确认与附件
- **WHEN** CI 的 ui-walk job 在两种视口下运行 `make ui-walk`
- **THEN** 上述五个步骤全部通过；新步骤所在的 helper 文件与调用它的 spec 文件都 ≤800 行；走查结束时该账号的最近选择为 `只问命令`（不把 `全部自动` 留给之后的步骤或用例）

#### Scenario: 走查对旧实现判红

## MODIFIED Requirements

### Requirement: 会话元数据 HTTP 冒烟
`smoke/session-meta.hurl` SHALL independently start with empty cookies (it does not depend on public/auth/chat/files) and SHALL be rerunnable because `make smoke` runs twice: it logs in as `zhangsan` (exact 200 Principal), creates or adopts a workspace named `smoke-sessions` (`POST /api/workspaces {"name":"smoke-sessions"}` → 201 or 409 only) and captures its id from `GET /api/workspaces` by that unique name, following `files.hurl`. It SHALL then, in order:
1. `POST /api/sessions {"workspaceId":<workspace id>,"scene":"code"}` → exact 201 whose body has exactly the fourteen keys `id,title,status,createdAt,updatedAt,scene,workspaceId,pinnedAt,archivedAt,pendingApproval,temporaryWorkspace,approvalMode,modelId,reasoningEffort` (`jsonpath "$.*" count == 14`) with `title` null, `status` `idle`, `scene` `code`, `workspaceId` the captured id, `pinnedAt` and `archivedAt` null, `pendingApproval` and `temporaryWorkspace` false, and `approvalMode` `write`, `modelId` `deepseek-v4.1-flash`, `reasoningEffort` `high` (the default single-model configuration; the composer steps this file gains from Requirement「输入框能力的冒烟与走查」 put the account's last choice back to `write` before the file ends, so the second run starts from the same values); capture `session_id`. Then `GET /api/audit?limit=1` → latest event `kind` `session.bind` with `actorId` `u1`, `workspaceId` the captured id and `detail.sessionId` equal to `session_id`.
2. `POST /api/sessions {"workspaceId":"00000000000000000000000000000000","scene":"code"}` (a well-formed but unknown workspace id) → exact 404 with `error.code` `not_found`; `POST /api/sessions {"scene":"code","color":"red"}` (extra key) → exact 400 with `error.code` `bad_request`; then `GET /api/audit?limit=1` → latest `kind` still `session.bind` whose `detail.sessionId` is `session_id` (neither rejected create wrote an audit row). `POST /api/sessions` without a body → exact 201 with `scene` null, `temporaryWorkspace` true and a `workspaceId` matching `^[0-9a-f]{32}$` (the bodyless create now makes a temporary workspace); capture `other_id` and that workspace id as `temp_ws`. `GET /api/workspaces` → 200 with no entry whose `id` is `temp_ws`, while `GET /api/workspaces/{{temp_ws}}/tree` → 200 with an empty `entries`; `POST /api/sessions {"workspaceId":"{{temp_ws}}"}` → exact 404 `not_found`.
3. `PATCH /api/sessions/{{session_id}} {"title":"冒烟会话","scene":"design","pinned":true}` → exact 200 fourteen-key DTO with that `title`, `scene` `design`, a nonnull `pinnedAt` and unchanged `workspaceId`; `PATCH` with an extra key (`{"color":"red"}`) → exact 400 with `error.code` `bad_request`; `GET /api/sessions` → 200 whose entry for `session_id` reflects title, scene, nonnull `pinnedAt` and the workspace id; `PATCH {"pinned":false}` → 200 with `pinnedAt` null and title/scene unchanged.
4. Prompt once: `POST /api/sessions/{{session_id}}/prompt {"message":"WORKBUDDY_THINK 会话元数据冒烟"}` → exact 202 capturing `assistantMessageId` (not retried). Because omp runs in `--approval-mode write` and the controlled upstream's first round is bash, the file SHALL answer the approval exactly as `chat.hurl` does under `make smoke`: poll messages GET with bounded retries until the captured assistant's `approvals` holds exactly one pending entry, `POST …/approvals/:approvalId {"decision":"allow"}` → 200 with `decision` `allow`, then poll messages GET with bounded retries until the captured assistant and the session are `done`. The file SHALL NOT use `skip_turn_control` (it never runs under `smoke-live`).
5. On the done snapshot assert: the captured assistant's `content` matches `content_pattern` (the exact fixed reply under `make smoke`), its `thinking` equals exactly `先读需求，再列要点，最后作答。` (the controlled upstream's `WORKBUDDY_THINK` reasoning relayed through real omp as `thinking_delta` and persisted into `chat_messages.thinking`), its bash step is `done`, and `session.title` is still `冒烟会话` (the first prompt SHALL NOT overwrite a title set by PATCH).
6. Slash whitelist through real omp: `GET /api/commands` → exact 200 whose `commands` has exactly two entries with `source` `builtin` and `name` `compact`, `todo` in that order (the smoke state dir installs no skill). `POST /api/sessions/{{session_id}}/prompt {"message":"/todo"}` → exact 202 capturing `todo_assistant_id`; poll messages GET with bounded retries until that assistant is `done` (no approval: the builtin runs without the model); assert its `content` equals exactly `No todos. Use /todo append <task> to start one.` (omp's own text relayed as `command_output`), its `steps` is empty and the user message content is `/todo`. Then `POST …/prompt {"message":"/session WORKBUDDY_THINK 冒烟"}` → exact 202 capturing `session_cmd_assistant_id` (`session` is a real omp builtin with an RPC `handle` outside the whitelist: unescaped it would answer with its usage text and never reach the model); poll until `done` (the escaped text reaches the model, whose controlled upstream answers the `WORKBUDDY_THINK` marker with its fixed reasoning; the session already holds a tool result from step 4, so there is no tool round and no approval is pending); assert the user message content equals `/session WORKBUDDY_THINK 冒烟` (persisted as typed, no leading space), the assistant `content` matches `content_pattern` (the fixed reply, proving the text was answered by the model rather than executed as a command), its `thinking` equals exactly `先读需求，再列要点，最后作答。` (the marker inside the escaped text reached the model) and its `steps` is empty.
7. `DELETE /api/sessions/{{session_id}}` → exact 204 with empty body (the session is `done`, so this exercises the non-running deletion path; the running path is proven by server integration tests); `GET /api/audit?limit=1` → latest `kind` `session.delete` with `actorId` `u1` and `detail.sessionId` equal to `session_id`; `GET /api/sessions/{{session_id}}/messages` → 404; `GET /api/sessions` → 200 without an entry for `session_id`; a second `DELETE /api/sessions/{{session_id}}` → exact 404.
8. Ownership: logout (204), login as `lisi`, `POST /api/sessions {"workspaceId":<zhangsan's workspace id>}` → exact 404 `not_found` (a foreign workspace is indistinguishable from an unknown one and creates no session), `PATCH /api/sessions/{{other_id}} {"title":"x"}` → 404 and `DELETE /api/sessions/{{other_id}}` → 404, with the number of entries in `lisi`'s own `GET /api/sessions` read before the three attempts and again after them and found unchanged, logout; login as `zhangsan`, `GET /api/sessions/{{other_id}}/messages` → 200 (the foreign attempts changed nothing), `PATCH /api/sessions/{{other_id}} {"archived":true}` → 200 with a nonnull `archivedAt`, `POST /api/sessions/{{other_id}}/prompt {"message":"hi"}` → exact 409 with `error.code` `session_archived`, `PATCH {"archived":false}` → 200 with `archivedAt` null, `DELETE /api/sessions/{{other_id}}` → 204, after which `GET /api/workspaces/{{temp_ws}}/tree` → 404 (the temporary workspace went with its last session), logout (204).
The file SHALL leave no live authentication session, running turn or session row it created; the adopted workspace remains for the next run. It asserts only the public REST/audit contract and consumes the caller-owned service like the other smoke files.
