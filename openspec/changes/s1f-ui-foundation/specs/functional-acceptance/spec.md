## ADDED Requirements

### Requirement: 功能验收清单与签收
`docs/acceptance/functional-checklist.md` SHALL 是界面验收的签收对象，按页面分节（登录、外壳、会话、文件、设置……），每行一条可在 1 分钟内判定的功能项，列为 `ID`、`操作`、`期望`、`结论`。`ID` 在文件内唯一（页面前缀 + 序号，如 `SH-01`）。`操作` 与 `期望` 描述用户可见的行为，不引用 demo 行号、像素值（`<数字>px`）或带 `.`/`#` 前缀的 CSS 选择器。`结论` 取 `待签`、`通过`、`不通过：<说明>` 之一。文件头 SHALL 写明运行方式（对着一个由调用方启动的真实服务逐项操作，不依赖截图对比）与签收规则。格式由一条守卫测试机械检查。

签收规则（人工执行，review-only，`AGENTS.md` 以一行注记指向本文件）：交付或改变用户可见功能的 issue 在同一 PR 里新增或更新对应行并把结论写为 `待签`；只有仓库所有者本人可以把结论改为 `通过` 或 `不通过`，agent 不得代签；一个 change 的 Epic 在其新增行仍有 `待签` 时不关闭，`不通过` 的行须关联一个修复 issue。`docs/acceptance/demo-parity-checklist.md` 保留为历史记录，不再更新。

#### Scenario: 行格式可判定
- **WHEN** 守卫测试读取 `docs/acceptance/functional-checklist.md`
- **THEN** 每个数据行恰有四列且 `ID` 不重复；`结论` 只取三种取值之一；全文不含 `demo:` 行号引用，`操作` 与 `期望` 列不含 `<数字>px` 与 `.`/`#` 前缀的选择器；对注入样本（重复 ID、第四种结论、含 `demo:123`）守卫各判失败

#### Scenario: 交付时不代签
- **WHEN** 评审一个新增或修改清单行的实现 PR
- **THEN** 这些行的 `结论` 为 `待签`；把任何行改为 `通过` 或 `不通过` 的提交只来自仓库所有者（review-only，无机械门禁）
