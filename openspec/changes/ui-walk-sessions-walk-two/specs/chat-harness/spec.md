## MODIFIED Requirements

### Requirement: UI 走查会话元数据
`web/playwright.config.ts` `testMatch` SHALL be exactly `"ui-walk*.spec.ts"`, which selects `web/e2e/ui-walk.spec.ts` and `web/e2e/ui-walk-sessions.spec.ts` and no helper module (no helper module under `web/e2e/` ends in `.spec.ts`), and `globalTimeout` SHALL be `300_000`, bounding both spec files across both projects; every other config value (serial single worker, retries 0, the 30 s per-test timeout, per-action/navigation timeouts, output handling, the `desktop-light` 1440×900 light and `mobile-dark` 390×844 dark projects) is unchanged, `make ui-walk` still runs `npm run ui-walk --workspace web`, and the CI ui-walk job keeps its identity and `timeout-minutes`. The journey of `ui-walk.spec.ts` (Requirement `UI 走查对话步骤`) is not changed.
`web/e2e/ui-walk-sessions.spec.ts` SHALL run one serial journey per project against the real server stack of `make ui-walk` (compiled app, real pinned omp 18.0.10, controlled upstream), under its own instance of the existing browser error oracle (its own two expected `/api/auth/me` 401 — before login and after the logout reload that ends the journey — and no unexpected console/page errors), with no browser route fulfillment, fake EventSource or arbitrary sleeps. It does **not** select fake-omp scenarios (the ui-walk stack runs real omp); it drives the controlled upstream through the prompt-text markers of omp-test-harness Requirement `受控上游思考与写入标记` and arms no gate. The journey SHALL, in order:
1. Log in as `zhangsan` through the UI and, before the chat page is opened (the chat page reads the workspace list when it mounts), ensure the workspace `ui-walk-sessions` exists via the page's authenticated request context (`POST /api/workspaces` → 201 or 409 only).
2. On the welcome state, click the scene pill `代码开发`: it becomes pressed (`aria-pressed="true"`, the other two `日常办公`/`创意设计` not pressed) and the `快捷任务` chips switch to the code-scene list. The composer footer reads `任务启动于` `未选择`; opening its workspace popover shows the search input `搜索工作空间`, typing `ui-walk-sessions` and choosing it makes the footer read `任务启动于` `ui-walk-sessions`.
3. Send `WORKBUDDY_THINK WORKBUDDY_WRITE 会话走查 <uuid>` (a fresh UUID per project). The `POST /api/sessions` request, observed and not fulfilled, SHALL carry a body that parses to a JSON object deep-equal to `{"workspaceId":<that workspace id>,"scene":"code"}`. The turn raises no approval bar (the tool round is a write-tier `write`), the `write` step reaches `已完成`, and the assistant reaches the exact fixed reply and done state.
4. Thinking fold: the assistant message shows, before its answer body, a collapsed `<details>` whose summary is `深度思考过程`; expanding it shows exactly `先读需求，再列要点，最后作答。`.
5. File changes: the assistant message shows a card headed `文件变更（1 个）` with one row whose path reads `zhangsan/ui-walk-sessions/workbuddy-report.html` (ADR-0011 logical path, never the sandbox root), marked `写入` with no +/− counts, and whose `查看详情` navigates to `/files?ws=<workspace id>` — asserted on the first navigation after the click, because the files page rewrites a missing or unknown `ws` to the first workspace and the settled URL would not tell — (the files page accepts only `ws`; there is no path parameter, so it lands on the workspace, not the file), after which the journey returns to the session by a real navigation; an `HTML` artifact card offers `打开网页预览`, which opens a dialog containing an `iframe` with `sandbox="allow-scripts"` (no `allow-same-origin`) whose document shows the heading `WorkBuddy`; the topbar `产物面板` opens a drawer listing that one file. (Edit `+N/−N` counts are not reachable through real omp with the controlled upstream; they are proven by the fake omp `edit-write` scenario in server tests.) The values shown in steps 4 and 5 SHALL also be read back from `GET /api/sessions/<id>/messages` through the page's request context: the assistant message's `thinking` equals that text, its one step's `changes` deep-equals `[{"path":"workbuddy-report.html","added":null,"removed":null,"kind":"write"}]`, and the session view carries `scene` `code` and that `workspaceId`.
6. Sidebar: the session is listed exactly once, under the `空间` section's `ui-walk-sessions` group, not under `任务` or `置顶任务` (on `mobile-dark` through the sidebar overlay, as in the existing journey).
7. Pin: the entry's row menu (the button named `更多操作：<title>` of that entry; on `mobile-dark` inside the sidebar overlay) → `置顶任务` moves the entry to the `置顶任务` section (still exactly one entry for the session, gone from `空间`), and the menu then offers `取消置顶` and no longer `置顶任务`.
8. Rename: the row menu → `重命名` opens the dialog `重命名任务` whose `任务名称` field holds the current title; entering a new title (unique per project) and `保存` closes the dialog and updates the sidebar entry and the topbar title; after a page reload the new title and the pinned section persist, and `GET /api/sessions` through the page's request context lists the session with that `title` and a non-null `pinnedAt`.
9. Search: the topbar `对话内搜索` opens the `搜索对话内容` box; typing the UUID shows the counter `1/1` and marks the user message as the current match (its article carries `aria-current="true"` and is in the viewport; the assistant's article carries no `aria-current`); replacing the term with one that has no match shows `0/0` and no current match; with the UUID typed again, `Esc` in the box closes it and clears the highlight.
10. (Slash candidates are not part of this journey yet.)
11. Delete: the row menu → `删除` opens the confirmation `删除任务` with text `确定要删除「<new title>」吗？删除后不可恢复。`; confirming `删除` shows `Toast` `任务已删除`, the entry disappears from every sidebar section, the page no longer selects `?session=<id>` (welcome state), and `GET /api/sessions/<id>/messages` through the page's request context answers 404.
A `finally` block around steps 2–11 SHALL delete the created session through the page's request context — `DELETE /api/sessions/<id>`, 204 or 404 accepted (404 once step 11 has deleted it; the server stops a running turn before deleting it) — on success and when a step fails, so no running turn or session row is left; the session id is taken from the 201 response of the observed `POST /api/sessions`, before the assertion on that request's body, so a failed step assertion cannot leave the session behind. The adopted workspace and the overwritten `workbuddy-report.html` remain for the next run. The journey then logs out through the UI. The test consumes the caller-owned app/upstream without starting or stopping them.

#### Scenario: 会话元数据走查
- **WHEN** `make ui-walk` runs with the glob `ui-walk*.spec.ts` against the real stack in both `desktop-light` (1440×900) and `mobile-dark` (390×844)
- **THEN** in each project the scene pill and footer workspace choice produce a bound `code` session, the thinking fold shows exactly `先读需求，再列要点，最后作答。`, the file-change card shows the one written file by logical path with `写入`, the html preview renders in a `allow-scripts`-only sandboxed iframe, the artifact drawer lists that file, the sidebar moves the session from `空间 › ui-walk-sessions` to `置顶任务` on pin, rename persists across reload, search counts `1/1` with highlight and `0/0` for a miss, and delete removes the session (Toast `任务已删除`, REST 404); `ui-walk.spec.ts` still passes unchanged in both projects and the whole run finishes within `globalTimeout` 300000 ms

#### Scenario: 假进度不能满足走查
- **WHEN** a candidate renders the thinking fold or file-change card from client-side fabrication without a server `thinking`/`changes` value, creates the session without the chosen workspace or scene, lists the session in two sidebar sections, keeps it after delete, loses the rename on reload, or shows a search counter without marking the matching message
- **THEN** the corresponding DOM or REST assertion fails and the walkthrough fails rather than passing on partial state
