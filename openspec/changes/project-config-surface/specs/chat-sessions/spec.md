## ADDED Requirements

### Requirement: 项目配置文件列表
`GET /api/project-config` (`server/src/sessions/rest-project-config.ts`, registered next to `GET /api/commands`) SHALL follow the same request rules as `GET /api/commands` (cookie guard first, no-store, no body, at most the single `workspaceId` key, 400 and 404 as there) and return200 `{files:[{path,kind,depth}]}`: the project configuration files that exist at the locations omp reads for the cwd a session of that account would run in. It is a list of files present, not of files in effect: omp keeps one instruction file per directory level by provider priority (verified by run on v18.0.10: with `AGENTS.md` and `.claude/CLAUDE.md` in one directory only the latter reaches the system prompt), and the host does not reproduce that. The directories are those of `listProjectSkills` (cwd upwards to the `.git` level or `sandboxRoot`); `depth` is 0 for the cwd and grows by one per level; `path` is relative to that directory with `/` separators. The location table is fixed and belongs to this requirement: `AGENTS.md`, `.omp/AGENTS.md`, `.omp/RULES.md`, `.claude/CLAUDE.md`, `.agents/AGENTS.md` (`kind:"instructions"`), `.omp/SYSTEM.md` at depth 0 only (`kind:"system"`), and the `*.md` files directly inside `.omp/agents` of the nearest directory that has a non-empty `.omp` — looked up through every ancestor up to `sandboxRoot`, not stopping at `.git` — (`kind:"agent"`, at most the first 64 in code-point order). Every table row SHALL be backed by a real-binary test that places only that file — once at depth 0 and once at depth 1 — and finds its marker in `get_state.systemPrompt` (agents: in the task tool's agent list); a location the pinned omp does not read SHALL be removed from the table, and one it reads only in the cwd restricted to depth 0, by changing this requirement before the route ships. A file is listed only when `lstat` says regular file (a symlink is not followed and not listed); the host reads no content, and any filesystem error for a location lists nothing for it. Entries are ordered by `depth`, then by `path` in code-point order. The route SHALL NOT touch any session or process.

#### Scenario: Files present at the read locations
- **WHEN** the owner GETs `/api/project-config?workspaceId=<own workspace>` whose root holds `AGENTS.md`, `.omp/RULES.md`, `.omp/agents/reviewer.md`, `.claude/CLAUDE.md`, `GEMINI.md` and `.omp/SYSTEM.md` → a symlink, while the owner root holds `AGENTS.md` and `.omp/SYSTEM.md`
- **THEN** the response lists, in this order, depth 0 `.claude/CLAUDE.md`, `.omp/RULES.md`, `.omp/agents/reviewer.md` (`agent`), `AGENTS.md`, then depth 1 `AGENTS.md`; `GEMINI.md`, the symlink and the ancestor's `.omp/SYSTEM.md` are absent
- **WHEN** the workspace holds none of the files, the id belongs to another account, or the request carries a body
- **THEN** the responses are 200 `{files:[]}`, 404 not_found and 400 bad_request

## MODIFIED Requirements

### Requirement: Slash 命令白名单与命令目录
`server/src/sessions/slash-commands.ts` SHALL export the builtin whitelist `BUILTIN_COMMANDS` in this fixed order: `compact` (label `整理上下文`, description `压缩较长对话的上下文，保留要点`, hint `可选：想保留的重点`) and `todo` (label `任务清单`, description `查看或修改助手的任务清单`, hint `可选：append <任务>`); no other omp builtin SHALL be whitelisted by this change (`retry` is deliberately excluded: turn-control's regenerate already covers it and its `agentInvoked:true` receipt would add a second local-command completion mode). It SHALL export `listSkills(agentDir)`: synchronously enumerate the entries of `<agentDir>/skills` whose name does not start with `.`, keep at most the first 256 of them in code-point order of their SKILL.md path (further entries are ignored without any filesystem access), and read `<entry>/SKILL.md` for each kept entry without branching on the entry type (a plain file simply fails the read). A symlink is followed only inside the skills directory — a deliberate host restriction; omp itself follows any symlinked directory (`discovery/helpers.ts:428-431`): the host resolves the real path of `<entry>/SKILL.md` and skips the entry unless that real path lies inside the real path of `<agentDir>/skills` — both real paths SHALL come from the kernel (`realpathSync.native`), not from Node's JS `realpathSync`, which stops resolving at a FIFO or socket and folds `..` lexically, so its result can name a different file than the one the kernel opens; and both SHALL be kept as the raw bytes the kernel returned (`{ encoding: "buffer" }`): the containment check compares bytes and the open is given the same bytes, because decoding a path to a string replaces every ill-formed UTF-8 sequence with U+FFFD and re-encoding it names a different path — then opens the resolved path with `O_NOFOLLOW`, so file content outside `skills/` never reaches the catalogue through a link; the read SHALL be bounded and non-blocking as defence in depth — under omp-runtime「OMP_STATE_DIR 托管布局」 the directory is no longer writable by the omp uid, but whatever an operator installs there is still read by the server process: SKILL.md is opened with `O_NONBLOCK | O_NOCTTY` (a terminal device placed there cannot become the server's controlling terminal), and only a regular file of at most 262144 bytes is read — a FIFO, device, directory or larger file is skipped like an unreadable one; normalise `\r\n?` to `\n` and read only the leading frontmatter block — the content starts with `---` and the block ends before the first later line starting with `---`; an unclosed block is no frontmatter — taking, without a YAML library, the top-level (unindented) `key: value` lines for `name`, `description` and `enabled`: a value is trimmed and loses one pair of surrounding quotes; a value that is exactly a block-scalar indicator (`>` or `|`, optionally followed by `+` or `-`) takes the following more-indented lines, each trimmed, joined with one U+0020 (`>`) or `\n` (`|`); `name` defaults to the entry name when missing or empty. An entry is skipped when SKILL.md is missing or unreadable, when `description` is missing or empty, or when the unquoted `enabled` value is `false` (omp's own drop rules for a user-level skill: `discovery/builtin.ts:295-300`, `discovery/helpers.ts:397-403`), and — a host rule; omp does not validate names — when `name` does not match `^[^\s/]+$` (such a name cannot be selected through `/skill:<name>`, whose name ends at the first U+0020). Entries sharing a `name` collapse to the one whose SKILL.md path is smallest in code-point order (omp is first-wins over the same order, `extensibility/skills.ts:220-221`). Any failure to enumerate `skills` (absent, not a directory, unreadable) yields `[]`, as omp's scan does (`discovery/helpers.ts:384-392`); the result is sorted by `name` in code-point order and is recomputed on every call (no cache). It SHALL export `listProjectSkills(cwd, sandboxRoot)` (#773): the project skills of a session cwd, read from `<D>/.omp/skills` for the directories `D` = `cwd`, its parent, and so on, stopping after the first `D` that has an entry named `.git` (that `D` is still scanned — omp's `repoRoot`, `capability/fs.ts:84-95`, `discovery/builtin.ts:284`) or after `sandboxRoot`, whichever comes first; a `cwd` that is not `sandboxRoot` or inside it is scanned alone. Each `<D>/.omp/skills` is read by exactly the rules of `listSkills` above (hidden entries, the 256-entry cap, kernel real paths as raw bytes with the containment boundary being that `skills` directory, `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, regular file of at most 262144 bytes, the frontmatter reader, the skip rules and the name rule), the directory being writable by the omp uid; a `description` longer than 200 code points is cut to its first 200. A name found in a nearer `D` hides the same name in a farther one (omp v18.0.10, verified by run: nearest project skill wins); the result is sorted by `name` in code-point order, never throws (any failure for one `D` yields nothing for that `D`) and is recomputed on every call. Only `.omp/skills` is read: omp v18.0.10 also loads project skills from `.claude`, `.codex`, `.agents`, `.agent`, `.opencode` and `.github` under the cwd (the first, third and fourth also under its ancestors), from the same four directories under the managed `HOME`, and from ancestors above `sandboxRoot` when no `.git` stops it; none of these is listed, and in the two precedence pairs run against the real binary (`.omp` project vs `.claude`/`.codex`/`.agents` project of the same name; platform vs `.claude` project of the same name) the `.omp` or platform skill won, so a listed name runs the listed skill. It SHALL export `sessionSkills(agentDir, cwd, sandboxRoot)`: the platform skills of `listSkills(agentDir)` and the project skills of `listProjectSkills(cwd, sandboxRoot)` as `{name, description, source: "skill" | "project", overrides}` — a project skill replaces the platform skill of the same name (omp runs the project one) and carries `overrides: true`; every other entry carries `overrides: false`; platform entries first, then project entries, each group in name order. It SHALL export `classifyPrompt(text, skills)` for already-trimmed text: text not starting with `/` → `{kind:"text"}`; otherwise the name is the characters after `/` up to the first whitespace or `:`; a name equal to a `BUILTIN_COMMANDS` name → `{kind:"builtin", name}`, except `todo` with the subcommand `import` or `export`, which is `{kind:"text"}`: the subcommand is taken as omp takes it (`slash-commands/helpers/parse.ts:22-36,58-64`) — the text after the name's terminating whitespace or `:` is trimmed, cut at its first whitespace and lower-cased — because omp resolves the path argument of these two subcommands with `resolveToCwd`, which honours absolute paths, `~` and `..` (`tools/path-utils.ts:565-579`), reads or writes that file with no tool frame, no step row and no `files.changed`, and echoes parse errors of an imported file as the reply; the host does not parse or validate the path, it simply does not whitelist the two subcommands, so the text reaches the model escaped like any other non-whitelisted `/` text; text starting with `/skill:` whose skill name — the characters up to the first U+0020, exactly omp's split (`extensibility/skills.ts:456-459`), so a newline is part of the name — equals the `name` of a skill in `skills` (the platform and project skills of the session's cwd: every caller passes `sessionSkills` of that session) → `{kind:"skill", name}`; every other `/`-prefixed text (different case, non-whitelisted builtin, unknown skill, a skill name broken by a newline, pasted paths) → `{kind:"text"}`. It SHALL export `toWireText(text, skills)`: `builtin`/`skill` → the text unchanged; `text` starting with `/` → one U+0020 followed by the text; anything else unchanged. Arguments of whitelisted commands (`/todo append 买菜`, `/compact:focus 保留结论`, `/skill:<name> 写周报`) SHALL pass through unchanged. A `/skill:<installed>` token in the middle of a prompt is `text` for the host and is left to omp (which executes the skill exactly as in its TUI). The host gives no guarantee that a `/skill:<name>` it classifies `text` is not run: omp's skill dispatch `trimStart()`s the escape space, so a skill omp loaded and the host does not list — one from another provider directory, from the managed `HOME`, from above `sandboxRoot`, or one the host's own read rules skipped — still runs (accepted residual, ADR-0012). The prompt route, regenerate and fork SHALL each classify with `sessionSkills` computed from the session's own cwd (the owner root for an unbound session, the workspace root for a bound one; a cwd that cannot be resolved contributes no project skill), read only for `/`-prefixed text.
`GET /api/commands` (`server/src/sessions/rest-commands.ts`, registered by registerSessions next to the session routes) SHALL require the cookie guard (401 with no-store otherwise, decided before the body/query check: an unauthenticated request carrying either is 401), carry Cache-Control:no-store, accept no body and no query string other than exactly one `workspaceId` key with a single value (an authenticated request with a body, any other key, a repeated key or an empty value SHALL return400 bad_request; a `workspaceId` that is malformed, unknown or not the caller's SHALL return404 not_found through the owner-scoped workspace `rootOf`, the same single 404 session creation answers) and return200 `{commands:[{name,label,description,hint,source,overrides}]}` for the cwd a session of that account would run in — the workspace root with `workspaceId`, the owner root without: the two builtins first in whitelist order with `name` equal to the builtin name and `source:"builtin"`, then every entry of `sessionSkills` in its order with `name` `skill:<skill name>`, `label` the skill name, `description` the description as returned (possibly English), `hint` `可选参数`, `source` `"skill"` (platform) or `"project"` and `overrides` as returned; builtins carry `overrides:false`; `hint` SHALL be a string or null; the route SHALL NOT be a content-parser owner and SHALL NOT touch any session or process (the workspace lookup is its only SQLite read).
**Branch alignment** (used by regenerate and fork instead of a plain equality on stored content). The *wire candidates* of a stored user content `c` are `c` itself and, when `c` starts with `/`, one U+0020 followed by `c` (the escaped form; a message persisted before the prompt route escaped was sent verbatim). Candidates depend only on the stored text — alignment never classifies history by the current skill set, so installing or removing a skill (platform or project) later does not move it. Regenerate SHALL return400 bad_request, with no spawn, no frame and no row change and after the 409 busy check, when `classifyPrompt` of the stored last user message yields `builtin` or `skill` (such a turn left no omp `user` entry); otherwise it SHALL require the text of the last branch entry to be a wire candidate of the stored last user message (any other outcome, including an empty list → 502 agent_unavailable with no row change, as before; only this pair is compared, earlier entries are not read). Fork SHALL return400 the same way when the chosen `messageId`'s content classifies `builtin` or `skill`; otherwise, with the source's stored `user` messages U1…Un in id order and the branch entries E1…Em in list order, it SHALL align them first-fit from the front: Ui is aligned to the current Ej when `Ej.text` is a wire candidate of `Ui.content`, consuming both; a Ui that does not match the current Ej is skipped and consumes no entry (it left no omp `user` entry: a whitelisted builtin, a skill invocation — leading or mid-prompt, which omp stores as a `custom` message — or any other local-only turn); an entry whose `entryId` or `text` is not a string matches nothing. Fork SHALL use the entry aligned to the chosen message (no aligned entry → 502 agent_unavailable and no new session row, as before). Fork's `draft` SHALL be the stored content of the chosen user message (identical to the branch text for every message that does not start with `/`; never carries the escape space).
