## ADDED Requirements

### Requirement: 项目配置文件列表
`GET /api/project-config` (`server/src/sessions/rest-project-config.ts`, registered next to `GET /api/commands`) SHALL follow the same request rules as `GET /api/commands` (cookie guard first, no-store, no body, at most the single `workspaceId` key, 400 and 404 as there) and return200 `{files:[{path,kind,depth}]}`: the project configuration files that exist at the locations omp reads for the cwd a session of that account would run in. It is a list of files present, not of files in effect: omp keeps one instruction file per directory level by provider priority (verified by run on v18.0.10: with `AGENTS.md` and `.claude/CLAUDE.md` in one directory only the latter reaches the system prompt), and the host does not reproduce that. The *walk* is the directory list of `listProjectSkills` (the resolved cwd upwards to the `.git` level or `sandboxRoot`; empty, and the response `{files:[]}`, when the resolved cwd is not inside the resolved `sandboxRoot`), and the agents lookup runs on the same resolved chain; `depth` is 0 for the cwd and grows by one per level; `path` is relative to that directory with `/` separators. The location table is fixed and belongs to this requirement (every row verified by run on v18.0.10, at depth 0 and at depth 1): in every directory of the walk, `AGENTS.md` and `.agents/AGENTS.md` (`kind:"instructions"`); in the cwd only, `.claude/CLAUDE.md` (`instructions`); in the nearest directory of the walk whose `.omp` holds at least one entry, `.omp/AGENTS.md` and `.omp/RULES.md` (`instructions`) and — only when that directory is the cwd — `.omp/SYSTEM.md` (`kind:"system"`); and the `*.md` files directly inside `.omp/agents` of the nearest directory, from the cwd up to `sandboxRoot` without stopping at `.git`, in which `.omp/agents` is a directory (`kind:"agent"`: of the regular `*.md` files, at most the first 64 in code-point order; `depth` is that directory's distance from the cwd; omp's `findAllNearestProjectConfigDirs`, `task/discovery.ts:86-95`). Every directory between an inspected directory — one of the walk, or one of the agents lookup — and a listed file (`.omp`, `.omp/agents`, `.claude`, `.agents`) SHALL be a real directory by `lstat`, so nothing outside an inspected directory is ever read. `.omp` and `.omp/agents` are enumerated through a directory handle reading at most 4096 entries. A `.omp` or `.omp/agents` that is a link, or holds more than 4096 entries, ends the respective nearest-directory search at that level with nothing listed for those rows (omp follows the link and stops there too); only a missing or unreadable one lets the search continue upwards. Every table row SHALL be backed by a real-binary test that places only that file — once at depth 0 and once at depth 1, with no `.git` in between — and finds its marker in `get_state.systemPrompt` (agents: in the task tool's agent list; for a cwd-only row: its absence at depth 1); where the pinned omp disagrees with a row — it does not read the location, reads it only in the cwd, or reads it at more levels than the row says — this requirement SHALL be changed to match before the route ships. A file is listed only when `lstat` says regular file (a symlink is not followed and not listed); the host reads no content, and any filesystem error for a location lists nothing for it. Entries are ordered by `depth`, then by `path` in code-point order. The route SHALL NOT touch any session or process.

#### Scenario: Files present at the read locations
- **WHEN** the owner GETs `/api/project-config?workspaceId=<own workspace>` whose root holds `AGENTS.md`, `.omp/RULES.md`, `.omp/agents/reviewer.md`, `.claude/CLAUDE.md`, `GEMINI.md` and `.omp/SYSTEM.md` → a symlink, while the owner root holds `AGENTS.md`, `.claude/CLAUDE.md`, `.omp/RULES.md`, `.omp/SYSTEM.md` and `.omp/agents/far.md`
- **THEN** the response lists, in this order, depth 0 `.claude/CLAUDE.md`, `.omp/RULES.md`, `.omp/agents/reviewer.md` (`agent`), `AGENTS.md`, then depth 1 `AGENTS.md`; `GEMINI.md`, the symlink and everything else of the owner root (its `.claude/CLAUDE.md`, and its `.omp` files because the nearer `.omp` wins) are absent
- **WHEN** the workspace root's `.omp` holds only `skills/x/SKILL.md` while the owner root holds `.omp/RULES.md` and `.omp/agents/far.md`, and separately the workspace root has no `.omp` at all
- **THEN** the first lists depth 1 `.omp/agents/far.md` only (the nearer non-empty `.omp` has no `RULES.md`, and `agents` is looked up on its own); the second lists depth 1 `.omp/RULES.md` and `.omp/agents/far.md`
- **WHEN** the workspace root's `.omp` is a symlink to a directory outside the sandbox holding `RULES.md` and `agents/a.md`, and separately only `.omp/agents` is such a symlink, while in both cases the owner root holds `.omp/RULES.md` and `.omp/agents/far.md`
- **THEN** neither response contains anything from the link target, no directory outside the inspected ones is enumerated, and the owner root's `.omp/RULES.md` and `.omp/agents/far.md` are absent in both (first: both searches end at the link; second: the workspace root's real `.omp` holds an entry and so is the nearest, and the agents search ends at the link)
- **WHEN** the workspace holds none of the files, the id belongs to another account, or the request carries a body
- **THEN** the responses are 200 `{files:[]}`, 404 not_found and 400 bad_request; a workspace of the caller whose root is unusable also answers 200 `{files:[]}`

## MODIFIED Requirements

### Requirement: Slash 命令白名单与命令目录
`server/src/sessions/slash-commands.ts` SHALL export the builtin whitelist `BUILTIN_COMMANDS` in this fixed order: `compact` (label `整理上下文`, description `压缩较长对话的上下文，保留要点`, hint `可选：想保留的重点`) and `todo` (label `任务清单`, description `查看或修改助手的任务清单`, hint `可选：append <任务>`); no other omp builtin SHALL be whitelisted by this change (`retry` is deliberately excluded: turn-control's regenerate already covers it and its `agentInvoked:true` receipt would add a second local-command completion mode). It SHALL export `listSkills(agentDir)`: synchronously enumerate the entries of `<agentDir>/skills` whose name does not start with `.`, keep at most the first 256 of them in code-point order of their SKILL.md path (further entries are ignored without any filesystem access), and read `<entry>/SKILL.md` for each kept entry without branching on the entry type (a plain file simply fails the read). A symlink is followed only inside the skills directory — a deliberate host restriction; omp itself follows any symlinked directory (`discovery/helpers.ts:428-431`): the host resolves the real path of `<entry>/SKILL.md` and skips the entry unless that real path lies inside the real path of `<agentDir>/skills` — both real paths SHALL come from the kernel (`realpathSync.native`), not from Node's JS `realpathSync`, which stops resolving at a FIFO or socket and folds `..` lexically, so its result can name a different file than the one the kernel opens; and both SHALL be kept as the raw bytes the kernel returned (`{ encoding: "buffer" }`): the containment check compares bytes and the open is given the same bytes, because decoding a path to a string replaces every ill-formed UTF-8 sequence with U+FFFD and re-encoding it names a different path — then opens the resolved path with `O_NOFOLLOW`, so file content outside `skills/` never reaches the catalogue through a link; the read SHALL be bounded and non-blocking as defence in depth — under omp-runtime「OMP_STATE_DIR 托管布局」 the directory is no longer writable by the omp uid, but whatever an operator installs there is still read by the server process: SKILL.md is opened with `O_NONBLOCK | O_NOCTTY` (a terminal device placed there cannot become the server's controlling terminal), and only a regular file of at most 262144 bytes is read — a FIFO, device, directory or larger file is skipped like an unreadable one; normalise `\r\n?` to `\n` and read only the leading frontmatter block — the content starts with `---` and the block ends before the first later line starting with `---`; an unclosed block is no frontmatter — taking, without a YAML library, the top-level (unindented) `key: value` lines for `name`, `description` and `enabled`: a value is trimmed and loses one pair of surrounding quotes; a value that is exactly a block-scalar indicator (`>` or `|`, optionally followed by `+` or `-`) takes the following more-indented lines, each trimmed, joined with one U+0020 (`>`) or `\n` (`|`); `name` defaults to the entry name when missing or empty. An entry is skipped when SKILL.md is missing or unreadable, when `description` is missing or empty, or when the unquoted `enabled` value is `false` (omp's own drop rules for a user-level skill: `discovery/builtin.ts:295-300`, `discovery/helpers.ts:397-403`), and — a host rule; omp does not validate names — when `name` does not match `^[^\s/]+$` (such a name cannot be selected through `/skill:<name>`, whose name ends at the first U+0020). Entries sharing a `name` collapse to the one whose SKILL.md path is smallest in code-point order (omp is first-wins over the same order, `extensibility/skills.ts:220-221`). Any failure to enumerate `skills` (absent, not a directory, unreadable) yields `[]`, as omp's scan does (`discovery/helpers.ts:384-392`); the result is sorted by `name` in code-point order and is recomputed on every call (no cache). It SHALL export `listProjectSkills(cwd, sandboxRoot)` (#773): the project skills of a session cwd, read from `<D>/.omp/skills` for the directories `D` = `cwd`, its parent, and so on, stopping after the first `D` where `lstat(<D>/.git)` succeeds (that `D` is still scanned — omp's `repoRoot`, `capability/fs.ts:84-95`, `discovery/builtin.ts:284`; the host does not enumerate `D`) or after `sandboxRoot`, whichever comes first. The walk runs on kernel real paths: `cwd` and `sandboxRoot` are first resolved (`realpathSync.native`, raw bytes), and a resolved `cwd` that is neither the resolved `sandboxRoot` nor below it (byte prefix followed by `/`) yields `[]` — the sandbox root is `2770` and the owner root is not checked for links by the session cwd resolver, so the omp uid can put a symlink where a cwd is expected; every `D` is a parent of the resolved `cwd`, hence a real directory inside the sandbox. Each `<D>/.omp/skills` is read by exactly the rules of `listSkills` above (hidden entries, the 256-entry cap, kernel real paths as raw bytes with the containment boundary being that `skills` directory, `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, regular file of at most 262144 bytes, the frontmatter reader, the skip rules and the name rule), with three additions because the directory is writable by the omp uid: a `SKILL.md` whose `fstat` link count is not 1 is skipped (a hard link to a file the server can read would otherwise echo that file's frontmatter); the kernel real path of `<D>/.omp/skills` SHALL equal, byte for byte, the kernel real path of `D` followed by `/.omp/skills` — so neither `.omp` nor `skills` is a link and the containment boundary cannot be moved outside `D` — otherwise that `D` yields nothing; and the directory is enumerated through a directory handle reading at most 4096 entries — one holding more yields nothing for that `D` (the 256-entry cap applies after the sort, as for the platform directory); a `description` longer than 200 code points is cut to its first 200. A name found in a nearer `D` hides the same name in a farther one (omp v18.0.10, verified by run: nearest project skill wins); the result is sorted by `name` in code-point order, never throws (any failure for one `D` yields nothing for that `D`) and is recomputed on every call. Only `.omp/skills` is read: omp v18.0.10 also loads project skills from `.claude`, `.codex`, `.agents`, `.agent`, `.opencode` and `.github` under the cwd (the first, third and fourth also under its ancestors), from the same four directories under the managed `HOME`, and from ancestors above `sandboxRoot` when no `.git` stops it; none of these is listed, and in the two precedence pairs run against the real binary (`.omp` project vs `.claude`/`.codex`/`.agents` project of the same name; platform vs `.claude` project of the same name) the `.omp` or platform skill won, so a listed name runs the listed skill — unless a nearer `.omp/skills` holds a skill of that name which the host's read rules skipped and omp loaded (omp follows links and has no caps): then the farther or platform entry is listed with its own `source` and `overrides` while omp runs the nearer one (accepted residual). It SHALL export `sessionSkills(agentDir, cwd, sandboxRoot)`: the platform skills of `listSkills(agentDir)` and the project skills of `listProjectSkills(cwd, sandboxRoot)` as `{name, description, source: "skill" | "project", overrides}` — a project skill replaces the platform skill of the same name (omp runs the project one) and carries `overrides: true`; every other entry carries `overrides: false`; platform entries first, then project entries, each group in name order. It SHALL export `classifyPrompt(text, skills)` for already-trimmed text: text not starting with `/` → `{kind:"text"}`; otherwise the name is the characters after `/` up to the first whitespace or `:`; a name equal to a `BUILTIN_COMMANDS` name → `{kind:"builtin", name}`, except `todo` with the subcommand `import` or `export`, which is `{kind:"text"}`: the subcommand is taken as omp takes it (`slash-commands/helpers/parse.ts:22-36,58-64`) — the text after the name's terminating whitespace or `:` is trimmed, cut at its first whitespace and lower-cased — because omp resolves the path argument of these two subcommands with `resolveToCwd`, which honours absolute paths, `~` and `..` (`tools/path-utils.ts:565-579`), reads or writes that file with no tool frame, no step row and no `files.changed`, and echoes parse errors of an imported file as the reply; the host does not parse or validate the path, it simply does not whitelist the two subcommands, so the text reaches the model escaped like any other non-whitelisted `/` text; text starting with `/skill:` whose skill name — the characters up to the first U+0020, exactly omp's split (`extensibility/skills.ts:456-459`), so a newline is part of the name — equals the `name` of a skill in `skills` (the platform and project skills of the session's cwd: every caller passes `sessionSkills` of that session) → `{kind:"skill", name}`; every other `/`-prefixed text (different case, non-whitelisted builtin, unknown skill, a skill name broken by a newline, pasted paths) → `{kind:"text"}`. It SHALL export `toWireText(text, skills)`: `builtin`/`skill` → the text unchanged; `text` starting with `/` → one U+0020 followed by the text; anything else unchanged. Arguments of whitelisted commands (`/todo append 买菜`, `/compact:focus 保留结论`, `/skill:<name> 写周报`) SHALL pass through unchanged. A `/skill:<installed>` token in the middle of a prompt is `text` for the host and is left to omp (which executes the skill exactly as in its TUI). The host gives no guarantee that a `/skill:<name>` it classifies `text` is not run: omp's skill dispatch `trimStart()`s the escape space, so a skill omp loaded and the host does not list — one from another provider directory, from the managed `HOME`, from above `sandboxRoot`, or one the host's own read rules skipped — still runs (accepted residual, ADR-0012). The prompt route, regenerate and fork SHALL each classify with `sessionSkills` computed from the session's own cwd (the owner root for an unbound session, the workspace root for a bound one; a cwd that cannot be resolved — `rootOf` throws or answers a path that is not a directory — contributes no project skill), read only for `/`-prefixed text. One more accepted mismatch, in the other direction: omp loads its skills when the process starts (verified by run on v18.0.10: a `SKILL.md` created afterwards is absent from `get_available_commands` and its `/skill:<name>` prompt is sent to the model as an ordinary message), while the host recomputes on every call; until that session's process is next started, the host classifies such a prompt `skill`, sends it unescaped, and regenerate or fork anchored on it answer 400.
`GET /api/commands` (`server/src/sessions/rest-commands.ts`, registered by registerSessions next to the session routes) SHALL require the cookie guard (401 with no-store otherwise, decided before the body/query check: an unauthenticated request carrying either is 401), carry Cache-Control:no-store, accept no body and no query string other than exactly one `workspaceId` key with a single value (an authenticated request with a body, any other key, a repeated key or an empty value SHALL return400 bad_request; a `workspaceId` that is malformed, unknown or not the caller's SHALL return404 not_found through the owner-scoped workspace `rootOf`; a workspace of the caller whose root is unusable — `rootOf` throws, or the path is not a directory — is not an error: the response is 200 with the builtins and the platform skills only) and return200 `{commands:[{name,label,description,hint,source,overrides}]}` for the cwd a session of that account would run in — the workspace root with `workspaceId`, the owner root without: the two builtins first in whitelist order with `name` equal to the builtin name and `source:"builtin"`, then every entry of `sessionSkills` in its order with `name` `skill:<skill name>`, `label` the skill name, `description` the description as returned (possibly English), `hint` `可选参数`, `source` `"skill"` (platform) or `"project"` and `overrides` as returned; builtins carry `overrides:false`; `hint` SHALL be a string or null; the route SHALL NOT be a content-parser owner and SHALL NOT touch any session or process (the workspace lookup is its only SQLite read).
**Branch alignment** (used by regenerate and fork instead of a plain equality on stored content). The *wire candidates* of a stored user content `c` are `c` itself and, when `c` starts with `/`, one U+0020 followed by `c` (the escaped form; a message persisted before the prompt route escaped was sent verbatim). Candidates depend only on the stored text — alignment never classifies history by the current skill set, so installing or removing a skill (platform or project) later does not move it. Regenerate SHALL return400 bad_request, with no spawn, no frame and no row change and after the 409 busy check, when `classifyPrompt` of the stored last user message yields `builtin` or `skill` (such a turn left no omp `user` entry); otherwise it SHALL require the text of the last branch entry to be a wire candidate of the stored last user message (any other outcome, including an empty list → 502 agent_unavailable with no row change, as before; only this pair is compared, earlier entries are not read). Fork SHALL return400 the same way when the chosen `messageId`'s content classifies `builtin` or `skill`; otherwise, with the source's stored `user` messages U1…Un in id order and the branch entries E1…Em in list order, it SHALL align them first-fit from the front: Ui is aligned to the current Ej when `Ej.text` is a wire candidate of `Ui.content`, consuming both; a Ui that does not match the current Ej is skipped and consumes no entry (it left no omp `user` entry: a whitelisted builtin, a skill invocation — leading or mid-prompt, which omp stores as a `custom` message — or any other local-only turn); an entry whose `entryId` or `text` is not a string matches nothing. Fork SHALL use the entry aligned to the chosen message (no aligned entry → 502 agent_unavailable and no new session row, as before). Fork's `draft` SHALL be the stored content of the chosen user message (identical to the branch text for every message that does not start with `/`; never carries the escape space).

### Requirement: REST prompt 受理与补偿
The prompt route SHALL accept only application/json and an object with exactly message:string. It SHALL trim the string once and require nonempty text of at most32768 UTF-8 bytes. Invalid shape, media, malformed JSON or oversized parser envelope SHALL return400 bad_request; decoded valid escape-heavy text SHALL NOT be rejected merely because its wire JSON exceeds32768 bytes. The existing bounded parser envelope remains distinct from the semantic message limit. A trimmed text that starts with `/` SHALL NOT be rejected for that reason: Requirement「Slash 命令白名单与命令目录」 decides whether it reaches omp as a command or as plain text.
The route SHALL use store.acceptPrompt(sessionId,principal.id,text) with the trimmed original text for the atomic admission (persisted user content and the title rule are unchanged) and then await supervisor.prompt(sessionId, toWireText(text, skills)) where `skills` is `sessionSkills(agentDir, cwd, sandboxRoot)` for that session's cwd, computed only for text starting with `/` (`[]` otherwise), and `toWireText`/`sessionSkills` are those of Requirement「Slash 命令白名单与命令目录」 (identity for every text that does not start with `/` and for whitelisted commands; a leading U+0020 otherwise) and `agentDir` is the registerSessionRoutes dependency of Requirement「会话 REST」. The owned SessionSupervisorPort SHALL expose prompt(sessionId:string,text:string):Promise<void>; resolution means dispatch accepted, not turn finished. Successful admission SHALL return202 {userMessageId,assistantMessageId} from that exact store admission. Running sessions SHALL return409 session_busy without added rows or dispatch; so SHALL a session whose supervisor control claim is held by an in-progress regenerate, fork or stop — the claim check and admission SHALL run without an intervening await; idle/done/failed/stopped SHALL be eligible.
Supervisor rejection SHALL compensate the unprogressed accepted pair through store.rollbackPrompt before returning the canonical error. HttpError agent_unavailable SHALL produce502, HttpError session_busy SHALL produce409, HttpError agent_capacity SHALL produce503; unknown failures SHALL remain generic5xx. Compensation failure SHALL propagate as generic5xx, not be masked as502/409/503. The supervisor SHALL NOT reject after publishing/persisting progress; post-dispatch failures belong to supervisor lifecycle. No retries or real runtime/SSE implementation are part of this boundary.

GET /api/sessions SHALL return200 {sessions:[...]} restricted to the owner and ordered updatedAt descending with the store's stable tie-break. PATCH /api/sessions/:id and DELETE /api/sessions/:id follow session-metadata「会话元数据修改」 and「会话删除」. The complete owner-scoped tree and synchronous supervisor.streamCursor(sessionId) SHALL be captured together in the same preParsing stack before done, with no await between them; the handler SHALL serialize only that cached pair. streamCursor SHALL NOT replace owner authorization.
POST /api/sessions/:id/stop and POST /api/sessions/:id/regenerate SHALL be bodyless content-parser owners (the logout precedent): any parsed body (including `{}`), empty-or-malformed JSON, unsupported media or an envelope above their minimal body limit SHALL return400 bad_request after authorization and before any supervisor call, frame or write. When the session is `running`, stop SHALL call supervisor.stop(sessionId) — which holds the session's control claim for the call, first settles every pending approval of that turn, if any exist (the pending set is the snapshot read on entry; it is not re-read before the `abort` frame), as `deny` (per approval: persist decision/decided_at and its `session.approval` audit row in one transaction → answer `Deny` → publish `approval.resolved`) and then writes the `abort` frame; when the turn's prompt frame is not yet written, stop instead records a stop intent and the supervisor writes `abort` right after that prompt's dispatch receipt resolves (after the stop call has returned), so stop neither cancels the dispatch nor compensates the accepted rows and the prompt request still returns its normal202 body (a failed acquisition or dispatch still follows the ordinary prompt compensation, and the intent never rewrites a terminal status another path reached first) — and return202 with body exactly `{}` without waiting for the turn to end; for any other status it SHALL return204 with no writes and no supervisor call. The stopped turn ends with `turn.end{status:"stopped"}` and session/assistant/running steps read `stopped`.
POST /api/sessions/:id/regenerate: a `running` session, or a session whose control claim is held by another regenerate, fork or stop, SHALL return409 session_busy. A session whose history does not end with an assistant message immediately preceded by a user message, or whose last user message classifies as a whitelisted command (`classifyPrompt` → `builtin|skill`, Requirement「Slash 命令白名单与命令目录」), SHALL return400 bad_request (checked after the 409 busy check, with no spawn, frame or row change). Otherwise it SHALL call supervisor.regenerate(sessionId), which registers the session's control claim with the last assistant message id read by the precheck and releases it once dispatch completes or the response returns: acquire the session's process — reusing a live one, or through the same lazy acquisition as prompt (a normal new generation, stream_epoch+1 with a fresh ring) when it has been reclaimed — through the process cap (`agent_capacity` → 503), `get_branch_messages`, require the last entry's `text` to be a wire candidate of the stored last user message (Requirement「Slash 命令白名单与命令目录」 Branch alignment; any other outcome, including an empty list → 502 agent_unavailable with no row change), `branch{entryId}`, `get_state`, then in one SQLite transaction — which SHALL first recheck that the session status is not `running` and its last assistant message id still equals the precheck's, otherwise write nothing, retire the process and return409 session_busy — delete the old assistant row (steps and approvals cascade), insert a new empty `running` assistant row, set `omp_session_file` to the new file and session status `running`, and dispatch the branch-returned text as the prompt, prefixed with one U+0020 when it starts with `/` (turn-control「重新生成 REST」); it SHALL return202 {assistantMessageId} of the new row. Runtime failure before the transaction SHALL leave every row unchanged and map to502 agent_unavailable; dispatch failure after the transaction SHALL settle the new assistant row and session as `failed`, return502 agent_unavailable (rows are already terminal, nothing is compensated) and SHALL NOT resurrect the deleted row.
POST /api/sessions/:id/fork SHALL accept only application/json and an object with exactly messageId:number; any other shape, a messageId that is not a `user` message of this session, a messageId whose stored content classifies as a whitelisted command (`classifyPrompt` → `builtin|skill`), or wrong media/malformed JSON SHALL return400 bad_request (the command check runs after the 409 busy check, with no spawn, frame or row change). A `running` source session, or one whose control claim is held by another regenerate, fork or stop, SHALL return409 session_busy. Otherwise the supervisor SHALL register the source session's control claim (with the last assistant message id read by the precheck), retire the source session's live idle process if one exists (its history is in the file, so this is lossless), then run a temporary runtime through the process cap (`agent_capacity` → 503) with `--resume <source omp_session_file>`, `get_branch_messages`, align the stored user messages to the entries (Branch alignment) and take the entry aligned to the chosen message (no aligned entry → 502 agent_unavailable; no new session row exists), `branch{entryId}`, `get_state`, shut the temporary process down, then in one transaction — which SHALL first recheck that the source status is not `running` and its last assistant message id still equals the precheck's, otherwise write nothing and return409 session_busy — insert the new session row (same owner, copied title, copied `workspace_id` and `scene`, `pinned_at` NULL, `parent_session_id` = source id, `omp_session_file` = the new file, `stream_epoch` 0). No new session row exists before this transaction commits, so every failure leaves none behind. The temporary runtime is not a session generation: it SHALL NOT bump either session's `stream_epoch`, owns no ring, publishes no events, is bound to no slot and counts only against the process cap. The transaction SHALL also copy every chat_messages/chat_steps row of the source that precedes the fork-point user message (new ids, same order, content, thinking, status, timestamps and step detail/output/changes, each copied verbatim including NULL), copy every `chat_approvals` row of those copied messages onto the new message ids (new approval ids; request_id, tool, title, requested_at, expires_at, decision and decided_at preserved), and set the new session's status to the status of the last copied assistant message (`done`, `failed` or `stopped`), leaving it `idle` only when nothing is copied. The source session's rows, status and file SHALL be unchanged; its live process, if any, receives no frame and is retired before the temporary process starts. It SHALL return201 {session,draft} where `session` is the new session's eight-key public view and `draft` is the stored content of the chosen user message (equal to the branch text for every message not starting with `/`; never carries the escape space).
POST /api/sessions/:id/approvals/:approvalId SHALL accept only application/json and an object with exactly decision:"allow"|"deny"; other shapes/media/malformed JSON SHALL return400 bad_request. `approvalId` SHALL be a canonical positive decimal integer naming a `chat_approvals` row whose message belongs to this session, otherwise404 not_found identical to a missing session; a non-canonical approvalId SHALL be rejected before body parsing, and an approvalId not owned by this session SHALL be rejected after body parsing but before any write, answer frame or publish. A row whose `decision` is already set SHALL return409 approval_settled with no writes. A pending row SHALL be settled in this order: in one transaction persist decision/decided_at and its `session.approval` audit row → answer the child (`Approve` for allow, `Deny` for deny) and cancel its timeout timer → publish `approval.resolved` → return200 with the settled approval object `{id,tool,title,requestedAt,expiresAt,decision}` (one element of the snapshot's `approvals` array).
