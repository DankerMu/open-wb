# Spec Delta

## MODIFIED Requirements

### Requirement: 受控上游思考与写入标记
The existing loopback fake-upstream (`server/test/support/fake-upstream.mjs`, the controlled upstream behind real omp in `make smoke`, `make ui-walk` and their CI jobs) SHALL additionally honour three markers found as substrings of the last user message text, selected by the same last-user-text lookup as `WORKBUDDY_UI_WALK:<uuid>` and combinable with it and with each other. `WORKBUDDY_THINK`: the answering text round (the request whose history already holds a `tool` role message) SHALL emit, after the `role` chunk and before the first `content` chunk, exactly three chunks whose `delta` is `{reasoning_content:<part>}` with parts `先读需求，`, `再列要点，`, `最后作答。` (the same deterministic thinking text as the fake omp `thinking` scenario), leaving the content chunks, finish reason and `[DONE]` unchanged; under an armed gate these reasoning chunks are part of the prefix sent before the hold and release is unchanged (unless `WORKBUDDY_HOLD_AT` selects another hold point,「受控上游节奏与闸门停点标记」). `WORKBUDDY_WRITE`: the tool round (history without a `tool` role message) SHALL issue one `write` tool call with arguments exactly `{"path":"workbuddy-report.html","content":"<!doctype html><title>WorkBuddy</title><h1>WorkBuddy</h1>\n"}` instead of the bash call; the answering round is unchanged. `WORKBUDDY_TODO`: the tool round (history without a `tool` role message) SHALL issue one `todo` tool call with arguments exactly `{"op":"init","list":[{"phase":"走查","items":["整理需求","输出结论"]}]}` instead of the bash call; the answering round is unchanged. The tool round issues a single call, so when the last user text contains both `WORKBUDDY_WRITE` and `WORKBUDDY_TODO` the `write` call SHALL win and no `todo` call is issued (every request that carries `WORKBUDDY_WRITE` keeps the frames it receives today); `WORKBUDDY_TODO` combines with `WORKBUDDY_THINK` and with a gate exactly as `WORKBUDDY_WRITE` does. Real omp v18.0.10 executes that `init` on its session task list and reports `tool_execution_end` whose `result.details.phases` is `[{name:"走查",tasks:[{content:"整理需求",status:"in_progress"},{content:"输出结论",status:"pending"}]}]` (it promotes the first pending task to `in_progress`); `todo` is not an exec-tier tool, so real omp in `--approval-mode write` raises no approval for it. These two statements about real omp are derived from the pinned binary and are proven only by the ui-walk step of chat-harness `UI 走查会话元数据`, which thereby also answers whether the `todo` tool (load mode `discoverable`) is callable in RPC mode; the fixture suite proves only the frames the upstream sends. Real omp in `--approval-mode write` treats that plain-path `write` as write tier, so it raises no approval, resolves the relative path against the session's `--cwd` (the bound workspace root for a bound session), writes the file and reports the absolute `details.resolvedPath`. The error marker keeps its precedence. Requests carrying none of the three markers (nor any marker of「受控上游节奏与闸门停点标记」or「受控上游浏览器标记」) SHALL receive byte-for-byte the frames they receive today (bash tool round, fixed reply, no reasoning chunk), so the existing `chat.hurl`, ui-walk journey and gate requirement are unaffected. The fixture test suite SHALL cover all three markers, their combination with a gate, the `WORKBUDDY_WRITE` precedence over `WORKBUDDY_TODO`, and the unmarked default.
A `user` message that omp synthesises to attach tool-result images (defined in「受控上游浏览器标记」) is not a user message for any rule of this requirement — neither for the round rule under either scope nor for the last-user-text marker lookup; requests holding none are unaffected. `start(options)` SHALL additionally accept an optional `toolRoundScope` (#1140). Omitted or `"history"` is the rule above: a request is a tool round when its whole history holds no `tool` role message. `"turn"` SHALL make the rule per turn: a request is a tool round when no `tool` role message follows the last `user` role message, so a later turn of the same session — whose history real omp resends in full — starts with a tool round again and its `WORKBUDDY_WRITE`, `WORKBUDDY_TODO` and default bash calls are issued; once that turn's `tool` message is appended the request is the answering round. Any other value SHALL make `start()` reject without listening. The scope decides only which round a request is: the last-user-text marker lookup, the error marker's precedence, `WORKBUDDY_THINK` on the answering round, gates and the request record behave identically under both scopes, and for a history with a single `user` message the two scopes produce byte-identical frames. The option exists only on `start()`: an upstream launched as a separate process (`.github/scripts/ci-fake-upstream.sh`, `make smoke`, `make ui-walk`) always runs with the default scope, so those journeys are unaffected. The official-binary test helper SHALL pass this option through to `start()` and SHALL NOT place a history-trimming forwarder between omp and the upstream.
Because the model proxy relays the upstream SSE bytes unchanged and omp's openai-completions provider maps `delta.reasoning_content` to `thinking_start`/`thinking_delta`/`thinking_end` unconditionally on the response side (vendored `ai/src/providers/openai-completions.ts:1150-1175`, independent of the model entry's `reasoning` declaration), a `WORKBUDDY_THINK` turn through real omp yields thinking frames regardless of `MODEL_REASONING`; the fixture proves frame arrival through real omp, not the behaviour of any real model.

#### Scenario: 思考标记产生 reasoning 块
- **WHEN** a chat-completions request whose history holds a `tool` message and whose last user text contains `WORKBUDDY_THINK` is sent, with and without an armed gate for its `WORKBUDDY_UI_WALK:<uuid>` marker
- **THEN** the stream is the role chunk, three `reasoning_content` chunks concatenating to exactly `先读需求，再列要点，最后作答。`, then the unchanged content chunks, finish and `[DONE]`; with an armed gate the reasoning chunks and the first content prefix are sent before the hold and release sends the unchanged remainder exactly once

#### Scenario: 写入标记替换 bash 工具轮
- **WHEN** a request without `tool` history whose last user text contains `WORKBUDDY_WRITE` is sent, and separately the same request without the marker
- **THEN** the marked request streams one `write` tool call with the exact documented arguments and finish reason `tool_calls`, no bash call; the unmarked request streams the unchanged bash tool call

#### Scenario: 无标记请求字节不变
- **WHEN** requests without any of the three markers (and without any marker of「受控上游节奏与闸门停点标记」or「受控上游浏览器标记」) are sent for the tool round and the answering round, with and without a gate
- **THEN** the frames are identical to the pre-change fixture output (no `reasoning_content` key, bash tool call, fixed reply), and every existing gate scenario passes unchanged

#### Scenario: 任务清单标记替换 bash 工具轮
- **WHEN** a request without `tool` history whose last user text contains `WORKBUDDY_TODO` is sent; separately one whose last user text contains both `WORKBUDDY_WRITE` and `WORKBUDDY_TODO`; separately a `WORKBUDDY_TODO` request whose history already holds a `tool` message
- **THEN** the first streams exactly one tool call named `todo` whose reassembled arguments are exactly `{"op":"init","list":[{"phase":"走查","items":["整理需求","输出结论"]}]}` with finish reason `tool_calls` and no bash call; the second streams the unchanged `write` tool call and no `todo` call; the third streams the unchanged fixed reply with no tool call

#### Scenario: 按回合判定工具轮
- **WHEN** an instance started with `toolRoundScope:"turn"` receives a request whose history is `user → assistant(tool_calls) → tool → assistant → user` with last user text `WORKBUDDY_TODO`; then the same history with one `tool` message appended after the last user message; then the first history with last user text `WORKBUDDY_WRITE`, and with no marker
- **THEN** the first streams exactly one `todo` tool call with the documented arguments and finish reason `tool_calls`; the second streams the unchanged fixed reply with no tool call; the third and fourth stream the documented `write` call and the unchanged bash call
- **WHEN** the same first history is sent to an instance started without the option, and to one started with `toolRoundScope:"history"`
- **THEN** both stream the unchanged fixed reply with no tool call (the whole history holds a `tool` message)
- **WHEN** under `toolRoundScope:"turn"` the last user text carries the error marker; separately `WORKBUDDY_THINK` on an answering round, with and without an armed gate; separately a single-user-message history for the tool round and the answering round
- **THEN** each response is byte-identical to what the default scope produces for the same request (apart from the generated completion id and timestamp)
- **WHEN** `start({toolRoundScope:"session"})` is called
- **THEN** it rejects and no port is bound

## ADDED Requirements

### Requirement: 受控上游浏览器标记
The loopback fake-upstream (`server/test/support/fake-upstream.mjs`) SHALL additionally honour two browser markers found in the last user message text, selected by the same last-user-text lookup as the markers of「受控上游思考与写入标记」 and decided on the tool round only (the same round rule and `toolRoundScope` option as that requirement). `WORKBUDDY_BROWSER_OPEN:<url>` — `<url>` being the characters after the colon up to the next whitespace or the end of the text, nonempty — SHALL make the tool round issue one `write` tool call whose arguments are exactly the compact JSON `{"path":"xd://browser","content":<the compact JSON text of {"action":"open","url":<url>} as a JSON string>}` instead of the bash call. `WORKBUDDY_BROWSER_SHOT` SHALL make the tool round issue one `write` tool call whose arguments are exactly `{"path":"xd://browser","content":"{\"action\":\"run\",\"code\":\"return await tab.screenshot()\"}"}` instead of the bash call. The answering round is unchanged for both. Precedence: the error marker keeps its precedence; `WORKBUDDY_WRITE` and `WORKBUDDY_TODO` win over both browser markers (every request carrying either keeps the frames it receives today); `WORKBUDDY_BROWSER_OPEN:<url>` wins over `WORKBUDDY_BROWSER_SHOT`; `WORKBUDDY_BROWSER_OPEN:` with an empty `<url>` is not a marker. Both combine with `WORKBUDDY_THINK` and with a gate exactly as `WORKBUDDY_WRITE` does. Real omp v18.0.10 with `tools.xdev` (default) routes such a `write` to its `browser` tool (an exec-tier tool: approval under `always-ask` and `write`, none under `yolo`); what it then does is proven only by browser-runtime「CI browser-image job」 and by omp-runtime「宿主 overlay」's real-omp scenario, the fixture suite proves only the frames the upstream sends. When the session's model can take images, real omp v18.0.10 appends, after a run of `tool` result messages that carry images, one synthetic `user` message whose `content` is an array starting with the text part `Attached image(s) from tool result:` followed by `image_url` parts (vendored `ai/src/providers/openai-completions.ts:2338-2357`; the screenshot of `tab.screenshot()` is such an image). The fake upstream SHALL treat a `user` message that directly follows a `tool` message and whose `content` is an array whose first element is a text part exactly `Attached image(s) from tool result:` as part of the preceding tool results: it is skipped by the round rule under both scopes and by the last-user-text lookup, so the answering round of a screenshot turn stays the answering round and keeps the real user's markers. Each request record (「受控上游请求记录」) is unchanged and keeps no message content; how the CI job observes the image parts that reach the upstream is settled by browser-runtime「CI browser-image job」 (task 6.1). The fake omp is not changed for these markers (its module set is fixed by「假 omp 夹具模块划分」); server tests drive browser frames through the pure reducer with frame constants. The fixture test suite SHALL cover both markers, the precedence rules, the empty-url case and the unmarked default.

#### Scenario: 浏览器打开标记替换 bash 工具轮
- **WHEN** a request without `tool` history whose last user text is `看页面 WORKBUDDY_BROWSER_OPEN:file:///srv/ws/index.html 然后说结论` is sent
- **THEN** it streams exactly one tool call named `write` whose reassembled arguments parse to `{path:"xd://browser",content:"{\"action\":\"open\",\"url\":\"file:///srv/ws/index.html\"}"}` with finish reason `tool_calls` and no bash call

#### Scenario: 截图标记替换 bash 工具轮
- **WHEN** a request without `tool` history whose last user text contains `WORKBUDDY_BROWSER_SHOT` is sent; separately the same request under `toolRoundScope:"turn"` with a history `user → assistant(tool_calls) → tool → assistant → user` whose last user text carries the marker
- **THEN** both stream exactly one `write` tool call whose reassembled arguments are exactly `{"path":"xd://browser","content":"{\"action\":\"run\",\"code\":\"return await tab.screenshot()\"}"}` with finish reason `tool_calls`

#### Scenario: 浏览器标记的优先级
- **WHEN** the last user text contains `WORKBUDDY_WRITE` and `WORKBUDDY_BROWSER_OPEN:about:blank`; separately `WORKBUDDY_TODO` and `WORKBUDDY_BROWSER_SHOT`; separately `WORKBUDDY_BROWSER_SHOT` and `WORKBUDDY_BROWSER_OPEN:about:blank`; separately `WORKBUDDY_BROWSER_OPEN:` followed by a space; separately a browser marker on a request whose history already holds a `tool` message (default scope)
- **THEN** respectively: the unchanged `write` call of `WORKBUDDY_WRITE`; the unchanged `todo` call; the `open` call for `about:blank`; the unchanged bash call; the unchanged fixed reply with no tool call

#### Scenario: omp 补的图片附件消息不算用户回合
- **WHEN** an instance started with `toolRoundScope:"turn"` receives a history `user("截图 WORKBUDDY_BROWSER_SHOT") → assistant(tool_calls) → tool → user([{type:"text",text:"Attached image(s) from tool result:"},{type:"image_url",…}])`; separately, with the default scope, the history `user("截图 WORKBUDDY_BROWSER_SHOT WORKBUDDY_THINK") → assistant(tool_calls) → tool → user([{type:"text",text:"Attached image(s) from tool result:"},{type:"image_url",…}])`; separately, with the default scope, a history with no `tool` message anywhere whose last message is a `user` whose array content starts with that text
- **THEN** the first two stream the fixed reply with no tool call (answering round), and the second's reply carries, before its content, exactly the three `reasoning_content` chunks of `WORKBUDDY_THINK` concatenating to `先读需求，再列要点，最后作答。` (the lookup skipped the attachment message and found the real user's marker); the third is a tool round whose last user text is that message's text, so no browser marker applies and the default bash call is issued
