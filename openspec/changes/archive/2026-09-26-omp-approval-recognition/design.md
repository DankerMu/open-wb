# Design: omp-approval-recognition（#460）

父设计：D5「识别规则」与「风险：识别依赖 omp UI 文案」，D8「测试侧 argv 注入」。

- **Change surface**：新建 `server/src/sessions/omp/ui-requests.ts`，内容为识别谓词、工具名解析、两种 `extension_ui_response` 帧形状、`{id,title,tool}` 类型与 `"allow"|"deny"` 类型。`server/src/sessions/omp/process.ts` 改动三处：`OmpEvents` 加 `approval`（`:159-163`）；`#onFrame` 的 UI 分支（`:554-564`）；新增公开方法 `respondApproval`，以及 outstanding 集合随 writes 关闭而清空。owner 侧类型只在 `ui-requests.ts` 定义并导出，`process.ts` 不做 re-export；#462、#464 与新测试从 `./ui-requests.js` 用 `import type` 引入。
- **拆分判定**（行数推算见 proposal Impact）：不拆约 787/800，并未超限；拆后 `process.ts` 约 756、`ui-requests.ts` 约 50。选定拆分是对父 2.0「若 2.1a 后将超限」条件的有意偏离：约 13 行余量落在 biome 折行误差内，评审轮次的任何修补都可能触发 size-guard。是否接受由编排者裁定。
- **Must preserve**：`process.ts:548-553`：先处理 `ready`，再对**每个**帧（含审批请求）发 `frame`。审批的 `approval` 事件必须在其 `frame` 之后同步发出，因为 `runtime.ts:349-367` 把 frame 推进回合流，由 #455 归约器过滤；`process.ts:557`：`typeof id==="string" && !#writesClosed` 是整个 UI 分支的闸门。缺字符串 id 或 writes 已关时，不写帧也不上抛；回绝帧逐字为 `{type:"extension_ui_response",id,cancelled:true}`。写失败仍走 `.catch(#failIo)`（`:559-563`）；`:565-573` response 关联不变；`:63-78` argv 保持 `yolo`，归 #481；`runtime.ts` 零 diff。`#bindProcess`（`:337-347`）不订阅 `approval`，这正是「runtime 永不作答」的实现。`#closeStdin`（`:525-527`）直接 `stdin.end()`，绕过 `closeInput`，所以 `respondApproval` 必须自己判断 `stdin.writableEnded`/`destroyed`。
- **Must add/change**：谓词为 `method==="select"`、`Array.isArray(options)`、`options` 恰两项且依次为 `"Approve"`、`"Deny"`、`typeof title==="string"`、`title.startsWith("Allow tool: ")`；`tool` 取前缀后到首个 `\n` 为止的片段，去首尾空白；为空时记 `"unknown"`；`respondApproval(id, decision): void` 仅当 `id` 在 outstanding 中且 stdin 可写时，同步调用 `#write`，写恰一帧 `{type:"extension_ui_response",id,value:"Approve"|"Deny"}`，并先把 id 移出集合。未知 id、第二次调用、stdin 已 end、writes 已关、fatal 或已退出时，不写、不抛、不发 `error`。
- **Governing invariant**：审批请求的应答只由 owner 调 `respondApproval` 写出，每个 id 至多一帧；transport 与 runtime 在任何路径上都不替 owner 作答。
- **Sibling surfaces**：必然变红的既有测试**无**，允许编辑列表为空。已核对：`omp-rpc.test.ts:118-145`（`extension-ui` confirm 仍 cancelled）；`omp-rpc-lifecycle.test.ts:195-224`（死后 confirm 仍无写出）；`omp-process.test.ts:520-535` 与 `server-assembly.test.ts:658`（argv 仍 `yolo`）；`session-events.test.ts:105` 与 `session-events-stop.test.ts:145-166`（归约器未动）；`fake-omp-approval.test.ts`（只测 fake）。
- **下游消费者**：#464 订阅 `approval`，取 `id`→`request_id`、`tool`、`title`，CAS 提交后调 `respondApproval(id,"allow"|"deny")`，超时调 `"allow"`，进程已死时调用是无害的空操作；#473 要求 Deny 先于 `abort` 写出，依赖 `respondApproval` 在调用时同步发出 stdin 写；#474 依赖进程退出时不写帧；#462 的 pending 键即上抛的 `id`；#481 切 argv 后测试侧替换变为空操作。转接缺口见 proposal Open questions。
- **Seams under test**（新建测试文件只经公开 API，不访问私有字段）：真实子进程：用 `createRealFakeRuntime(scenario)`（`session-supervisor-helpers.ts:87-121`）的 `runtime.spawnImpl`，在测试内包装。包装做两件事：把 `--approval-mode` 后一项的 `yolo` 换为 `write`（替换容错，#481 后为空操作）；包 `child.stdin.write`，把写出的行记录为帧，先例 `omp-rpc.test.ts:199-205`。包装后的 spawnImpl 注入 `OmpProcessOpts.spawnImpl` 或 `SessionRuntimeOpts.spawnImpl`/`clock`。时钟用 `createClock`，辅助用 `createTokens`、`observeChild`、`collectUntilError`（`support/omp-runtime.ts`）。probe 的写法沿用 `fake-omp-frames.test.ts:77-79`：`probe:<pid>:<tmp>/probe.txt`，回合结束后发送，从 text_delta 取 `frames=`；合成帧：`startFakeProcess`（`support/omp-rpc.ts:283-300`）配合 `child.emitLine`；观察写出用 `child.stdin.on("data")`，先例 `omp-rpc-lifecycle.test.ts:203-211`。这就是 issue 所说的「直接喂给 transport 分类器」；观察窗：`harness.waitFrame(proc, pred, 300)` 以 `/timed out/` 拒绝；窗口结束后再检查 stdin 记录。
- **Required evidence**（R 表示先红后绿，G 表示守护、恒绿；T=`"Allow tool: bash\nCommand: echo workbuddy-smoke"`）：
  - E1 R：真实 fake `approval`（argv 记录含 `--approval-mode write`），发 prompt。预期 `approval` 恰一次，内容 `toEqual {id:"r1",title:T,tool:"bash"}`，且 r1 的 `frame` 先于 `approval`。之后 300ms 内无 `tool_execution_end`/`agent_end`，stdin 无任何 `extension_ui_response`。
  - E2 R：接 E1，调 `respondApproval("r1","allow")`。预期 stdin 的 UI 应答恰为 `[{type:"extension_ui_response",id:"r1",value:"Approve"}]`；`tool_execution_end{toolCallId:"tool-1"}` 无 `isError` 键；终止 `agent_end`。再调 `("r1","allow")`、`("r1","deny")`、`("nope","allow")`，均不抛、无写出。probe 的 `frames=` 恰为 `negotiate_protocol,get_state,prompt,extension_ui_response,prompt`。
  - E3 R：新实例 `respondApproval("r1","deny")`。预期恰一帧 `value:"Deny"`；`tool_execution_end{isError:true}`，其 `result.content[0].text` 为 `"Tool call denied by user: bash"`；终止 `agent_end`。第二次调 `"allow"` 无写出；probe 的 `frames=` 同 E2。
  - E4 R：FakeChild 发 `{type:"extension_ui_request",id:"u1",method:"select",title:"Allow tool: \nCommand: x",options:["Approve","Deny"]}`。预期 `approval` 为 `{id:"u1",title:<原文>,tool:"unknown"}`，300ms 内无写出。
  - E5 G：真实 fake `extension-ui`（argv 同为 write）。预期 stdin 含 `{type:"extension_ui_response",id:"ui-confirm-1",cancelled:true}`，回合终止，无 `approval`。
  - E6 G：FakeChild 依次发四帧，title 除 n3 外均为 `"Allow tool: bash"`：n1 `{method:"input"}`；n2 `{method:"select",options:["A","B"]}`；n3 `{method:"select",title:"Pick one",options:["Approve","Deny"]}`；n4 `{method:"select",options:["Deny","Approve"]}`。预期各自恰收到 `{type:"extension_ui_response",id:<nX>,cancelled:true}`，无 `approval`。另发一帧缺 `id` 的审批形状，预期无写出、无 `approval`。
  - E7 R：FakeChild 上报审批 u2 后调 `proc.closeInput()`，再调 `respondApproval("u2","allow")`。预期不抛、之后无写出、`errors` 无新增。另一实例上报后调 `child.exit(0)`，再调 respondApproval，预期同上。原生退出后才到达的审批形状请求，预期无 `approval`、无写出（此末项为 G）。
  - E8 R：SessionRuntime + `approval` + idleMs 600000，prompt 后手动 `next()` 迭代到 r1 帧。`clock.advance(120_000)` 后 300ms 内 stdin 无 UI 应答、无 `tool_execution_end`、`signals` 为 `[]`。之后 `await shutdown()`，预期迭代以 `AgentUnavailableError` 结束；子进程在 EOF 退出，`{code:0,signal:null}`、`stdinEnded`、`signals` 为 `[]`；全程无任何 `extension_ui_response`。
  - E9 R：同 E8，但 idleMs 为 100000，`clock.advance(100_000)` 触发 idle retire。预期子进程 `{code:0,signal:null}`、`signals` 为 `[]`、迭代失败、全程无 UI 应答。
  - E11 R（停止时不作答）：真实 fake `approval-then-abort`（#458 已交付，fake 零改动）。上报 r1 后调 `proc.request({type:"abort",id:"a1"})`，该请求保持 pending，因为 fake 在 selecting 态会延后 abort。预期 300ms 内无 `extension_ui_response`、无 `agent_end`。随后调 `respondApproval("r1","deny")`，预期依次出现 `tool_execution_end{isError:true}`、`message_end{stopReason:"aborted"}`、终止 `agent_end`，以及 `response{command:"abort",id:"a1"}`，该 abort 请求随之 resolve。probe 的 `frames=` 恰为 `negotiate_protocol,get_state,prompt,abort,extension_ui_response,prompt`。本项只证明 transport 在 abort 时不替 owner 作答；「Deny 先于 abort」的次序是 supervisor 的职责（#473）。
  - E10 G（源码守护）：
    - `grep -n extension_ui_response server/src/sessions/omp/{runtime,commands}.ts` 无匹配。有意不 grep ui-requests.ts：它只构造帧形状，不负责写出。
    - `grep -nE 'from "\./(process|runtime|commands)\.js"|stdin' server/src/sessions/omp/ui-requests.ts` 无匹配，作为「UI 请求分类模块边界」导入方向与不写 stdin 的证据；typecheck/knip 拦不住这里的循环导入。
    - size-guard 退出 0；knip 零新增。
  - E12 R（同步写出次序，#473 的 Deny 先于 abort 依赖它）：真实 fake `approval-then-abort`，上报 r1 后在同一 tick 内先调 `respondApproval("r1","deny")`，再调 `proc.request({type:"abort",id:"a1"})`，中间不 await。预期 stdin 记录中 `extension_ui_response` 排在 `abort` 之前；回合结束后 probe 的 `frames=` 恰为 `negotiate_protocol,get_state,prompt,extension_ui_response,abort,prompt`（写法同 `fake-omp-frames.test.ts:186-211`）。若实现把写出放进微任务或 await 之后，此项变红。
  - 写失败：过闸后 `respondApproval` 的写 promise 与回绝路径一样走 `.catch(#failIo)`（`process.ts:559-563`），不静默吞错，也不留下未处理的 rejection。
- **Non-goals**：见 proposal。
- **Review focus**：谓词精确（顺序、长度、前缀区分大小写，缺 id 不上抛）；`frame`→`approval` 次序与 writes 关闭闸门；`respondApproval` 在 retire（`stdin.end` 已调用、尚未退出）时不写、不触发 `#failIo`；`runtime.ts` 零 diff；owner 的 `approval` 监听器抛错时沿既有 `frame` 监听器路径进入 `#onLine` 的 catch（既有行为，本刀不改）。
