# Design: fake-omp-thinking-scenarios（#518）

父设计：design D12（场景定义与两个旋钮）、D5「取证」、Context「omp 事实」（edit/write `details` 形状，vendored `resource/oh-my-pi/packages/coding-agent/src/edit/renderer.ts:58-97`、`edit/diff.ts:54-56`、`tools/write.ts:314-324`）。行号为 origin/master。

- **Change surface**：`server/test/support/fake-omp.mjs` 的 `parseArgs`（:113-133）、场景常量与 `abortable` 判定（:24-57）、`handlePrompt`/`turns` 分派（:336-371）；新纯构建模块 `server/test/support/fake-omp-thinking.mjs`（必建，见行数预算）；新测试文件。
- **Must preserve**：
  - 既有全部场景（含 A 的八个）的出站帧逐字节不变；`--scenario`/`--resume`/`--session-dir`/`--approval-mode`/`--ready-delay-ms` 解析不变；新 argv 被其它场景完全忽略、与 `--scenario` 次序无关（`session-supervisor-helpers.ts` 在生产 argv 之后追加 `--scenario`；`uid-isolation.test.ts` `HANG_PATTERN` 只匹配 `scenario hang-term$`）。
  - 串行 queue 与 `inbound` 记录点（`onLine`）不变；probe 回报不变。
  - `fake-omp.test.ts` 及其它直接/间接使用 fake-omp 的测试零改动全绿；CI `uid-isolation` 绿。
- **Must add/change**：
  - 具名常量 `THINKING_PARTS = ["先读需求，", "再列要点，", "最后作答。"]` 与 `THINKING_TEXT = THINKING_PARTS.join("")`（= `先读需求，再列要点，最后作答。`，与 fake-upstream `THINK_PARTS` 同文本）。
  - thinking 帧形状（`message_update.assistantMessageEvent`）：`{type:"thinking_start", contentIndex:0, partial}`、`{type:"thinking_delta", contentIndex:0, delta, partial}`、`{type:"thinking_end", contentIndex:0, content, partial}`；正文 `text_delta` 用 `contentIndex:1`、沿用 fixture 既有正文 deltas（≥3 段）；`message_end{stopReason:"stop"}` 的 `message.content` 依次为 `{type:"thinking", thinking:<全部 delta 之和>}` 与文本块；`partial` 与 `message_update.message` 均为**固定小形状** `{role:"assistant", content:[]}`（同既有 `emitDeltas` 的 `message` 风格；不做累积快照——omp 的真实 partial 是累积的，但 `--thinking-repeat 2185` 下累积会使输出按平方增长到数百 MB，且宿主归约不读 message_update 的 partial/message）。
  - `--thinking-repeat <n>`：解析沿用既有 `argv[++i]` 写法（缺值即 `undefined`，按非法处理；紧随其后的 token 会被当作它的值，这是既有 argv 解析的统一行为，不另设例外）。只在 `thinking` 下校验，`/^[1-9][0-9]*$/` 且为安全整数；缺省 1；非法（`0`、负数、非整数、缺值）→ 模块顶层求值时（`queue = readyGate.then(...)` 之前）抛错退出（退出码非 0、stdout 无帧），同 `--ready-delay-ms` 先例。三段 delta 按原次序整体重复 n 次。两个旋钮只作用于 `thinking` 场景：`edit-write` 虽复用同一组 thinking 帧构建，但恒按 repeat=1、不挂起。
  - `--hold-after-thinking`：只在 `thinking` 下生效；`thinking_end` 之后置 `abortTurn = "pending"` 并返回（同 `holdTurn`），`handleAbort` 以既有 `emitAbortedEnd` 兑现（`message_end aborted`、终止 `agent_end`、`response{command:"abort"}` 回显 id，无 `text_delta`）；此后 prompt 再次跑同一 thinking 回合并挂起。abort 早于 `thinking_end` 被读到时：串行 queue 保证它在 prompt 处理（含 `thinking_end` 与置 pending）之后才被处理，因此 aborted 尾部紧随 `thinking_end`。
  - `edit-write`：`agent_start` → thinking 三帧组（同默认 thinking）→ 一个 `message_end{stopReason:"toolUse"}`，`content` 为两个 `toolCall`（`edit` 在前、`write` 在后），其前无正文 delta → edit：`tool_execution_start{toolCallId, toolName:"edit", args:{input:<固定 hashline input>}}`；真实写 `<cwd>/notes.md`（固定 post-edit 内容）；`tool_execution_end{toolCallId, toolName:"edit", result:{content:[{type:"text",text:…}], details:{path:"<cwd>/notes.md", diff:"+1|a\n+2|b\n-3|c\n 4|d"}}}` → write：`tool_execution_start{…, toolName:"write", args:{path:"out/report.html", content:<固定 html>}}`；`mkdir -p <cwd>/out` 并真实写 `report.html`；`tool_execution_end{…, result:{content:[…], details:{resolvedPath:"<cwd>/out/report.html"}}}`（无 `diff` 键）→ ≥2 段固定回答 `text_delta` → `message_end{stop}` → 终止 `agent_end`。`<cwd>` 为该回合时 `process.cwd()`；写失败时该调用的 end 帧 `isError: true` 且无 `details`，回合仍完成。任何 `--approval-mode` 下无 `extension_ui_request`。
  - 行数预算与模块划分（必做）：纯构建部分（常量、thinking 事件与 message_end thinking 块构建、`edit-write` 固定内容与 `details` 构建、repeat 取值校验）放入新模块 `fake-omp-thinking.mjs`：只导出被主文件使用的名字、只导入 `node:` 内建模块、不导入 `fake-omp.mjs`/`fake-omp-proxy.mjs`、无模块级可变状态、不 emit、不写文件；主文件保留 argv、状态机、emit、真实写文件与分派。改后 `fake-omp.mjs` ≤ 720 行（为 #552 的 `slash` 与 `--branch-entry` 留 ≥80 行）。对应 spec MODIFIED「假 omp 夹具模块划分」（三个模块）。
- **Governing invariant**：新场景与旋钮只在各自 `--scenario` 下改变出站帧；`thinking_end.content` 与 `message_end` thinking 块恒等于该回合全部 `thinking_delta` 的拼接；`edit-write` 每个 `tool_execution_end` 发出时它报告的文件已真实存在于 `<cwd>`。
- **Sibling surfaces**：
  - 解析：`parseArgs`（沿用 `argv[++i]`）、`parseReadyDelay` 同形校验。
  - 状态机：`abortable`/`ABORT_SCENARIOS` 判定、`abortTurn`、`handleAbort`、`emitAbortedEnd`（`thinking` 仅在 `--hold-after-thinking` 下可 abort；无旋钮时同 `normal`：`dispatch` 对不可 abort 场景回 `response{command:"abort", success:false, error:"unsupported"}`，不得为此把 `thinking` 无条件放进可 abort 集合）。
  - 消费者：3.3 #519（`--thinking-repeat 2185` 越 32768、`--hold-after-thinking` 下 stop）、3.4 #522 与 4.3b #525（`edit-write` 的 details 与真实文件、`<cwd>` 以 spawn 工作目录决定）、10.1 #552（在同文件继续加场景）；宿主经 `session-supervisor-helpers.ts:95-103` `spawnImpl` 追加 `--scenario` 并选工作目录。
  - CI：`uid-isolation` job 直接执行本 fixture（异 uid），新代码不得引入对 uid/HOME 的新依赖。
- **Seams under test**：真实子进程，经 `fake-omp-helpers.ts` 的 `startFake`（含 `cwd` 选项，#520 已交付）/`startPromptedSession`，只看 stdout 帧与磁盘文件。
- **Required evidence**（新文件 `server/test/fake-omp-metadata-scenarios.test.ts`；每条新断言先在 fixture 未改时跑红）：
  1. `thinking`，默认 argv（yolo）与 `--approval-mode write` 各一次：ack、`agent_start` 后恰为 `thinking_start`、三段 `thinking_delta`（delta 依次为三段常量）、`thinking_end.content === "先读需求，再列要点，最后作答。"`、≥3 段 `text_delta`、`message_end{stop}` 且 `message.content[0]` 为 `{type:"thinking", thinking:"先读需求，再列要点，最后作答。"}`、`content[1].type === "text"`、终止 `agent_end`；全程无 `tool_execution_*` 与 `extension_ui_request`；同进程第二次 prompt 帧类型序列相同。
  2. `--thinking-repeat 3` → 恰九段 `thinking_delta` 按三段常量循环；`--thinking-repeat 2185` → 恰 6555 段，`thinking_end.content` 与 message_end thinking 块均为常量重复 2185 次（`[...s].length === 32775`），其后正文、`message_end{stop}`、`agent_end` 照常；该次运行 stdout 总字节 < 4 MiB（证明 partial/message 未累积）。
  3. 非法 repeat：`0`、`-1`、`1.5`、`abc`、argv 末尾缺值 → 进程非 0 退出且 stdout 无任何帧。缺值用例的构造：不传 `startFake` 的 `scenario` 选项，`extraArgs` 为 `["--scenario", "thinking", "--thinking-repeat"]`（旋钮在末尾；否则 `startFake` 追加的 `--scenario` 会被当作 repeat 的值）。旋钮被其它场景忽略：(a) `edit-write --thinking-repeat 3 --hold-after-thinking` → 恰三段 `thinking_delta`、不挂起、两组工具帧与完成帧照常（帧类型序列同证据 5）；(b) `normal` 带 `--thinking-repeat 0 --hold-after-thinking` → 不因 repeat 为 0 启动失败，帧类型序列与不带旋钮时逐帧相同。
  4. `--hold-after-thinking`：`thinking_end` 后在 ≥200 ms 观察窗内无帧；发 `abort{id:X}` → 依次 `message_end{stopReason:"aborted"}`、终止 `agent_end`、`response{id:X, command:"abort"}`，其间无 `text_delta`；第二次 prompt 再次到 `thinking_end` 并挂起；同一写入中 `prompt` 紧跟 `abort` → aborted 尾部紧随 `thinking_end`（中间无其它帧）；两旋钮都不给 → 与证据 1 的帧类型序列逐帧相同。
  5. `edit-write`（`--approval-mode write`，`startFake({cwd: <dir>})`，`<dir>` 取 realpath）：帧类型序列恰为 ack、`agent_start`、thinking 三帧组、`message_end{toolUse}`（其前无 `text_delta`）、edit start（`args` 恰 `{input:…}`，无 `path` 键）、edit end（`result.details` 深等 `{path:"<dir>/notes.md", diff:"+1|a\n+2|b\n-3|c\n 4|d"}`）、write start（`args.path === "out/report.html"`）、write end（`result.details` 深等 `{resolvedPath:"<dir>/out/report.html"}`，无 `diff` 键）、≥2 段 `text_delta`、`message_end{stop}`、终止 `agent_end`；每个 end 帧被读到时对应文件已存在（在收到该帧的回调中同步 `existsSync` 断言）且内容等于 fixture 文档化的固定内容；yolo 下同样无 `extension_ui_request`。
  6. 同场景在另一目录 `<other>` 运行 → 全部报告路径以 `<other>` 为根，diff 与帧类型序列不变。
  7. 模块划分：`fake-omp-thinking.mjs` 的 import 只含 `node:` 说明符（`grep '^import' ` 核对）、不含 `fake-omp.mjs`/`fake-omp-proxy.mjs`；`fake-omp.mjs` 以 `./fake-omp-thinking.mjs` 静态导入；`node --check` 三文件通过；新模块无 shebang、无模块级 `let`；`wc -l` 三文件均 ≤800 且 `fake-omp.mjs` ≤720（写入 PR）。
- **Non-goals**：见 proposal。
- **Review focus**：帧形状与次序逐帧对照 spec；`edit-write` 工具前无正文、end 帧前真实落盘；非法 repeat 在任何帧前失败；旋钮对其它场景无影响；既有场景零变化；行数预算与新模块的纯度。
