# chat-sessions Spec Delta

## MODIFIED Requirements

### Requirement: 项目配置文件列表
`GET /api/project-config` (`server/src/sessions/rest-project-config.ts`, registered next to `GET /api/commands`) SHALL follow the same request rules as `GET /api/commands` (cookie guard first, no-store, no body, at most the single `workspaceId` key, 400 and 404 as there) and return200 `{files:[{path,kind,depth}]}`: the project configuration files that exist at the locations omp reads for the cwd a session of that account would run in. It is a list of files present, not of files in effect: omp keeps one instruction file per directory level by provider priority (verified by run on v18.0.10 and re-verified on v18.12.3: with `AGENTS.md` and `.claude/CLAUDE.md` in one directory only the latter reaches the system prompt), and the host does not reproduce that. The *walk* is the directory list of `listProjectSkills` (the resolved cwd upwards to the `.git` level or `sandboxRoot`; empty, and the response `{files:[]}`, when the resolved cwd is not inside the resolved `sandboxRoot`), and the agents lookup runs on the resolved chain from the cwd up to `sandboxRoot` without stopping at `.git` (it is not bounded by the walk); `depth` is 0 for the cwd and grows by one per level; `path` is relative to that directory with `/` separators. Since #1563 the host plants a `.git` marker in every session cwd (workspace root at creation and before every spawn, owner root before every spawn; omp-runtime「会话工作目录的仓库根标记」), so for a workspace created by this host the walk is the workspace root alone and every listed `depth` of the walk rows is 0 (the agents row may still list depth ≥ 1); the walk rule is kept as stated so a cwd without the marker (a workspace whose marker was removed and not yet re-asserted) is still described truthfully. The location table is fixed and belongs to this requirement (every row that existed before #1563 was verified by run on v18.0.10 and re-verified on v18.12.3; the rows #1563 adds are read from the v18.12.3 sources and are verified by the row test before the route ships, at depth 0 and, without a `.git` in between, at depth 1): in every directory of the walk, `AGENTS.md`, `.agents/AGENTS.md` and `.agent/AGENTS.md` (`kind:"instructions"`; #1563: v18.12.3 takes the singular `.agent` directory as a second candidate at every level, by code reading) and `.agents/SYSTEM.md`, `.agents/SYSTEM_TEMPLATE.md`, `.agent/SYSTEM.md`, `.agent/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 walks them from the cwd up to the repo root, by code reading); in the cwd only, `.claude/CLAUDE.md` (`instructions`) and `.claude/SYSTEM.md`, `.claude/SYSTEM_TEMPLATE.md`, `.codex/SYSTEM.md`, `.codex/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 reads these two directories in the cwd only, by code reading) and, when `.gemini` is a real directory, `.gemini/system.md` and `.gemini/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1570: v18.12.3 reads these in the cwd only, `discovery/gemini.ts:320-344`, found by the group-6 real run — the literal file name is lower-case `system.md`); in the nearest directory of the walk whose `.omp` holds at least one entry, `.omp/AGENTS.md` and `.omp/RULES.md` (`instructions`) and `.omp/SYSTEM.md` and `.omp/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 takes both from that nearest non-empty `.omp`, no longer from the cwd only, and `SYSTEM_TEMPLATE.md` — new in v18.12.x — replaces the whole system prompt); and the `*.md` files directly inside `.omp/agents` of the nearest directory, from the cwd up to `sandboxRoot` without stopping at `.git`, in which `.omp/agents` is a directory (`kind:"agent"`: of the regular `*.md` files, at most the first 64 in code-point order; `depth` is that directory's distance from the cwd; omp v18.12.3's `task` tool still looks agent definitions up with `findAllNearestProjectConfigDirs`, which walks to the filesystem root, so the host's `.git` marker does not bound this row — re-verified on v18.12.3 by the row test, which keeps its "found past a .git level" case). Every directory between an inspected directory — one of the walk, or one of the agents lookup — and a listed file (`.omp`, `.omp/agents`, `.claude`, `.codex`, `.gemini`, `.agents`, `.agent`) SHALL be a real directory by `lstat`, so nothing outside an inspected directory is ever read. `.omp` and `.omp/agents` are enumerated through a directory handle reading at most 4096 entries. A `.omp` or `.omp/agents` that is a link, or holds more than 4096 entries, ends the respective nearest-directory search at that level with nothing listed for those rows (omp follows the link and stops there too); only a missing or unreadable one lets the search continue upwards (within the walk for the `.omp` rows; up to `sandboxRoot` for the agents row). Every table row SHALL be backed by a real-binary test that places only that file — once at depth 0 and once at depth 1, with no `.git` in between — and finds its marker in `get_state.systemPrompt` (agents: in the task tool's agent list; for a cwd-only row: its absence at depth 1), plus one case with the host's `.git` marker in the cwd in which no depth-1 row of the walk is read while the agents row is still found at depth 1; where the pinned omp disagrees with a row — it does not read the location, reads it only in the cwd, or reads it at more levels than the row says — this requirement SHALL be changed to match before the route ships. A file is listed only when `lstat` says regular file (a symlink is not followed and not listed); the host reads no content, and any filesystem error for a location lists nothing for it. Entries are ordered by `depth`, then by `path` in code-point order. The route SHALL NOT touch any session or process.

- **WHEN** the workspace holds none of the files, the id belongs to another account, or the request carries a body
- **THEN** the responses are 200 `{files:[]}`, 404 not_found and 400 bad_request; a workspace of the caller whose root is unusable also answers 200 `{files:[]}`

### Requirement: Slash 命令白名单与命令目录
`server/src/sessions/slash-commands.ts` SHALL export the builtin whitelist `BUILTIN_COMMANDS` in this fixed order: `compact` (label `整理上下文`, description `压缩较长对话的上下文，保留要点`, hint `可选：想保留的重点`) and `todo` (label `任务清单`, description `查看或修改助手的任务清单`, hint `可选：append <任务>`); no other omp builtin SHALL be whitelisted by this change (`retry` is deliberately excluded: turn-control's regenerate already covers it and its `agentInvoked:true` receipt would add a second local-command completion mode). It SHALL export `listSkills(agentDir)`: synchronously enumerate the entries of `<agentDir>/skills` whose name does not start with `.`, keep at most the first 256 of them in code-point order of their SKILL.md path (further entries are ignored without any filesystem access), and read `<entry>/SKILL.md` for each kept entry without branching on the entry type (a plain file simply fails the read). A symlink is followed only inside the skills directory — a deliberate host restriction; omp itself follows any symlinked directory (`discovery/helpers.ts:428-431`): the host resolves the real path of `<entry>/SKILL.md` and skips the entry unless that real path lies inside the real path of `<agentDir>/skills` — both real paths SHALL come from the kernel (`realpathSync.native`), not from Node's JS `realpathSync`, which stops resolving at a FIFO or socket and folds `..` lexically, so its result can name a different file than the one the kernel opens; and both SHALL be kept as the raw bytes the kernel returned (`{ encoding: "buffer" }`): the containment check compares bytes and the open is given the same bytes, because decoding a path to a string replaces every ill-formed UTF-8 sequence with U+FFFD and re-encoding it names a different path — then opens the resolved path with `O_NOFOLLOW`, so file content outside `skills/` never reaches the catalogue through a link; the read SHALL be bounded and non-blocking as defence in depth — under omp-runtime「OMP_STATE_DIR 托管布局」 the directory is no longer writable by the omp uid, but whatever an operator installs there is still read by the server process: SKILL.md is opened with `O_NONBLOCK | O_NOCTTY` (a terminal device placed there cannot become the server's controlling terminal), and only a regular file of at most 262144 bytes is read — a FIFO, device, directory or larger file is skipped like an unreadable one; normalise `\r\n?` to `\n` and read only the leading frontmatter block — the content starts with `---` and the block ends before the first later line starting with `---`; an unclosed block is no frontmatter — taking, without a YAML library, the top-level (unindented) `key: value` lines for `name`, `description` and `enabled`: a value is trimmed and loses one pair of surrounding quotes; a value that is exactly a block-scalar indicator (`>` or `|`, optionally followed by `+` or `-`) takes the following more-indented lines, each trimmed, joined with one U+0020 (`>`) or `\n` (`|`); `name` defaults to the entry name when missing or empty. An entry is skipped when SKILL.md is missing or unreadable, when `description` is missing or empty, or when the unquoted `enabled` value is `false` (omp's own drop rules for a user-level skill: `discovery/builtin.ts:295-300`, `discovery/helpers.ts:397-403`), and — a host rule; omp does not validate names — when `name` does not match `^[^\s/]+$` (such a name cannot be selected through `/skill:<name>`, whose name ends at the first U+0020). Entries sharing a `name` collapse to the one whose SKILL.md path is smallest in code-point order (omp is first-wins over the same order, `extensibility/skills.ts:220-221`). Any failure to enumerate `skills` (absent, not a directory, unreadable) yields `[]`, as omp's scan does (`discovery/helpers.ts:384-392`); the result is sorted by `name` in code-point order and is recomputed on every call (no cache). It SHALL export `listProjectSkills(cwd, sandboxRoot)` (#773): the project skills of a session cwd, read from `<D>/.omp/skills` for the directories `D` = `cwd`, its parent, and so on, stopping after the first `D` where `lstat(<D>/.git)` succeeds (that `D` is still scanned — omp's `repoRoot`, `capability/fs.ts:84-95`, `discovery/builtin.ts:284`; the host does not enumerate `D`) or after `sandboxRoot`, whichever comes first. The walk runs on kernel real paths: `cwd` and `sandboxRoot` are first resolved (`realpathSync.native`, raw bytes), and a resolved `cwd` that is neither the resolved `sandboxRoot` nor below it (byte prefix followed by `/`) yields `[]` — the sandbox root is `2770` and the owner root is not checked for links by the session cwd resolver, so the omp uid can put a symlink where a cwd is expected; every `D` is a parent of the resolved `cwd`, hence a real directory inside the sandbox. Each `<D>/.omp/skills` is read by exactly the rules of `listSkills` above (hidden entries, the 256-entry cap, kernel real paths as raw bytes with the containment boundary being that `skills` directory, `O_NOFOLLOW | O_NONBLOCK | O_NOCTTY`, regular file of at most 262144 bytes, the frontmatter reader, the skip rules and the name rule), with three additions because the directory is writable by the omp uid: a `SKILL.md` whose `fstat` link count is not 1 is skipped (a hard link to a file the server can read would otherwise echo that file's frontmatter); the kernel real path of `<D>/.omp/skills` SHALL equal, byte for byte, the kernel real path of `D` followed by `/.omp/skills` — so neither `.omp` nor `skills` is a link and the containment boundary cannot be moved outside `D` — otherwise that `D` yields nothing; and the directory is enumerated through a directory handle reading at most 4096 entries — one holding more yields nothing for that `D` (the 256-entry cap applies after the sort, as for the platform directory); a `description` longer than 200 code points is cut to its first 200. A name found in a nearer `D` hides the same name in a farther one (omp v18.0.10, verified by run: nearest project skill wins); the result is sorted by `name` in code-point order, never throws (any failure for one `D` yields nothing for that `D`) and is recomputed on every call. Only `.omp/skills` is read: omp v18.0.10 also loads project skills from `.claude`, `.codex`, `.agents`, `.agent`, `.opencode` and `.github` under the cwd (the first, third and fourth also under its ancestors), from the same four directories under the managed `HOME`, and from ancestors above `sandboxRoot` when no `.git` stops it; none of these is listed, and in the two precedence pairs run against the real binary (`.omp` project vs `.claude`/`.codex`/`.agents` project of the same name; platform vs `.claude` project of the same name) the `.omp` or platform skill won, so a listed name runs the listed skill — unless a nearer `.omp/skills` holds a skill of that name which the host's read rules skipped and omp loaded (omp follows links and has no caps): then the farther or platform entry is listed with its own `source` and `overrides` while omp runs the nearer one (accepted residual). It SHALL export `sessionSkills(agentDir, cwd, sandboxRoot)`: the platform skills of `listSkills(agentDir)` and the project skills of `listProjectSkills(cwd, sandboxRoot)` as `{name, description, source: "skill" | "project", overrides}` — a project skill replaces the platform skill of the same name (omp runs the project one) and carries `overrides: true`; every other entry carries `overrides: false`; platform entries first, then project entries, each group in name order. It SHALL export `classifyPrompt(text, skills)` for already-trimmed text: text not starting with `/` → `{kind:"text"}`; otherwise the name is the characters after `/` up to the first whitespace or `:`; a name equal to a `BUILTIN_COMMANDS` name → `{kind:"builtin", name}`, except `todo` with the subcommand `import` or `export`, which is `{kind:"text"}`: the subcommand is taken as omp takes it (`slash-commands/helpers/parse.ts:22-36,58-64`) — the text after the name's terminating whitespace or `:` is trimmed, cut at its first whitespace and lower-cased — because omp resolves the path argument of these two subcommands with `resolveToCwd`, which honours absolute paths, `~` and `..` (`tools/path-utils.ts:565-579`), reads or writes that file with no tool frame, no step row and no `files.changed`, and echoes parse errors of an imported file as the reply; the host does not parse or validate the path, it simply does not whitelist the two subcommands, so the text reaches the model escaped like any other non-whitelisted `/` text; text starting with `/skill:` whose skill name — the characters up to the first U+0020, exactly omp's split (`extensibility/skills.ts:456-459`), so a newline is part of the name — equals the `name` of a skill in `skills` (the platform and project skills of the session's cwd: every caller passes `sessionSkills` of that session) → `{kind:"skill", name}`; every other `/`-prefixed text (different case, non-whitelisted builtin, unknown skill, a skill name broken by a newline, pasted paths) → `{kind:"text"}`. It SHALL export `toWireText(text, skills)`: `builtin`/`skill` → the text unchanged; `text` starting with `/` → one U+0020 followed by the text; anything else unchanged. Arguments of whitelisted commands (`/todo append 买菜`, `/compact:focus 保留结论`, `/skill:<name> 写周报`) SHALL pass through unchanged. A `/skill:<installed>` token in the middle of a prompt is `text` for the host and is left to omp (which executes the skill exactly as in its TUI). The host gives no guarantee that a `/skill:<name>` it classifies `text` is not run: omp's skill dispatch `trimStart()`s the escape space, so a skill omp loaded and the host does not list — one from another provider directory, from the managed `HOME`, from above `sandboxRoot`, or one the host's own read rules skipped — still runs (accepted residual, ADR-0012). The prompt route, regenerate and fork SHALL each classify with `sessionSkills` computed from the session's own cwd (the owner root for an unbound session, the workspace root for a bound one; a cwd that cannot be resolved — `rootOf` throws or answers a path that is not a directory — contributes no project skill), read only for `/`-prefixed text. One more accepted mismatch, in the other direction: omp loads its skills when the process starts (verified by run on v18.0.10: a `SKILL.md` created afterwards is absent from `get_available_commands` and its `/skill:<name>` prompt is sent to the model as an ordinary message), while the host recomputes on every call; until that session's process is next started, the host classifies such a prompt `skill`, sends it unescaped, and regenerate or fork anchored on it answer 400.
`GET /api/commands` (`server/src/sessions/rest-commands.ts`, registered by registerSessions next to the session routes) SHALL require the cookie guard (401 with no-store otherwise, decided before the body/query check: an unauthenticated request carrying either is 401), carry Cache-Control:no-store, accept no body and no query string other than exactly one `workspaceId` key with a single value (an authenticated request with a body, any other key, a repeated key or an empty value SHALL return400 bad_request; a `workspaceId` that is malformed, unknown or not the caller's SHALL return404 not_found through the owner-scoped workspace `rootOf`; a workspace of the caller whose root is unusable — `rootOf` throws, or the path is not a directory — is not an error: the response is 200 with the builtins and the platform skills only) and return200 `{commands:[{name,label,description,hint,source,overrides}]}` for the cwd a session of that account would run in — the workspace root with `workspaceId`, the owner root without: the two builtins first in whitelist order with `name` equal to the builtin name and `source:"builtin"`, then every entry of `sessionSkills` in its order with `name` `skill:<skill name>`, `label` the skill name, `description` the description as returned (possibly English), `hint` `可选参数`, `source` `"skill"` (platform) or `"project"` and `overrides` as returned; builtins carry `overrides:false`; `hint` SHALL be a string or null; the route SHALL NOT be a content-parser owner and SHALL NOT touch any session or process (the workspace lookup is its only SQLite read).
**Branch alignment** (used by regenerate and fork instead of a plain equality on stored content). The *wire candidates* of a stored user content `c` are `c` itself and, when `c` starts with `/`, one U+0020 followed by `c` (the escaped form; a message persisted before the prompt route escaped was sent verbatim). For a user message stored with a non-NULL `attachments` list the candidates are those same strings each followed by the attachment suffix rebuilt from that list's paths — for an attachment-only message, whose stored content is the empty string, that is the single candidate consisting of the suffix alone — (message-attachments「交给 omp 的附件后缀」; the suffix function lives beside `toWireText` and is the one the prompt route uses); a message without attachments keeps the candidates above. Candidates depend only on the stored row (its text and its attachments) — alignment never classifies history by the current skill set, so installing or removing a skill (platform or project) later does not move it. Regenerate SHALL return400 bad_request, with no spawn, no frame and no row change and after the 409 busy check, when `classifyPrompt` of the stored last user message yields `builtin` or `skill` (such a turn left no omp `user` entry); otherwise it SHALL require the text of the last branch entry to be a wire candidate of the stored last user message (any other outcome, including an empty list → 502 agent_unavailable with no row change, as before; only this pair is compared, earlier entries are not read). Fork SHALL return400 the same way when the chosen `messageId`'s content classifies `builtin` or `skill`; otherwise, with the source's stored `user` messages U1…Un in id order and the branch entries E1…Em in list order, it SHALL align them first-fit from the front: Ui is aligned to the current Ej when `Ej.text` is a wire candidate of `Ui.content`, consuming both; a Ui that does not match the current Ej is skipped and consumes no entry (it left no omp `user` entry: a whitelisted builtin, a skill invocation — leading or mid-prompt, which omp stores as a `custom` message — or any other local-only turn); an entry whose `entryId` or `text` is not a string matches nothing. Fork SHALL use the entry aligned to the chosen message (no aligned entry → 502 agent_unavailable and no new session row, as before). Fork's `draft` SHALL be the stored content of the chosen user message (identical to the branch text for every message that does not start with `/`; never carries the escape space).
