# chat-sessions Spec Delta

## MODIFIED Requirements

### Requirement: 项目配置文件列表
`GET /api/project-config` (`server/src/sessions/rest-project-config.ts`, registered next to `GET /api/commands`) SHALL follow the same request rules as `GET /api/commands` (cookie guard first, no-store, no body, at most the single `workspaceId` key, 400 and 404 as there) and return200 `{files:[{path,kind,depth}]}`: the project configuration files that exist at the locations omp reads for the cwd a session of that account would run in. It is a list of files present, not of files in effect: omp keeps one instruction file per directory level by provider priority (verified by run on v18.0.10 and re-verified on v18.12.3: with `AGENTS.md` and `.claude/CLAUDE.md` in one directory only the latter reaches the system prompt), and the host does not reproduce that. The *walk* is the directory list of `listProjectSkills` (the resolved cwd upwards to the `.git` level or `sandboxRoot`; empty, and the response `{files:[]}`, when the resolved cwd is not inside the resolved `sandboxRoot`), and the agents lookup runs on the resolved chain from the cwd up to `sandboxRoot` without stopping at `.git` (it is not bounded by the walk); `depth` is 0 for the cwd and grows by one per level; `path` is relative to that directory with `/` separators. Since #1563 the host plants a `.git` marker in every session cwd (workspace root at creation and before every spawn, owner root before every spawn; omp-runtime「会话工作目录的仓库根标记」), so for a workspace created by this host the walk is the workspace root alone and every listed `depth` of the walk rows is 0 (the agents row may still list depth ≥ 1); the walk rule is kept as stated so a cwd without the marker (a workspace whose marker was removed and not yet re-asserted) is still described truthfully. The location table is fixed and belongs to this requirement (every row that existed before #1563 was verified by run on v18.0.10 and re-verified on v18.12.3; the rows #1563 adds are read from the v18.12.3 sources and are verified by the row test before the route ships, at depth 0 and, without a `.git` in between, at depth 1): in every directory of the walk, `AGENTS.md`, `.agents/AGENTS.md` and `.agent/AGENTS.md` (`kind:"instructions"`; #1563: v18.12.3 takes the singular `.agent` directory as a second candidate at every level, by code reading) and `.agents/SYSTEM.md`, `.agents/SYSTEM_TEMPLATE.md`, `.agent/SYSTEM.md`, `.agent/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 walks them from the cwd up to the repo root, by code reading); in the cwd only, `.claude/CLAUDE.md` (`instructions`) and `.claude/SYSTEM.md`, `.claude/SYSTEM_TEMPLATE.md`, `.codex/SYSTEM.md`, `.codex/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 reads these two directories in the cwd only, by code reading); in the nearest directory of the walk whose `.omp` holds at least one entry, `.omp/AGENTS.md` and `.omp/RULES.md` (`instructions`) and `.omp/SYSTEM.md` and `.omp/SYSTEM_TEMPLATE.md` (`kind:"system"`; #1563: v18.12.3 takes both from that nearest non-empty `.omp`, no longer from the cwd only, and `SYSTEM_TEMPLATE.md` — new in v18.12.x — replaces the whole system prompt); and the `*.md` files directly inside `.omp/agents` of the nearest directory, from the cwd up to `sandboxRoot` without stopping at `.git`, in which `.omp/agents` is a directory (`kind:"agent"`: of the regular `*.md` files, at most the first 64 in code-point order; `depth` is that directory's distance from the cwd; omp v18.12.3's `task` tool still looks agent definitions up with `findAllNearestProjectConfigDirs`, which walks to the filesystem root, so the host's `.git` marker does not bound this row — re-verified on v18.12.3 by the row test, which keeps its "found past a .git level" case). Every directory between an inspected directory — one of the walk, or one of the agents lookup — and a listed file (`.omp`, `.omp/agents`, `.claude`, `.codex`, `.agents`, `.agent`) SHALL be a real directory by `lstat`, so nothing outside an inspected directory is ever read. `.omp` and `.omp/agents` are enumerated through a directory handle reading at most 4096 entries. A `.omp` or `.omp/agents` that is a link, or holds more than 4096 entries, ends the respective nearest-directory search at that level with nothing listed for those rows (omp follows the link and stops there too); only a missing or unreadable one lets the search continue upwards (within the walk for the `.omp` rows; up to `sandboxRoot` for the agents row). Every table row SHALL be backed by a real-binary test that places only that file — once at depth 0 and once at depth 1, with no `.git` in between — and finds its marker in `get_state.systemPrompt` (agents: in the task tool's agent list; for a cwd-only row: its absence at depth 1), plus one case with the host's `.git` marker in the cwd in which no depth-1 row of the walk is read while the agents row is still found at depth 1; where the pinned omp disagrees with a row — it does not read the location, reads it only in the cwd, or reads it at more levels than the row says — this requirement SHALL be changed to match before the route ships. A file is listed only when `lstat` says regular file (a symlink is not followed and not listed); the host reads no content, and any filesystem error for a location lists nothing for it. Entries are ordered by `depth`, then by `path` in code-point order. The route SHALL NOT touch any session or process.

#### Scenario: Files present at the read locations
- **WHEN** the owner GETs `/api/project-config?workspaceId=<own workspace>` whose root holds `AGENTS.md`, `.omp/RULES.md`, `.omp/SYSTEM_TEMPLATE.md`, `.omp/agents/reviewer.md`, `.claude/CLAUDE.md`, `.claude/SYSTEM.md`, `GEMINI.md` and `.omp/SYSTEM.md` → a symlink, while the owner root holds `AGENTS.md`, `.claude/CLAUDE.md`, `.omp/RULES.md`, `.omp/SYSTEM.md` and `.omp/agents/far.md`; the workspace was created by this host (its root holds the `.git` marker)
- **THEN** the response lists, in this order, depth 0 `.claude/CLAUDE.md`, `.claude/SYSTEM.md` (`system`), `.omp/RULES.md`, `.omp/SYSTEM_TEMPLATE.md` (`system`), `.omp/agents/reviewer.md` (`agent`), `AGENTS.md`; nothing of the owner root is listed (the walk ends at the marker, and the agents lookup found the nearer `.omp/agents`); `GEMINI.md` and the symlink are absent
- **WHEN** the same layout but the workspace root's `.git` marker has been removed (not yet re-asserted by a spawn)
- **THEN** the response additionally lists depth 1 `AGENTS.md` only (the nearer `.omp` wins for its rows, `.claude/CLAUDE.md` is cwd-only, and the agents lookup found the workspace's own `.omp/agents`)
- **WHEN** the marker is absent, the workspace root's `.omp` holds only `skills/x/SKILL.md` while the owner root holds `.omp/RULES.md`, `.omp/SYSTEM.md` and `.omp/agents/far.md`, and separately the workspace root has no `.omp` at all; and separately the marker is present, the workspace root has no `.omp` and the owner root holds `.omp/RULES.md`, `.omp/SYSTEM.md` and `.omp/agents/far.md`
- **THEN** the first lists depth 1 `.omp/agents/far.md` only (the nearer non-empty `.omp` has no `RULES.md` or `SYSTEM.md`, and `agents` is looked up on its own); the second lists depth 1 `.omp/RULES.md`, `.omp/SYSTEM.md` (`system`) and `.omp/agents/far.md`; the third lists depth 1 `.omp/agents/far.md` only (the marker bounds the walk, not the agents lookup)
- **WHEN** the marker is absent and the workspace root's `.omp` is a symlink to a directory outside the sandbox holding `RULES.md` and `agents/a.md`, and separately only `.omp/agents` is such a symlink, while in both cases the owner root holds `.omp/RULES.md` and `.omp/agents/far.md`
- **THEN** neither response contains anything from the link target, no directory outside the inspected ones is enumerated, and the owner root's `.omp/RULES.md` and `.omp/agents/far.md` are absent in both (first: both searches end at the link; second: the workspace root's real `.omp` holds an entry and so is the nearest, and the agents search ends at the link)
- **WHEN** the workspace holds none of the files, the id belongs to another account, or the request carries a body
- **THEN** the responses are 200 `{files:[]}`, 404 not_found and 400 bad_request; a workspace of the caller whose root is unusable also answers 200 `{files:[]}`
