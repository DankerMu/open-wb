## MODIFIED Requirements

### Requirement: 会话 REST
registerSessionRoutes(app,{store,supervisor,agentDir,sandboxRoot,workspaceRootOf}) SHALL register GET/POST /api/sessions, GET /api/sessions/:id/messages, POST /api/sessions/:id/prompt, POST /api/sessions/:id/stop, POST /api/sessions/:id/regenerate, POST /api/sessions/:id/fork, POST /api/sessions/:id/approvals/:approvalId, POST /api/sessions/:id/undo, PATCH /api/sessions/:id and DELETE /api/sessions/:id (eleven routes). All SHALL use the existing cookie guard and authenticated principal.id; all matched responses SHALL carry Cache-Control:no-store without changing sibling routes. Unauthenticated requests SHALL return401 before body parsing. Unknown or foreign session ids SHALL return identical404 not_found before body parsing, with no writes or supervisor dispatch.
Id-scoped authorization SHALL use the existing owner-scoped store.getMessages(sessionId,principal.id) null result before parsing; acceptPrompt SHALL independently recheck ownership on admission. REST SHALL NOT use the trusted-supervisor-only runtimeState accessor for authorization.
registerSessions SHALL additionally register `GET /api/commands` (`rest-commands.ts`), whose contract is Requirement「Slash 命令白名单与命令目录」, and `GET /api/project-config` (`rest-project-config.ts`), whose contract is Requirement「项目配置文件列表」 (neither is one of the eleven session routes, neither is a content-parser owner, and neither reads a session: both answer for the cwd of an optional `workspaceId`); `agentDir`, the sandbox root and the owner-scoped workspace `rootOf` are passed to registerSessionRoutes for the prompt route's `toWireText` and to the command route; the project-config route takes the sandbox root and `rootOf` only. POST /api/sessions SHALL accept an optional body `{workspaceId?,scene?,approvalMode?,modelId?,reasoningEffort?}` whose validation, binding and audit rules are session-metadata「会话创建与空间绑定」 and session-composer-settings「创建会话时的设置与继承」, and SHALL return201 the session view {id,title:null,status:"idle",createdAt,updatedAt,scene,workspaceId,pinnedAt:null,archivedAt:null,pendingApproval:false,temporaryWorkspace,approvalMode,modelId,reasoningEffort} with `scene` equal to the accepted value or null when absent, and `workspaceId` equal to the accepted value (`temporaryWorkspace` false) or, when absent, the id of the temporary workspace created for this session in the same transaction (`temporaryWorkspace` true; temporary-workspaces「临时空间的创建」) — a bodyless request therefore yields a null `scene` and a non-null `workspaceId` — and with `approvalMode`/`modelId`/`reasoningEffort` equal to the effective values of the new row (session-composer-settings「有效值解析」). GET /api/sessions SHALL return200 {sessions:[...]} restricted to the owner and ordered updatedAt descending with the store's stable tie-break. PATCH /api/sessions/:id and DELETE /api/sessions/:id follow session-metadata「会话元数据修改」 and「会话删除」. POST /api/sessions/:id/undo follows message-undo「撤回 REST」. registerSessions SHALL also register `GET /api/sessions/events` (session-list-push「列表事件端点」), which is not one of the eleven routes, reads no session id and is not a content-parser owner. registerSessions SHALL likewise register `GET /api/composer/options` (session-composer-settings「输入框选项端点」), which is not one of the eleven routes, reads no session and is not a content-parser owner. GET messages SHALL return200 {session,messages:[{id,role,content,thinking,status,createdAt,approvals,undo,attachments,error,thinkingMs,thinkingSegments,steps:[{id,ordinal,name,detail,output,changes,status,bodyOffset}]}],streamCursor:{epoch,seq},todo}, ordered createdAt/id and step ordinal; the snapshot object SHALL contain exactly the four top-level keys session,messages,streamCursor,todo, where `todo` is the session's stored task list — the normalized object `{phases:[{name,tasks:[{content,status}]}]}` parsed from `chat_sessions.todo`, or null for a stored NULL (content rules belong to session-todo「任务清单快照」) — and is not part of any session view; step output SHALL be a string, empty for a running step or a stored NULL. `thinking` SHALL be present on every message as `string | null` (a stored NULL, including every user message, reads null; content rules belong to thinking-fold). `undo` SHALL be present on every message: null on every assistant message and one of `available|too_large|failed|command|unbound|none` on every user message (message-undo「可撤回状态」). `changes` SHALL be present on every step as `Change[] | null`, a stored NULL reading null and a stored value reading the array of `{path,added,removed,kind}` whose element rules belong to turn-artifacts. `approvals` SHALL be present on every message as an array of all `chat_approvals` rows of that message in ascending id order, each `{id,tool,title,requestedAt,expiresAt,decision,stepId}` with `decision` ∈ `allow|deny|timeout|null` and `stepId` the `chat_approvals.step_id` value (`null` for a stored NULL; pairing rules belong to tool-approval「确认与步骤配对」); it SHALL be `[]` for a user message and for an assistant message without approval rows. Several pending (`decision:null`) entries MAY coexist on one message (parallel tool calls); a later approval request never replaces an earlier entry. `attachments` SHALL be present on every message as an array of `{path,size}` in stored order — the attachments recorded when that user message was admitted (message-attachments「附件落库与快照」) — and SHALL be `[]` for a stored NULL, which includes every assistant message and every user message sent without attachments. `error` SHALL be present on every message as `null` or the four-key object `{reason,message,status,detail}` of upstream-failure「失败的公开形状」 (content, classification and sanitisation rules belong to upstream-failure): every user message reads `null`, and an assistant message reads `null` when its three error columns are all NULL (including every turn that did not fail, every `stopped` turn and every row the startup reconciliation set to `failed`). `thinkingMs` SHALL be present on every message as `null` or a non-negative safe integer, the `thinking_ms` column value of thinking-fold「思考时长记录与下发」 (when it is written, cleared and copied belongs to thinking-fold): every user message reads `null`, and an assistant message reads `null` while its column is NULL. `thinkingSegments` SHALL be present on every message as an array of that message's `chat_thinking_segments` rows in ascending row id order, each exactly `{bodyOffset,thinkingOffset,thinkingLength,stepsBefore,thinkingMs}` read from the columns `body_offset`, `thinking_offset`, `thinking_length`, `steps_before` and `thinking_ms` (`thinkingLength` and `thinkingMs` SHALL read `null` for a stored NULL — the segment is open, or the host exited while it was open — while `bodyOffset`, `thinkingOffset` and `stepsBefore` are never null; when rows are written belongs to thinking-fold「思考时长记录与下发」): every user message and every assistant message without rows reads `[]`. `bodyOffset` SHALL be present on every step as `null` (a stored NULL, which includes every step written before migration 045) or the non-negative `chat_steps.body_offset` value (chat-stream「分段位置的记录与下发」). Session views (list entries, create/PATCH responses, the snapshot `session`, the fork and undo response `session`) SHALL contain exactly the fourteen keys id,title,status,createdAt,updatedAt,scene,workspaceId,pinnedAt,archivedAt,pendingApproval,temporaryWorkspace,approvalMode,modelId,reasoningEffort, where `scene` ∈ `office|code|design|null`, `workspaceId` is the bound workspace id or null, `pinnedAt` is epoch milliseconds or null, and `archivedAt` (epoch milliseconds or null), `pendingApproval` (boolean) and `temporaryWorkspace` (boolean) are defined by session-metadata「会话视图扩展键」, and `approvalMode` ∈ `always-ask|write|yolo`, `modelId` (a string) and `reasoningEffort` ∈ `off|minimal|low|medium|high|xhigh|max|null` are the effective values of session-composer-settings「有效值解析」 (never the raw stored columns); GET /api/sessions lists archived sessions too (the client separates them by `archivedAt`) (`parent_session_id` and `omp_session_file` SHALL NOT be exposed); Only the declared streamCursor boundary SHALL expose the generation epoch; other internal ownership/runtime fields and step timing fields SHALL NOT leak. The complete owner-scoped tree (including `todo`) and synchronous supervisor.streamCursor(sessionId) SHALL be captured together in the same preParsing stack before done, with no await between them; the handler SHALL serialize only that cached pair. streamCursor SHALL NOT replace owner authorization.
POST /api/sessions/:id/stop and POST /api/sessions/:id/regenerate SHALL be bodyless content-parser owners (the logout precedent): any parsed body (including `{}`), empty-or-malformed JSON, unsupported media or an envelope above their minimal body limit SHALL return400 bad_request after authorization and before any supervisor call, frame or write. When the session is `running`, stop SHALL call supervisor.stop(sessionId) — which holds the session's control claim for the call, first settles every pending approval of that turn, if any exist (the pending set is the snapshot read on entry; it is not re-read before the `abort` frame), as `deny` (per approval: persist decision/decided_at and its `session.approval` audit row in one transaction → answer `Deny` → publish `approval.resolved`) and then writes the `abort` frame; when the turn's prompt frame is not yet written, stop instead records a stop intent and the supervisor writes `abort` right after that prompt's dispatch receipt resolves (after the stop call has returned), so stop neither cancels the dispatch nor compensates the accepted rows and the prompt request still returns its normal202 body (a failed acquisition or dispatch still follows the ordinary prompt compensation, and the intent never rewrites a terminal status another path reached first) — and return202 with body exactly `{}` without waiting for the turn to end; for any other status it SHALL return204 with no writes and no supervisor call. The stopped turn ends with `turn.end{status:"stopped"}` and session/assistant/running steps read `stopped`.
POST /api/sessions/:id/regenerate: a `running` session, or a session whose control claim is held by another regenerate, fork or stop, SHALL return409 session_busy. A session whose history does not end with an assistant message immediately preceded by a user message, or whose last user message classifies as a whitelisted command (`classifyPrompt` → `builtin|skill`, Requirement「Slash 命令白名单与命令目录」), SHALL return400 bad_request (checked after the 409 busy check, with no spawn, frame or row change). Otherwise it SHALL call supervisor.regenerate(sessionId), which registers the session's control claim with the last assistant message id read by the precheck and releases it once dispatch completes or the response returns: acquire the session's process — reusing a live one, or through the same lazy acquisition as prompt (a normal new generation, stream_epoch+1 with a fresh ring) when it has been reclaimed — through the process cap (`agent_capacity` → 503), `get_branch_messages`, require the last entry's `text` to be a wire candidate of the stored last user message (Requirement「Slash 命令白名单与命令目录」 Branch alignment; any other outcome, including an empty list → 502 agent_unavailable with no row change), `branch{entryId}`, `get_state`, then in one SQLite transaction — which SHALL first recheck that the session status is not `running` and its last assistant message id still equals the precheck's, otherwise write nothing, retire the process and return409 session_busy — delete the old assistant row (steps, approvals and thinking segments cascade), insert a new empty `running` assistant row, set `omp_session_file` to the new file and session status `running` (leaving `chat_sessions.todo` unchanged), and dispatch the branch-returned text as the prompt, prefixed with one U+0020 when it starts with `/` (turn-control「重新生成 REST」); it SHALL return202 {assistantMessageId} of the new row. Runtime failure before the transaction SHALL leave every row unchanged and map to502 agent_unavailable; dispatch failure after the transaction SHALL settle the new assistant row and session as `failed`, return502 agent_unavailable (rows are already terminal, nothing is compensated) and SHALL NOT resurrect the deleted row.
POST /api/sessions/:id/fork SHALL accept only application/json and an object with exactly messageId:number; any other shape, a messageId that is not a `user` message of this session, a messageId whose stored content classifies as a whitelisted command (`classifyPrompt` → `builtin|skill`), or wrong media/malformed JSON SHALL return400 bad_request (the command check runs after the 409 busy check, with no spawn, frame or row change). A `running` source session, or one whose control claim is held by another regenerate, fork or stop, SHALL return409 session_busy. Otherwise the supervisor SHALL register the source session's control claim (with the last assistant message id read by the precheck), retire the source session's live idle process if one exists (its history is in the file, so this is lossless), then run a temporary runtime through the process cap (`agent_capacity` → 503) with `--resume <source omp_session_file>`, `get_branch_messages`, align the stored user messages to the entries (Branch alignment) and take the entry aligned to the chosen message (no aligned entry → 502 agent_unavailable; no new session row exists), `branch{entryId}`, `get_state`, shut the temporary process down, then in one transaction — which SHALL first recheck that the source status is not `running` and its last assistant message id still equals the precheck's, otherwise write nothing and return409 session_busy — insert the new session row (same owner, copied title, copied `workspace_id` and `scene`, copied raw `approval_mode` (stored as the current `APPROVAL_MAX_MODE` when the source's raw mode is above it — session-metadata「fork 继承会话元数据」), `model_id` and `reasoning_effort`, `pinned_at` NULL, `todo` NULL (the task list is not copied), `parent_session_id` = source id, `omp_session_file` = the new file, `stream_epoch` 0). No new session row exists before this transaction commits, so every failure leaves none behind. The temporary runtime is not a session generation: it SHALL NOT bump either session's `stream_epoch`, owns no ring, publishes no events, is bound to no slot and counts only against the process cap. The transaction SHALL also copy every chat_messages/chat_steps row of the source that precedes the fork-point user message (new ids, same order, content, thinking, thinking_ms, status, timestamps and message attachments, step ordinal/detail/output/changes/body_offset, each copied verbatim including NULL), copy every `chat_thinking_segments` row of those copied messages onto the new message ids (new row ids in the same order; body_offset, thinking_offset, thinking_length, steps_before and thinking_ms verbatim including NULL), copy every `chat_approvals` row of those copied messages onto the new message ids (new approval ids; request_id, tool, title, requested_at, expires_at, decision and decided_at preserved; `step_id` remapped to the id of the copied step of the same message with the same ordinal as the step the source row names, and NULL when the source row's `step_id` is NULL or names no step of that message), and set the new session's status to the status of the last copied assistant message (`done`, `failed` or `stopped`), leaving it `idle` only when nothing is copied. The source session's rows, status and file SHALL be unchanged; its live process, if any, receives no frame and is retired before the temporary process starts. It SHALL return201 {session,draft,attachments} where `session` is the new session's public view (the same key set as every session view), `attachments` is the stored attachment array of the chosen user message (`[]` when it has none; message-attachments「重新生成与分叉中的附件」) and `draft` is the stored content of the chosen user message (equal to the branch text for every message not starting with `/`; never carries the escape space).
POST /api/sessions/:id/approvals/:approvalId SHALL accept only application/json and an object with exactly decision:"allow"|"deny"; other shapes/media/malformed JSON SHALL return400 bad_request. `approvalId` SHALL be a canonical positive decimal integer naming a `chat_approvals` row whose message belongs to this session, otherwise404 not_found identical to a missing session; a non-canonical approvalId SHALL be rejected before body parsing, and an approvalId not owned by this session SHALL be rejected after body parsing but before any write, answer frame or publish. A row whose `decision` is already set SHALL return409 approval_settled with no writes. A pending row SHALL be settled in this order: in one transaction persist decision/decided_at and its `session.approval` audit row → answer the child (`Approve` for allow, `Deny` for deny) and cancel its timeout timer → publish `approval.resolved` → return200 with the settled approval object `{id,tool,title,requestedAt,expiresAt,decision,stepId}` (one element of the snapshot's `approvals` array; answering never writes `stepId`).

## ADDED Requirements

### Requirement: 迁移 045 分段位置与确认关联
迁移 `045_chat_interleaved_segments.sql` SHALL 在既有 runner 持有的事务内执行，回执紧随 `044` 之后追加，只做以下三件事，不重建既有表、不回填：
1. `ALTER TABLE chat_steps ADD COLUMN body_offset INTEGER`：可空、无缺省、无 CHECK、无索引，追加为末列；
2. `ALTER TABLE chat_approvals ADD COLUMN step_id INTEGER`：可空、无缺省、无 CHECK、无外键、无索引，追加为末列（只会指向同一消息的步骤，由应用层保证；步骤只随其消息删除，而消息删除同时级联删除这一行，所以不需要外键）；
3. 新建 `chat_thinking_segments(id INTEGER PRIMARY KEY AUTOINCREMENT, message_id INTEGER NOT NULL REFERENCES chat_messages(id) ON DELETE CASCADE, body_offset INTEGER NOT NULL, thinking_offset INTEGER NOT NULL, steps_before INTEGER NOT NULL, thinking_length INTEGER NULL, thinking_ms INTEGER NULL, CHECK (body_offset >= 0 AND thinking_offset >= 0 AND steps_before >= 0 AND (thinking_length IS NULL OR thinking_length >= 0) AND (thinking_ms IS NULL OR thinking_ms >= 0)))` 及索引 `chat_thinking_segments_message(message_id)`。
既有列顺序、约束、索引与 `sqlite_sequence` 不变；032–044 的文件 SHALL 不改；受信迁移的计数断言随之加一。迁移本身不逆转。迁移账本拒绝「回执多于已发现的迁移文件」的库（`server/src/core/db/migration-ledger.ts:370-371`），所以已应用 045 的库不能直接交给不含 045 文件的旧构建：回退只能前滚修复，或在回退代码时保留 045 文件（旧代码不读写新列与新表），或连库一起恢复到部署前的备份。

#### Scenario: 新库与存量库
- **WHEN** `openDb` 打开一个新库，另打开一份持有前 044 条回执、带步骤、审批与思考的消息行的存量库副本
- **THEN** 回执里 `045` 恰出现一次且紧随 `044`；`chat_steps.body_offset` 与 `chat_approvals.step_id` 存在、为 INTEGER、可空、无缺省，各为所在表的最后一列；`chat_thinking_segments` 存在且列、约束、外键与索引如上；存量库每行原有列值与行数不变，新列读作 NULL，`chat_thinking_segments` 为空；`PRAGMA foreign_key_check` 为空；再次打开目录不变

#### Scenario: 约束与级联
- **WHEN** 向 `chat_thinking_segments` 写入 `body_offset` 为 -1 或 `thinking_ms` 为 -5 的行，或 `message_id` 不存在的行；另删除一条带两行思考段的助手消息
- **THEN** 三种写入都被 SQLite 拒绝（前两种违反 CHECK，第三种违反外键，`foreign_keys` 已开启）、既有行不变；删除后该消息的思考段行不存在，无孤儿行

#### Scenario: 中途失败可重试
- **WHEN** 在一次性副本里预置已存在的 `chat_thinking_segments` 表使 `045` 失败，随后移除冲突对象重试
- **THEN** 失败时没有 `045` 的回执，`chat_steps` 与 `chat_approvals` 没有新列，此前的回执与数据不变；重试时恰应用一次
