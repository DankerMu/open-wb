# Spec delta: chat-harness（S1c B 修改）

> 本 delta 按仓内先例**整段重述**被修改的 Requirement（含其全部 Scenario）；基线为 change A（`s1c-turn-control-governance`）对同名 Requirement 的重述文本（A 先于 B 归档），归档时以本文整段替换同名 Requirement，未在此重述的 Requirement（含 A 重述的「HTTP 冒烟对话用例」「UI 走查对话步骤」）不变。B 相对 A：`make smoke` 配方追加 `smoke/session-meta.hurl`（Make oracle 同 PR），新增会话元数据 HTTP 冒烟与 UI 走查两条 Requirement，Playwright `testMatch` 改 glob。

## MODIFIED Requirements

### Requirement: 手动真实上游冒烟入口
`make smoke-live` SHALL consume an already-running service without build/start/stop. If MODEL_UPSTREAM_BASE_URL or MODEL_UPSTREAM_API_KEY is absent or empty, it SHALL exit nonzero and identify the missing variable without printing its value or executing Hurl. Required values SHALL be transferred literally through Make and quoted shell expansion, without evaluating Make/shell syntax in their bytes. After gates, missing Hurl SHALL produce explicit installation guidance. Hurl SHALL run in a clean child environment containing only PATH, with `--test --jobs 1 --retry 0`, `base_url` from raw SMOKE_BASE_URL, `content_pattern=^.+$`, `min_bash_steps=0`, `skip_turn_control=true`, and only `smoke/chat.hurl`. Upstream gate values SHALL NOT appear in Hurl args/environment or diagnostics. Hurl failure SHALL propagate nonzero. The existing `make smoke` recipe SHALL change only by gaining `--variable "skip_turn_control=false"` (S1c A) and by appending `smoke/session-meta.hurl` as its last argument, directly after `smoke/files.hurl` (S1c B), so that its Hurl file arguments are exactly `smoke/public.hurl smoke/auth.hurl smoke/chat.hurl smoke/files.hurl smoke/session-meta.hurl` in that order and every other byte of the recipe (the hurl preflight line, `env -i`, flags and `--variable` arguments as left by A) is unchanged; B adds no Make target, no Hurl variable and no CI job, and the `smoke-live` recipe is not changed by B (it still runs only `smoke/chat.hurl`). The Make oracle (`scripts/test-ci-harness.sh`) SHALL pin both updated recipes; when B appends the file, the oracle's expected `smoke` recipe and every mutation decoy derived from it (the variants that today end in `smoke/chat.hurl smoke/files.hurl`, including the `endif`, spaced `smoke :` and `phase2-decoy` redefinition decoys) SHALL be updated in the same PR, so the guardrail suite accepts exactly the new recipe and still rejects each mutation.
The target SHALL be listed exactly once in .PHONY and the command header. The existing Make oracle SHALL protect its exact recipe and reject duplicate/redefined targets, including `smoke-live :`, missing/duplicated .PHONY entries and mutated invocation.

#### Scenario: Missing configuration fails before invocation
- WHEN either required upstream variable is missing or empty
- THEN make exits nonzero with that variable name and no Hurl invocation, without revealing configured values

#### Scenario: Literal clean invocation
- WHEN both gate values are nonempty and Hurl is discoverable
- THEN one clean child receives exact shape-only argv and caller baseURL bytes, no upstream values, and the target returns the Hurl result

#### Scenario: Exact command guard
- WHEN the Make oracle inspects a duplicate spaced smoke-live header, altered recipe or missing .PHONY entry
- THEN it rejects the changed contract; the current complete guardrail suite remains green

#### Scenario: smoke 配方追加会话元数据冒烟
- **WHEN** the Make oracle inspects the `smoke` recipe after S1c B, and separately a candidate that omits `smoke/session-meta.hurl`, places it before `smoke/files.hurl`, adds it to `smoke-live`, or adds a second recipe line for it
- **THEN** the exact recipe ending `smoke/files.hurl smoke/session-meta.hurl` is accepted together with the unchanged `smoke-live` recipe, each candidate is rejected, and `make test-guardrails` stays green on the real Makefile

#### Scenario: AGENTS.md 冒烟证据行随配方同 PR 更新
- **WHEN** the same PR appends `smoke/session-meta.hurl` to the `smoke` recipe
- **THEN** the `HTTP smoke` row in `AGENTS.md` (the row `scripts/test-ci-harness.sh` pins verbatim as the oracle) is rewritten in the same PR to list `session-meta.hurl` as the fifth file with five-file wording, the oracle's expected row text is updated to the identical string, and `make test-guardrails` rejects a Makefile/AGENTS.md pair where only one side changed


## ADDED Requirements

### Requirement: 会话元数据 HTTP 冒烟
`smoke/session-meta.hurl` SHALL independently start with empty cookies (it does not depend on public/auth/chat/files) and SHALL be rerunnable because `make smoke` runs twice: it logs in as `zhangsan` (exact 200 Principal), creates or adopts a workspace named `smoke-sessions` (`POST /api/workspaces {"name":"smoke-sessions"}` → 201 or 409 only) and captures its id from `GET /api/workspaces` by that unique name, following `files.hurl`. It SHALL then, in order:
1. `POST /api/sessions {"workspaceId":<workspace id>,"scene":"code"}` → exact 201 whose body has exactly the eight keys `id,title,status,createdAt,updatedAt,scene,workspaceId,pinnedAt` (`jsonpath "$.*" count == 8`) with `title` null, `status` `idle`, `scene` `code`, `workspaceId` the captured id and `pinnedAt` null; capture `session_id`. Then `GET /api/audit?limit=1` → latest event `kind` `session.bind` with `actorId` `u1`.
2. `POST /api/sessions {"workspaceId":"00000000000000000000000000000000","scene":"code"}` (a well-formed but unknown workspace id) → exact 404 with `error.code` `not_found`; `POST /api/sessions {"scene":"code","color":"red"}` (extra key) → exact 400 with `error.code` `bad_request`; then `GET /api/audit?limit=1` → latest `kind` still `session.bind` for `session_id` (neither rejected create wrote an audit row). `POST /api/sessions` without a body → exact 201 with `workspaceId` null and `scene` null (the bodyless create keeps working); capture `other_id`.
3. `PATCH /api/sessions/{{session_id}} {"title":"冒烟会话","scene":"design","pinned":true}` → exact 200 eight-key DTO with that `title`, `scene` `design`, a nonnull `pinnedAt` and unchanged `workspaceId`; `PATCH` with an extra key (`{"color":"red"}`) → exact 400 with `error.code` `bad_request`; `GET /api/sessions` → 200 whose entry for `session_id` reflects title, scene, nonnull `pinnedAt` and the workspace id; `PATCH {"pinned":false}` → 200 with `pinnedAt` null and title/scene unchanged.
4. Prompt once: `POST /api/sessions/{{session_id}}/prompt {"message":"WORKBUDDY_THINK 会话元数据冒烟"}` → exact 202 capturing `assistantMessageId` (not retried). Because omp runs in `--approval-mode write` and the controlled upstream's first round is bash, the file SHALL answer the approval exactly as `chat.hurl` does under `make smoke`: poll messages GET with bounded retries until the captured assistant's `approvals` holds exactly one pending entry, `POST …/approvals/:approvalId {"decision":"allow"}` → 200 with `decision` `allow`, then poll messages GET with bounded retries until the captured assistant and the session are `done`. The file SHALL NOT use `skip_turn_control` (it never runs under `smoke-live`).
5. On the done snapshot assert: the captured assistant's `content` matches `content_pattern` (the exact fixed reply under `make smoke`), its `thinking` equals exactly `先读需求，再列要点，最后作答。` (the controlled upstream's `WORKBUDDY_THINK` reasoning relayed through real omp as `thinking_delta` and persisted into `chat_messages.thinking`), its bash step is `done`, and `session.title` is still `冒烟会话` (the first prompt SHALL NOT overwrite a title set by PATCH).
6. `DELETE /api/sessions/{{session_id}}` → exact 204 with empty body (the session is `done`, so this exercises the non-running deletion path; the running path is proven by server integration tests); `GET /api/audit?limit=1` → latest `kind` `session.delete` with `actorId` `u1`; `GET /api/sessions/{{session_id}}/messages` → 404; `GET /api/sessions` → 200 without an entry for `session_id`; a second `DELETE /api/sessions/{{session_id}}` → exact 404.
7. Ownership: logout (204), login as `lisi`, `POST /api/sessions {"workspaceId":<zhangsan's workspace id>}` → exact 404 `not_found` (a foreign workspace is indistinguishable from an unknown one and creates no session), `PATCH /api/sessions/{{other_id}} {"title":"x"}` → 404 and `DELETE /api/sessions/{{other_id}}` → 404, logout; login as `zhangsan`, `GET /api/sessions/{{other_id}}/messages` → 200 (the foreign attempts changed nothing), `DELETE /api/sessions/{{other_id}}` → 204, logout (204).
The file SHALL leave no live authentication session, running turn or session row it created; the adopted workspace remains for the next run. It asserts only the public REST/audit contract and consumes the caller-owned service like the other smoke files.
Note (non-normative): the `thinking` assertion proves that reasoning frames reach the host through real omp and are persisted and served in the snapshot; the controlled upstream emits `reasoning_content` whenever the marker is present and omp parses it on the response side regardless of the model entry's `reasoning` flag, so this file does not prove the `MODEL_REASONING` switch nor any real model's reasoning (grill open item 1 remains for `smoke-live`/manual verification against DMXAPI). `make smoke` runs with the default `MODEL_REASONING` (on).

#### Scenario: 绑定、元数据、思考与删除全链路
- **WHEN** `make smoke` runs `smoke/session-meta.hurl` twice against the compiled app, real pinned omp 18.0.10 and the controlled upstream
- **THEN** each run creates a bound `code` session with an exact eight-key DTO and a `session.bind` audit event, the unknown-workspace create is 404 and the extra-key create is 400 without an audit row, `lisi`'s create bound to `zhangsan`'s workspace is 404, PATCH updates and GET reflects title/scene/pin and unpin, the extra-key PATCH is 400, the prompt's single bash approval is answered `allow` and the turn completes with the exact reply, `thinking` exactly `先读需求，再列要点，最后作答。`, a done bash step and the PATCHed title intact, DELETE is 204 with a `session.delete` audit event, the deleted session's messages GET and second DELETE are 404, and the second run passes identically on the adopted workspace

#### Scenario: 删除与所有权不可伪造
- **WHEN** a candidate returns 204 but keeps the row (list or messages GET still find it), answers a second DELETE with 204, lets `lisi` PATCH or DELETE `zhangsan`'s session or create a session bound to `zhangsan`'s workspace, accepts an unknown `workspaceId` or an extra create key, lets the prompt title overwrite the PATCHed title, or drops `thinking` (null or different text)
- **THEN** the corresponding assertion fails without retrying any POST, PATCH or DELETE

### Requirement: UI 走查会话元数据
`web/playwright.config.ts` `testMatch` SHALL change from `"ui-walk.spec.ts"` to exactly `"ui-walk*.spec.ts"`, which selects `web/e2e/ui-walk.spec.ts` and the new `web/e2e/ui-walk-sessions.spec.ts` and no helper module (`ui-walk-gate.ts`, `ui-walk-layout.ts`, `ui-walk-oracle.ts`, `route-hold.ts`, `ui-shots.mjs` do not end in `.spec.ts`); the same file SHALL also be edited so that `globalTimeout` changes from `150_000` to `300_000` (a required edit of `web/playwright.config.ts` in this change, bounding both spec files across both projects); every other config value (serial single worker, retries 0, per-action/navigation timeouts, output handling, the `desktop-light` 1440×900 light and `mobile-dark` 390×844 dark projects) is unchanged, `make ui-walk` still runs `npm run ui-walk --workspace web`, and the CI ui-walk job keeps its identity and `timeout-minutes`. The journey of `ui-walk.spec.ts` (Requirement `UI 走查对话步骤`, including A's approval/stop/regenerate/fork steps) is not changed by B except where B's sidebar partitions change the locator path to its unbound sessions (they are listed under the `任务` section).
`web/e2e/ui-walk-sessions.spec.ts` SHALL run one serial journey per project against the real server stack of `make ui-walk` (compiled app, real pinned omp 18.0.10, controlled upstream), under the existing browser error oracle (no unexpected console/page errors), with no browser route fulfillment, fake EventSource or arbitrary sleeps. It does **not** select fake-omp scenarios (the ui-walk stack runs real omp); it drives the controlled upstream through the prompt-text markers of omp-test-harness Requirement `受控上游思考与写入标记`. The journey SHALL, in order:
1. Log in as `zhangsan` through the UI and ensure the workspace `ui-walk-sessions` exists via the page's authenticated request context (`POST /api/workspaces` → 201 or 409 only).
2. On the welcome state, click the scene pill `代码开发`: it becomes pressed (`aria-pressed="true"`, the other two `日常办公`/`创意设计` not pressed) and the `快捷任务` chips switch to the code-scene list. The composer footer reads `任务启动于` `未选择`; opening its workspace popover shows the search input `搜索工作空间`, typing `ui-walk-sessions` and choosing it makes the footer read `任务启动于` `ui-walk-sessions`.
3. Send `WORKBUDDY_THINK WORKBUDDY_WRITE 会话走查 <uuid>` (a fresh UUID per project). The observed `POST /api/sessions` request body SHALL parse to a JSON object deep-equal to `{"workspaceId":<that workspace id>,"scene":"code"}`. The turn raises no approval bar (the tool round is a write-tier `write`), the `write` step reaches `已完成`, and the assistant reaches the exact fixed reply and done state.
4. Thinking fold: the assistant message shows, before its answer body, a collapsed `<details>` whose summary is `深度思考过程`; expanding it shows exactly `先读需求，再列要点，最后作答。`.
5. File changes: the assistant message shows a card headed `文件变更（1 个）` with one row whose path reads `zhangsan/ui-walk-sessions/workbuddy-report.html` (ADR-0011 logical path, never the sandbox root), marked `写入` with no +/− counts, and whose `查看详情` 跳到该空间的文件页 — it navigates to `/files?ws=<workspace id>` (the files page accepts only `ws`, `web/src/features/files/page.tsx:268`; there is no path parameter, so it lands on the workspace, not the file); an `HTML` artifact card offers `打开网页预览`, which opens a dialog containing an `iframe` with `sandbox="allow-scripts"` (no `allow-same-origin`) whose document shows the heading `WorkBuddy`; the topbar `产物面板` opens a drawer listing that one file. (Edit `+N/−N` counts are not reachable through real omp with the controlled upstream; they are proven by the fake omp `edit-write` scenario in server tests.)
6. Sidebar: the session is listed exactly once, under the `空间` section's `ui-walk-sessions` group, not under `任务` or `置顶任务` (on `mobile-dark` through the sidebar overlay, as in the existing journey).
7. Pin: the entry's `更多` menu → `置顶任务` moves the entry to the `置顶任务` section (still exactly one entry for the session, gone from `空间`), and the menu then offers `取消置顶`.
8. Rename: `更多` → `重命名` opens `重命名任务`; entering a new title and `保存` updates the sidebar entry and the topbar title; after a page reload the new title and the pinned section persist.
9. Search: the topbar `对话内搜索` opens the `搜索对话内容` box; typing the UUID shows the counter `1/1`, scrolls the user message into view and marks it highlighted; a term with no match shows `0/0`; `Esc` closes the box and clears the highlight.
10. Delete: `更多` → `删除` opens the confirmation `删除任务` with text `确定要删除「<title>」吗？删除后不可恢复。`; confirming `删除` shows `Toast` `任务已删除`, the entry disappears from every sidebar section, the page no longer selects `?session=<id>` (welcome state), and `GET /api/sessions/<id>/messages` through the page's request context answers 404.
If the journey fails before step 10, a `finally` block SHALL delete the created session through `DELETE /api/sessions/<id>` (204 or 404 accepted; if the turn is still running and the DELETE answers 409 `session_busy` because the running-path deletion has not landed yet, the block first calls `POST /api/sessions/<id>/stop`, polls `status` to a terminal value and repeats the DELETE) so no running turn or session row is left; the adopted workspace and the overwritten `workbuddy-report.html` remain for the next run. The test consumes the caller-owned app/upstream without starting or stopping them and arms no gate.

#### Scenario: 会话元数据走查
- **WHEN** `make ui-walk` runs with the glob `ui-walk*.spec.ts` against the real stack in both `desktop-light` (1440×900) and `mobile-dark` (390×844)
- **THEN** in each project the scene pill and footer workspace choice produce a bound `code` session, the thinking fold shows exactly `先读需求，再列要点，最后作答。`, the file-change card shows the one written file by logical path with `写入`, the html preview renders in a `allow-scripts`-only sandboxed iframe, the sidebar moves the session from `空间 › ui-walk-sessions` to `置顶任务` on pin, rename persists across reload, search counts `1/1` with highlight and `0/0` for a miss, and delete removes the session (Toast `任务已删除`, REST 404); `ui-walk.spec.ts` still passes unchanged in both projects and the whole run finishes within `globalTimeout` 300000 ms

#### Scenario: 假进度不能满足走查
- **WHEN** a candidate renders the thinking fold or file-change card from client-side fabrication without a server `thinking`/`changes` value, lists the session in two sidebar sections, keeps it after delete, loses the rename on reload, or shows a search counter without scrolling to and highlighting the matching message
- **THEN** the corresponding DOM or REST assertion fails and the walkthrough fails rather than passing on partial state
