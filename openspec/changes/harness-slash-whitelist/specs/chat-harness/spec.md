## MODIFIED Requirements

### Requirement: 会话元数据 HTTP 冒烟
`smoke/session-meta.hurl` SHALL independently start with empty cookies (it does not depend on public/auth/chat/files) and SHALL be rerunnable because `make smoke` runs twice: it logs in as `zhangsan` (exact 200 Principal), creates or adopts a workspace named `smoke-sessions` (`POST /api/workspaces {"name":"smoke-sessions"}` → 201 or 409 only) and captures its id from `GET /api/workspaces` by that unique name, following `files.hurl`. It SHALL then, in order:
1. `POST /api/sessions {"workspaceId":<workspace id>,"scene":"code"}` → exact 201 whose body has exactly the eight keys `id,title,status,createdAt,updatedAt,scene,workspaceId,pinnedAt` (`jsonpath "$.*" count == 8`) with `title` null, `status` `idle`, `scene` `code`, `workspaceId` the captured id and `pinnedAt` null; capture `session_id`. Then `GET /api/audit?limit=1` → latest event `kind` `session.bind` with `actorId` `u1`, `workspaceId` the captured id and `detail.sessionId` equal to `session_id`.
2. `POST /api/sessions {"workspaceId":"00000000000000000000000000000000","scene":"code"}` (a well-formed but unknown workspace id) → exact 404 with `error.code` `not_found`; `POST /api/sessions {"scene":"code","color":"red"}` (extra key) → exact 400 with `error.code` `bad_request`; then `GET /api/audit?limit=1` → latest `kind` still `session.bind` whose `detail.sessionId` is `session_id` (neither rejected create wrote an audit row). `POST /api/sessions` without a body → exact 201 with `workspaceId` null and `scene` null (the bodyless create keeps working); capture `other_id`.
3. `PATCH /api/sessions/{{session_id}} {"title":"冒烟会话","scene":"design","pinned":true}` → exact 200 eight-key DTO with that `title`, `scene` `design`, a nonnull `pinnedAt` and unchanged `workspaceId`; `PATCH` with an extra key (`{"color":"red"}`) → exact 400 with `error.code` `bad_request`; `GET /api/sessions` → 200 whose entry for `session_id` reflects title, scene, nonnull `pinnedAt` and the workspace id; `PATCH {"pinned":false}` → 200 with `pinnedAt` null and title/scene unchanged.
4. Prompt once: `POST /api/sessions/{{session_id}}/prompt {"message":"WORKBUDDY_THINK 会话元数据冒烟"}` → exact 202 capturing `assistantMessageId` (not retried). Because omp runs in `--approval-mode write` and the controlled upstream's first round is bash, the file SHALL answer the approval exactly as `chat.hurl` does under `make smoke`: poll messages GET with bounded retries until the captured assistant's `approvals` holds exactly one pending entry, `POST …/approvals/:approvalId {"decision":"allow"}` → 200 with `decision` `allow`, then poll messages GET with bounded retries until the captured assistant and the session are `done`. The file SHALL NOT use `skip_turn_control` (it never runs under `smoke-live`).
5. On the done snapshot assert: the captured assistant's `content` matches `content_pattern` (the exact fixed reply under `make smoke`), its `thinking` equals exactly `先读需求，再列要点，最后作答。` (the controlled upstream's `WORKBUDDY_THINK` reasoning relayed through real omp as `thinking_delta` and persisted into `chat_messages.thinking`), its bash step is `done`, and `session.title` is still `冒烟会话` (the first prompt SHALL NOT overwrite a title set by PATCH).
6. Slash whitelist through real omp: `GET /api/commands` → exact 200 whose `commands` has exactly two entries with `source` `builtin` and `name` `compact`, `todo` in that order (the smoke state dir installs no skill). `POST /api/sessions/{{session_id}}/prompt {"message":"/todo"}` → exact 202 capturing `todo_assistant_id`; poll messages GET with bounded retries until that assistant is `done` (no approval: the builtin runs without the model); assert its `content` equals exactly `No todos. Use /todo append <task> to start one.` (omp's own text relayed as `command_output`), its `steps` is empty and the user message content is `/todo`. Then `POST …/prompt {"message":"/session WORKBUDDY_THINK 冒烟"}` → exact 202 capturing `session_cmd_assistant_id` (`session` is a real omp builtin with an RPC `handle` outside the whitelist: unescaped it would answer with its usage text and never reach the model); poll until `done` (the escaped text reaches the model, whose controlled upstream answers the `WORKBUDDY_THINK` marker with its fixed reasoning; the session already holds a tool result from step 4, so there is no tool round and no approval is pending); assert the user message content equals `/session WORKBUDDY_THINK 冒烟` (persisted as typed, no leading space), the assistant `content` matches `content_pattern` (the fixed reply, proving the text was answered by the model rather than executed as a command), its `thinking` equals exactly `先读需求，再列要点，最后作答。` (the marker inside the escaped text reached the model) and its `steps` is empty.
7. `DELETE /api/sessions/{{session_id}}` → exact 204 with empty body (the session is `done`, so this exercises the non-running deletion path; the running path is proven by server integration tests); `GET /api/audit?limit=1` → latest `kind` `session.delete` with `actorId` `u1` and `detail.sessionId` equal to `session_id`; `GET /api/sessions/{{session_id}}/messages` → 404; `GET /api/sessions` → 200 without an entry for `session_id`; a second `DELETE /api/sessions/{{session_id}}` → exact 404.
8. Ownership: logout (204), login as `lisi`, `POST /api/sessions {"workspaceId":<zhangsan's workspace id>}` → exact 404 `not_found` (a foreign workspace is indistinguishable from an unknown one and creates no session), `PATCH /api/sessions/{{other_id}} {"title":"x"}` → 404 and `DELETE /api/sessions/{{other_id}}` → 404, with the number of entries in `lisi`'s own `GET /api/sessions` read before the three attempts and again after them and found unchanged, logout; login as `zhangsan`, `GET /api/sessions/{{other_id}}/messages` → 200 (the foreign attempts changed nothing), `DELETE /api/sessions/{{other_id}}` → 204, logout (204).
The file SHALL leave no live authentication session, running turn or session row it created; the adopted workspace remains for the next run. It asserts only the public REST/audit contract and consumes the caller-owned service like the other smoke files.
Note (non-normative): the `thinking` assertion proves that reasoning frames reach the host through real omp and are persisted and served in the snapshot; the controlled upstream emits `reasoning_content` whenever the marker is present and omp parses it on the response side regardless of the model entry's `reasoning` flag, so this file does not prove the `MODEL_REASONING` switch nor any real model's reasoning (grill open item 1 remains for `smoke-live`/manual verification against DMXAPI). `make smoke` runs with the default `MODEL_REASONING` (on).

#### Scenario: 绑定、元数据、思考与删除全链路
- **WHEN** `make smoke` runs `smoke/session-meta.hurl` twice against the compiled app, real pinned omp 18.0.10 and the controlled upstream
- **THEN** each run creates a bound `code` session with an exact eight-key DTO and a `session.bind` audit event, the unknown-workspace create is 404 and the extra-key create is 400 without an audit row, `lisi`'s create bound to `zhangsan`'s workspace is 404, PATCH updates and GET reflects title/scene/pin and unpin, the extra-key PATCH is 400, the prompt's single bash approval is answered `allow` and the turn completes with the exact reply, `thinking` exactly `先读需求，再列要点，最后作答。`, a done bash step and the PATCHed title intact, `GET /api/commands` lists exactly the two builtins, `/todo` completes with exactly omp's `No todos…` text and no step, `/session WORKBUDDY_THINK 冒烟` is persisted as typed and answered by the model's fixed reply with the marker's `thinking`, DELETE is 204 with a `session.delete` audit event, the deleted session's messages GET and second DELETE are 404, and the second run passes identically on the adopted workspace

#### Scenario: 删除与所有权不可伪造

- **THEN** the corresponding assertion fails without retrying any POST, PATCH or DELETE

### Requirement: UI 走查会话元数据
`web/playwright.config.ts` `testMatch` SHALL be exactly `"ui-walk*.spec.ts"`, which selects `web/e2e/ui-walk.spec.ts` and `web/e2e/ui-walk-sessions.spec.ts` and no helper module (no helper module under `web/e2e/` ends in `.spec.ts`), and `globalTimeout` SHALL be `300_000`, bounding both spec files across both projects; every other config value (serial single worker, retries 0, the 30 s per-test timeout, per-action/navigation timeouts, output handling, the `desktop-light` 1440×900 light and `mobile-dark` 390×844 dark projects) is unchanged, `make ui-walk` still runs `npm run ui-walk --workspace web`, and the CI ui-walk job keeps its identity and `timeout-minutes`. The journey of `ui-walk.spec.ts` (Requirement `UI 走查对话步骤`) is not changed.
`web/e2e/ui-walk-sessions.spec.ts` SHALL run one serial journey per project against the real server stack of `make ui-walk` (compiled app, real pinned omp 18.0.10, controlled upstream), under its own instance of the existing browser error oracle (its own two expected `/api/auth/me` 401 — before login and after the logout reload that ends the journey — and no unexpected console/page errors), with no browser route fulfillment, fake EventSource or arbitrary sleeps. It does **not** select fake-omp scenarios (the ui-walk stack runs real omp); it drives the controlled upstream through the prompt-text markers of omp-test-harness Requirement `受控上游思考与写入标记` and arms no gate. The journey SHALL, in order:
1. Log in as `zhangsan` through the UI and, before the chat page is opened (the chat page reads the workspace list when it mounts), ensure the workspace `ui-walk-sessions` exists via the page's authenticated request context (`POST /api/workspaces` → 201 or 409 only).
2. On the welcome state, click the scene pill `代码开发`: it becomes pressed (`aria-pressed="true"`, the other two `日常办公`/`创意设计` not pressed) and the `快捷任务` chips switch to the code-scene list. The composer footer reads `任务启动于` `未选择`; opening its workspace popover shows the search input `搜索工作空间`, typing `ui-walk-sessions` and choosing it makes the footer read `任务启动于` `ui-walk-sessions`.
3. Send `WORKBUDDY_THINK WORKBUDDY_WRITE 会话走查 <uuid>` (a fresh UUID per project). The `POST /api/sessions` request, observed and not fulfilled, SHALL carry a body that parses to a JSON object deep-equal to `{"workspaceId":<that workspace id>,"scene":"code"}`. The turn raises no approval bar (the tool round is a write-tier `write`), the `write` step reaches `已完成`, and the assistant reaches the exact fixed reply and done state.
4. Thinking fold: the assistant message shows, before its answer body, a collapsed `<details>` whose summary is `深度思考过程`; expanding it shows exactly `先读需求，再列要点，最后作答。`.
5. File changes: the assistant message shows a card headed `文件变更（1 个）` with one row whose path reads `zhangsan/ui-walk-sessions/workbuddy-report.html` (ADR-0011 logical path, never the sandbox root), marked `写入` with no +/− counts, and whose `查看详情` navigates to `/files?ws=<workspace id>` — asserted on the first navigation after the click, because the files page rewrites a missing or unknown `ws` to the first workspace and the settled URL would not tell — (the files page accepts only `ws`; there is no path parameter, so it lands on the workspace, not the file), after which the journey returns to the session by a real navigation; an `HTML` artifact card offers `打开网页预览`, which opens a dialog containing an `iframe` with `sandbox="allow-scripts"` (no `allow-same-origin`) whose document shows the heading `WorkBuddy`; the topbar `产物面板` opens a drawer listing that one file. (Edit `+N/−N` counts are not reachable through real omp with the controlled upstream; they are proven by the fake omp `edit-write` scenario in server tests.) The values shown in steps 4 and 5 SHALL also be read back from `GET /api/sessions/<id>/messages` through the page's request context: the assistant message's `thinking` equals that text, its one step's `changes` deep-equals `[{"path":"workbuddy-report.html","added":null,"removed":null,"kind":"write"}]`, and the session view carries `scene` `code` and that `workspaceId`.
6. Sidebar: the session is listed exactly once, under the `空间` section's `ui-walk-sessions` group, not under `任务` or `置顶任务` (on `mobile-dark` through the sidebar overlay, as in the existing journey).
7. Pin: the entry's row menu (the button named `更多操作：<title>` of that entry; on `mobile-dark` inside the sidebar overlay) → `置顶任务` moves the entry to the `置顶任务` section (still exactly one entry for the session, gone from `空间`), and the menu then offers `取消置顶` and no longer `置顶任务`.
8. Rename: the row menu → `重命名` opens the dialog `重命名任务` whose `任务名称` field holds the current title; entering a new title (unique per project) and `保存` closes the dialog and updates the sidebar entry and the topbar title; after a page reload the new title and the pinned section persist, and `GET /api/sessions` through the page's request context lists the session with that `title` and a non-null `pinnedAt`.
9. Search: the topbar `对话内搜索` opens the `搜索对话内容` box; typing the UUID shows the counter `1/1` and marks the user message as the current match (its article carries `aria-current="true"` and is fully in the viewport; the assistant's article carries no `aria-current`); replacing the term with one that has no match shows `0/0` and no current match; with the UUID typed again, `Esc` in the box closes it and clears the highlight.
10. Slash candidates through real omp: typing `/` in the composer shows the `命令候选` listbox with exactly `整理上下文`, `任务清单` (no skill is installed in the ui-walk state dir); typing `/t` leaves `任务清单`, `Enter` sets the draft to `/todo ` without sending; sending it shows the user bubble `/todo` and an assistant message whose body reads exactly `No todos. Use /todo append <task> to start one.` with no step card and no approval bar, and the composer unlocks. Then typing `/session WORKBUDDY_THINK <uuid2>` (a fresh UUID; `session` is a real non-whitelisted omp builtin) shows no listbox; `Enter` sends it; the user bubble shows `/session WORKBUDDY_THINK <uuid2>` as typed and the assistant reaches the exact fixed reply with no step card and no approval bar (the escaped text was answered by the model, not by omp's `/session` usage output; the session already holds the tool result of step 3, so the controlled upstream answers without a tool round). `GET /api/sessions/<id>/messages` through the page's request context then returns the `/todo` assistant with exactly that `content` and empty `steps`, the `/session …` user message with exactly the typed `content` (no leading space), and that turn's assistant with `thinking` exactly `先读需求，再列要点，最后作答。` (the `WORKBUDDY_THINK` marker inside the escaped text reached the model).
11. Delete: the row menu → `删除` opens the confirmation `删除任务` with text `确定要删除「<new title>」吗？删除后不可恢复。`; confirming `删除` shows `Toast` `任务已删除`, the entry disappears from every sidebar section, the page no longer selects `?session=<id>` (welcome state), and `GET /api/sessions/<id>/messages` through the page's request context answers 404.
A `finally` block around steps 2–11 SHALL delete the created session through the page's request context — `DELETE /api/sessions/<id>`, 204 or 404 accepted (404 once step 11 has deleted it; the server stops a running turn before deleting it) — on success and when a step fails, so no running turn or session row is left; the session id is taken from the 201 response of the observed `POST /api/sessions`, before the assertion on that request's body, so a failed step assertion cannot leave the session behind. The adopted workspace and the overwritten `workbuddy-report.html` remain for the next run. The journey then logs out through the UI. The test consumes the caller-owned app/upstream without starting or stopping them.
